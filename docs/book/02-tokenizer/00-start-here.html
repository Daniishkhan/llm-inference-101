What you will build: a tokenizer

A language model never sees letters. It reads token ids: whole numbers, from 0 to 50,256 for GPT-2, each standing for a short run of bytes. The tokenizer turns text into ids before the model runs, and turns the ids it produces back into text. It is the first and the last thing every request passes through, and this week you write one that gives exactly the ids GPT-2's own tokenizer gives.

You run it as uv run python -m llm101.tokenizer "some text". When it is finished it does three things:

  • It prints the text token by token, each token on a background colour that alternates between two, so that you can see where one token ends and the next begins.
  • Under the text, it prints the ids, separated by spaces.
  • Last, one line: N tokens, C characters, B bytes.

By default it loads GPT-2's tokenizer from the two files in data/gpt2/. With --train PATH it trains a tokenizer of its own on a text file instead, with --vocab-size tokens (512 unless you say otherwise), and uses that. The spec is the table in the module README, under "Spec".

Under the program sit seven milestones: UTF-8 by hand (M1); counting and merging pairs, then training (M2, M3); encoding and decoding with the merges (M4); GPT-2's real files and the program (M5); a fast encoder with a heap over a linked list (M6); and the Experiment in BENCH.md, on what a sentence costs in tokens and how fast your encoder is against tiktoken (M7). The table in "The six days" below gives each its chapter and its day.

You write all of it. tiktoken, OpenAI's tokenizer, is the tests' oracle: they build GPT-2's tokenizer with it from the same two files you load, and compare your ids with its ids. It is never your tool; the tests read gpt2.py to check that it does not import it.

Why the tokenizer comes second

A token is the unit everything else is counted in. Prompts are billed per token, the KV cache of Module 5 stores per token, a reply streams one token at a time, and Module 9 fills a batch by a budget of tokens. The same sentence takes very different numbers of tokens in different scripts, so the tokenizer sets what a request costs before the model sees it. The module also holds three patterns an interview asks about: hash maps (counting pairs), heaps (the best merge first) and linked lists (merging in place). And Module 1's harness measures it: M7 times your encoder with your own time_calls and summarise.

First principle

A tokenizer is a table and a few rules. GPT-2's starts from the 256 possible bytes, so that no text is ever unknown, and adds 50,000 merges, each gluing two existing tokens into a new one. The list of merges, in the order they were learned, is the tokenizer: encoding replays them on new text, earliest first, and decoding glues the bytes back together.

The rule: you type every line

This course rebuilds one skill above all: writing code with your own hands. So the rule of CLAUDE.md holds everywhere: you type every solution. The tutor writes the problems, the tests and the explanations, never the code that solves them.

For this book, that means three things.

  • The book teaches on different problems. Shifts and masks are taught on a colour, counting on the words of a text, heaps on a hospital's triage queue, linked lists on a playlist. Each mechanism is shown complete, one step away from your task, with its own names; the last step is yours.
  • Hints come one rung at a time. Chapter 8 has a hint ladder per milestone, folded away: four rungs, from "where to look" to "the same mechanism on a different problem". Open one, close the book, try again. There is no fifth rung.
  • There is no live tutor. The tutor panel on each page composes a prompt, with the chapter and milestone filled in, for you to paste into Claude Code, which answers under the same rules: an explanation, a question back, or one rung.

First-time setup

The hook from Module 1 is already installed. Run uv sync again, because this module adds two packages to pyproject.toml:

$ cd ~/Desktop/projects/llm-inference-101
$ uv sync
  • regex, a runtime dependency. GPT-2's split pattern uses \p{L}, "any letter, in any script", which Python's own re does not know (chapter 3).
  • tiktoken, for development only: the oracle. Your code in src/ never imports it.

On a fresh clone, run tools/install-hooks.sh once as well: it installs the pre-commit hook, which refuses a commit whose files are not formatted or fail the lint check, and says which file and why.

GPT-2's files

GPT-2's tokenizer is two files, committed in data/gpt2/ so that neither the tests nor CI need the network: vocab.json, which maps each of the 50,257 tokens to its id, and merges.txt, the 50,000 merges in the order they were learned. Check that they are present and unchanged:

$ uv run python tools/fetch-gpt2-tokenizer.py --check
ok: data/gpt2/vocab.json
ok: data/gpt2/merges.txt

--check compares each file with the checksum in the script and downloads nothing. The tests make the same check before they compare a single id, so a changed file fails loudly instead of giving wrong answers. Chapter 4 takes the files apart.

-k utf8_encode keeps the tests whose name contains utf8_encode; -x stops at the first failure. Read from the top: the test test_utf8_encode_the_docstring_examples, line 15 of tests/m02/test_utf8.py, called utf8_encode("A"); that went into src/llm101/tokenizer/utf8.py, line 33, where the stub raised. How to read this book

  • Cover and retype the examples. Each program is complete and was run before it was printed. Read it until you could explain every line, cover it, and type it into scratch/ from memory, under the name shown with it. Then compare it with the page and run it with uv run python scratch/NAME.py. A concept chapter has at most eight programs, so this fits in the read block; if the block runs out, type the rest with the page open. Typing, not pasting, either way.
  • Compare the output. Most programs show their exact output. Where a program prints a time, it is one run on the M5: your numbers will differ, the shape should not. Numbers about GPT-2, such as ids and counts of tokens, come from running the oracle on data/gpt2/. Chapters 1 to 3 show them as tables marked "From the oracle"; chapter 4 shows you how to build the oracle yourself.
  • Answer before you open. Say or write your answer to a "Try it" or "Check yourself" before you unfold it. A wrong guess you correct is worth more than a right answer you read.
  • The callouts have one job each. First principle: what the machine does. Analogy: a picture, and where it stops being true. Trap: a mistake, where you would make it. Python you need: a construct refreshed. In a real engine: where vLLM or a similar engine does the same.

How to get unstuck

In the build block, in this order (docs/methodology.md, "When you are stuck in the build"):

  1. Re-read the test that fails and the docstring of the function in the stub. Most of the time the answer is in one of them.
  2. Reproduce the smallest version of the problem in scratch/: three ids instead of a thousand, one word instead of a corpus, one merge instead of fifty thousand.
  3. Ask for one rung of the hint ladder, in chapter 8 or from Claude Code, and say which rung you are on.
  4. Only once the tests are green, ask for a review.

In a drill, the rule is stricter: at the bell, ask for one rung or log a timeout. A timeout has no reveal. The problem stays open and comes back at its +2 day redo.

A contract with yourself

  • One commit per milestone, named: M1: utf8_encode green. Seven such commits, and M7's prediction committed before its run, are the record a reviewer wants to see.
  • The log, every day: five lines in log.md on what surprised you, in block 5, on the day.
  • The prediction before the measurement, written in BENCH.md before anything runs. Only a written guess can surprise you.

Check yourself

Why does a token, rather than a character or a byte, matter for what a request costs?

Answer

Because everything after the tokenizer counts in tokens: prompts are billed per token, the KV cache stores per token, a reply streams one token at a time, and a batch is filled by a budget of tokens. The same text can take very different numbers of tokens in different scripts, so the tokenizer sets the cost before the model runs.

What is tiktoken's job in this module, and where may it not appear?

Answer

It is the oracle: the tests build GPT-2's tokenizer with it from the same two files in data/gpt2/ and compare your ids with its ids. It may not appear in your code; the tests read gpt2.py to check that it does not import tiktoken.

On day one, uv run pytest tests/m02 ends 136 failed, with not one test green. Module 1 had tests that passed on day one. What changed?

Answer

The tests that read your code (no .encode() in utf8.py, no tiktoken in gpt2.py, no apply_merges in fast.py) call your function first, so a stub that raises NotImplementedError fails them. They pass only once the function works and keeps the rule.

A test fails with E NotImplementedError: TODO(you). Is there a bug in your code?

Answer

No. The function has not been written yet: its body is still the stub's raise. The traceback above that line shows which test called which function, and on which line.

The tests may build tiktoken and compare your ids with its ids, but gpt2.py may not import it. Why is one allowed and not the other? What would a test prove if your code called tiktoken?

Answer

A test is worth something only if the two sides were worked out apart. tiktoken is a second, independent tokenizer built from the same two files, so when its ids and yours agree on thousands of texts, that is evidence your code is right. If your code called tiktoken, the test would compare tiktoken with itself: it would pass and prove nothing about what you wrote. And the module exists so that you type the tokenizer, not import one.

days_to_wait and longest_draw are review drills: their stubs do not say which pattern they need. Why leave it out?

Answer

Because recognising the pattern is the hard half of a problem you have not seen. In an interview nobody says "this is a heap problem", and a drill that names its pattern trains only the easy half, the typing. So you name it yourself, and it goes in the ledger's Pattern column. If you cannot name it, that is what the next redo is for.
