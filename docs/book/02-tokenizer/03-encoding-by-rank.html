The problem: new text, old merges

Chapter 2 trained merges on a tiny corpus. Here they are again, as a list in the order they were learned:

merges = [(101, 97), (116, 256), (256, 116), (115, 258), (257, 115)]
#          e a        t + ea      ea + t      s + eat     tea + s
#          -> 256     -> 257      -> 258      -> 259      -> 260

Now a user sends text the trainer never saw. There is no counting this time: the merges are fixed, and the only question is which to apply, in which order. That sounds like a detail, but different orders give different tokens. Take the made-up chunk "eatea", the bytes 101 97 116 101 97, and two ways to apply the same five merges:

StepBy position: the leftmost pair that has a mergeBy rank: the pair learned earliest
starte a t e ae a t e a
1(e, a) at the left: ea t e a(e, a) is rank 0, everywhere: ea t ea
2(ea, t) is now leftmost: eat e a(t, ea) is rank 1, (ea, t) only rank 2: ea tea
3(e, a) again: eat ea(ea, tea) has no merge: stop
endeat · ea, the ids 258 256ea · tea, the ids 256 257

Same merges, same text, different tokens. The right one is by rank: apply the merge learned earliest among those that fit. Training applied merge 0 to every word, then merge 1, then merge 2, so on any word of the training text, replaying by rank gives exactly the tokens training ended with, the tokens the model learned from. Any other order hands the model splits it never saw, and ids that do not match GPT-2's.

First principle

A tokenizer is a pure function: the same text must give the same ids every time, on every machine, because the model learned what each id means from the ids that training produced. Everything a byte-pair tokenizer knows is its list of merges, in order. Encoding adds no knowledge; it replays the list faithfully: the same merges, in the same order, never across the boundaries that training respected.

Analogy

Rank is precedence, as in arithmetic. In 2 + 3 × 4 you do the × first, wherever it stands, and get 14. A calculator that works strictly from the left gets 20. The rank of a merge is its precedence: the lowest rank goes first, wherever it stands in the word. Where it breaks: arithmetic has a handful of levels of precedence, and a BPE tokenizer has one level per merge, 50,000 for GPT-2. And when a rank wins, every occurrence of that pair in the chunk merges at once, from the left, where arithmetic does one operation at a time.

A table of ranks

Encoding asks again and again: "what is the rank of this pair?" Searching a list is slow; a dict answers at once. The tests build that dict from their merges, RANKS = {pair: rank for rank, pair in enumerate(MERGES)}, and for the tea merges it is:

{(101, 97): 0, (116, 256): 1, (256, 116): 2, (115, 258): 3, (257, 115): 4}

Most pairs are not in it: (116, 101), "t e", was never merged, and ranks[(116, 101)] raises KeyError. What you want is a rank that loses every comparison.

Python you need

math.inf is a float that is greater than every other number, and equal to itself. d.get(key, math.inf) gives the value if the key is there, and infinity if it is not, so a missing key always loses a contest for the smallest.

Here is the idea on a race, where not everyone finished. Each runner's finishing place is a rank, and a runner with no place should never be "the best":

import math

# Where each runner finished the race: 0 is the winner. Not everyone finished.
places = {"Ines": 0, "Tom": 1, "Kofi": 2, "Mai": 3}

print(places.get("Kofi", math.inf), places.get("Sam", math.inf))
print(math.inf > 1_000_000, math.inf == math.inf)

group = ["Mai", "Sam", "Tom"]
best = min(group, key=lambda name: places.get(name, math.inf))
print("best of", group, "->", best)

late_group = ["Sam", "Lea"]  # neither of them finished
best = min(late_group, key=lambda name: places.get(name, math.inf))
print("best of", late_group, "->", best, places.get(best, math.inf))

2 inf
True True
best of ['Mai', 'Sam', 'Tom'] -> Tom
best of ['Sam', 'Lea'] -> Sam inf

Of Mai, Sam and Tom, Tom finished best, and Sam counted as infinitely late. The last line is the one to remember: when nobody in the group has a place, every key is infinity, they all tie, and min returns the first. Sam is not a winner, and only the rank you get back says so.

Trap

min never says "none of these". Check the rank of what it returned: if it is infinity, nothing qualified, and for encoding that means there is nothing left to merge.

Encoding a word by hand

Now encode a word the trainer never saw, "tease", whose bytes are 116 101 97 115 101. The docstring of apply_merges gives the rule: among the neighbouring pairs, find the one with the lowest rank and replace every occurrence of it, from the left; stop when no neighbouring pair has a rank. On paper:

RoundTokensNeighbouring pairs and their ranksLowestBecomes
1116 101 97 115 101(116, 101) –, (101, 97) 0, (97, 115) –, (115, 101) –(101, 97), rank 0256
2116 256 115 101(116, 256) 1, (256, 115) –, (115, 101) –(116, 256), rank 1257
3257 115 101(257, 115) 4, (115, 101) –(257, 115), rank 4260
4260 101(260, 101) –nonestop

A dash is math.inf: no rank. "tease" becomes [260, 101], "teas" and "e". In round 3 the lowest rank present was 4: ranks 2 and 3 were skipped because their pairs never appeared. The new id is always 256 plus the winning rank.

Going through all the merges in order, 0, 1, 2, and applying each wherever it fits gives the same tokens (once a merge is done, no pair of a lower rank can appear, since a pair of rank r only holds ids made before it). But for GPT-2 that reads every chunk 50,000 times. Asking "which pair here has the lowest rank?" skips the merges that cannot apply, and chapter 5 answers that question faster still.

From ids back to text

Decoding is the easy direction: every token stands for some bytes, so join them in order with b"".join(pieces), the bytes cousin of "".join, and decode the result as UTF-8.

The catch: a token is a run of bytes, and nothing stops a run from ending in the middle of a character. Ask tiktoken for GPT-2's tokens of "你好" and you get four. Each character is three bytes, and the tokens cut them two and one:

Joined, the pieces are perfect UTF-8. One piece on its own, or a list of ids that stops halfway, is not. bytes.decode has an errors argument for exactly that case:

# GPT-2's four tokens for "你好", as bytes (seen through tiktoken). Each character is 3 bytes.
pieces = [b"\xe4\xbd", b"\xa0", b"\xe5\xa5", b"\xbd"]

whole = b"".join(pieces)
print(whole, len(whole), whole.decode("utf-8"))

first = pieces[0]  # a token that stops in the middle of a character
print(repr(first.decode("utf-8", errors="replace")))
print(repr(first.decode("utf-8", errors="ignore")))
try:
    first.decode("utf-8")  # errors="strict" is the default
except UnicodeDecodeError as error:
    print("strict:", error)

broken = whole[:4] + b"!"  # one whole character, then the start of the next, then "!"
print(repr(broken.decode("utf-8", errors="replace")))
print(repr(broken.decode("utf-8", errors="ignore")))

Three answers to bytes that are not a whole character:

  • errors="strict", the default, raises UnicodeDecodeError: right when broken bytes mean a bug, wrong for a tokenizer, which meets them in normal use.
  • errors="replace" puts the replacement character � (U+FFFD) where the broken piece was, so you can see that something was lost, and where.
  • errors="ignore" drops the broken bytes without a trace: "你!" looks like good text.

The docstring of Tokenizer.decode chooses "replace", so decode never raises on valid ids. (Chapter 1 shows how a decoder sees that a sequence is broken.) Mind the order of the steps: join all the bytes first, then decode once. Decoding token by token would turn "你好" into four �, although every byte was there.

Trap

errors="ignore" makes a round trip fail silently: the text comes back shorter and nothing complains. The round trips at the end of the chapter catch exactly this.

The tokenizer's two tables

So far a byte's id has been the byte itself: "t" is 116 because its byte is 116. That is a choice, not a law. The docstring of Tokenizer takes the ids of the 256 single-byte tokens as a parameter, byte_ids: byte_ids[b] is the id of the token for byte b. A tokenizer you train passes range(256), so byte b is id b. GPT-2 numbered its bytes another way: "!" is id 0 and the space is 220, for reasons chapter 4 explains. Taking the numbering as a parameter lets one class serve both.

The two directions read that numbering from opposite ends. encode starts from a byte and needs its id: that is byte_ids as it was given. decode starts from an id and needs its bytes: the same pairs read the other way, so one table is the other turned round. The Write it at the end of this chapter, invert_table, practises exactly that turning round, on a table of its own. test_tokenizer_encode_goes_through_byte_ids numbers the bytes backwards, so that a tokenizer which quietly assumes "id b is byte b" fails it.

A table can only be turned round if it is fair: "the numbers 0 to 255 in some order", as the docstring puts it, each id used by exactly one byte. Picture a row of eight cinema seats renumbered after a refit. The seat that was number 0 may now be number 3, and that is fine, as long as every number from 0 to 7 is painted on exactly one seat. Two seats with the same number, a number missing, or a seat numbered 8, and the usher's chart no longer works. The simplest check: sort the new numbers, and compare them with 0 to 7.

# A row of 8 seats, renumbered after a refit: renumbered[old] is the new number of the seat
# that used to be number old. A fair renumbering uses each of 0 to 7 exactly once.
renumberings = {
    "fair": [3, 0, 7, 1, 6, 2, 5, 4],
    "too few": [3, 0, 7, 1, 6, 2, 5],
    "a repeat": [3, 0, 7, 1, 6, 2, 5, 5],
    "out of range": [3, 0, 8, 1, 6, 2, 5, 4],
    "nine seats": [3, 0, 7, 1, 6, 2, 5, 4, 7],
}
for name, renumbered in renumberings.items():
    fair = sorted(renumbered) == list(range(8))
    same_set = set(renumbered) == set(range(8))
    print(f"{name:12}  sorted {sorted(renumbered)!s:27}  fair {fair!s:5}  same set {same_set}")

Sorted, a fair renumbering is exactly 0, 1, 2 and so on, so one comparison catches every way of being unfair. Comparing sets is not enough on its own: the nine numbers of the last row hold 7 twice, and their set is still 0 to 7, because a set forgets how often a number came. (sorted takes any iterable, a range included.) Mathematicians call a fair renumbering a permutation: the same numbers, shuffled.

A special token, such as GPT-2's <|endoftext|>, is neither a byte nor a merge: it is known only to decode, and encode never produces one (chapter 4 says why). An id that belongs to no byte, no merge and no special token has no bytes to give, so decode and token_bytes raise ValueError.

Why split before merging

Encoding by rank works on one chunk of text at a time, and so far a chunk has been one word. Why cut the text up at all? Because BPE only counts, and real text is full of frequent pairs you do not want as tokens. The GPT-2 paper (2019) gives the example: without a split, BPE learns "dog.", "dog!" and "dog?" as separate tokens, spending vocabulary on one word with different punctuation. With the split, punctuation never shares a chunk with the letters before it, merges never cross chunks, and one token serves every case. From the oracle:

TextChunksGPT-2 ids
dog. dog! dog?dog | . | ·dog | ! | ·dog | ?9703, 13, 3290, 0, 3290, 30

A space is shown as ·. GPT-2's split keeps the space in front of a word with the word, so " dog" is token 3290 every time. (The first "dog" has no space in front, so it is another token, 9703.) The split also stops a token from holding the end of one word and the start of the next. The test test_tokenizer_merges_never_cross_chunks gives a tokenizer the single merge (100, 32), "d" then space, and checks that "d d" stays three tokens: the chunks are "d" and " d", and neither holds a "d" followed by a space.

So encoding is two layers: split the text into chunks, then encode each chunk on its own, by rank, and put the results one after another, as the docstring of Tokenizer.encode says. Training used the same split, so encoding respects the same boundaries. That leaves one question: what exactly is a chunk? It needs a rule that says where a word, a number or a run of punctuation begins and ends, in any script, and where the spaces go. GPT-2 writes that rule as one regular expression, and the rest of this chapter builds it, from the first character class to the whole pattern.

Regular expressions from first principles

A regular expression is a small description of a shape of text, such as "one or more letters", which Python's re module uses to find the stretches of text with that shape.

Python you need

Raw strings. In "\n" Python turns the backslash and the n into one newline character before re ever sees them. In a raw string, r"\s", the backslash stays, and re gets to read \s itself. Write every pattern as a raw string.

  • A character class, in square brackets, matches one character from a set: [a-z] is any lower-case letter from a to z, [0-9] any digit. A ^ just inside the bracket turns it round: [^a-z ] is any character except those. \s is any white space (space, tab, newline) and \S anything else.
  • + after a piece means "one or more of it, as many as possible", and ? means "one or none".
  • re.findall(pattern, text) slides along the text from the left and returns every match, in order, each starting where the last one ended. re.fullmatch(pattern, text) asks whether the whole text has the shape, and returns a match object or None.
import re

text = "Tea at 4, cake at 5. Colour or color?"

print(re.findall(r"[a-z]+", text))  # runs of lower-case letters
print(re.findall(r"[A-Za-z]+", text))  # either case
print(re.findall(r"[0-9]", text))  # one digit at a time
print(re.findall(r"[Cc]olou?r", text))  # u? : one u, or none
print(re.findall(r"\S+", text))  # runs of anything that is not white space
print(re.findall(r"[^a-z ]+", text))  # runs of anything but lower case and the space

print(re.fullmatch(r"[a-z]+", "cake"))  # the whole string must match
print(re.fullmatch(r"[a-z]+", "cake!"))

In the first line "Tea" gave 'ea' and "Colour" gave 'olour': a capital is not in [a-z], and a pattern does exactly what it says. + is greedy, which is why "cake" is one match and not four. The last two lines are checking, not finding: "cake!" does not fit [a-z]+ from end to end. Three more pieces, and you can read GPT-2's pattern:

  • Alternation, A|B: try A here; only if A fails, try B. The first alternative that matches wins, even if a later one would have matched more.
  • A group, (?:...), makes several pieces into one, so that + or ? applies to all of them: (?:ha)+ is "ha" once or more. Plain brackets (...) group too, but they also capture, which changes what findall returns.
  • A negative lookahead, (?!X), matches no characters at all. It is a check: "at this point, what comes next is not X".
import re

print(re.findall(r"cat|category", "category"))  # the first alternative that matches wins
print(re.findall(r"category|cat", "category"))

print(re.findall(r"(?:ha)+", "haha, hahaha!"))  # a group that repeats, captured as a whole
print(re.findall(r"(ha)+", "haha, hahaha!"))  # a capturing group: findall returns the group

print(re.findall(r"[a-z]+(?!\?)", "tea? cake"))  # not followed by "?"... after backtracking
print(re.findall(r"[a-z]+(?![a-z?])", "tea? cake"))  # nor by another letter

['cat']
['category']

Line 1: at position 0, cat matches, so category is never tried. Swap them and the longer word wins: the order of the alternatives is part of the meaning. Lines 3 and 4 differ only in ?:. With a capturing group, findall returns what the group matched, and a repeated group remembers only its last turn.

Lines 5 and 6 show the machine at work. In "tea?", [a-z]+ first takes all of "tea", and the lookahead sees "?" and fails. The engine does not give up: it backtracks, gives back one letter, and tries "te". The next character is now "a", so the lookahead passes, and "te" is a match. Line 6 also refuses a letter next, and "tea" is skipped entirely. That backtracking is how \s+(?!\S) in GPT-2's pattern works, below.

Trap

Once a pattern has a capturing group, findall returns the groups, not the whole matches. If findall gives you fragments, look for plain brackets and make them (?:...).

Letters in every script: the regex package

GPT-2 needs "any letter, in any script", and Unicode has a name for it: \p{L}, the property "letter". \p{N} is the property "number": digits, and numerals such as ½ and Ⅻ. Python's own re knows neither. [a-z] stops at the end of the English alphabet, so in "Grüße" it finds only "r" and "e". \w, the nearest thing re has, is Unicode-aware, but it lumps letters, digits and the underscore together, which GPT-2's pattern must tell apart. And re refuses \p{L} outright: on Python 3.13, re.compile(r"\p{L}") raises re.PatternError: bad escape \p at position 0 (the appendix lists it with this module's other errors). The regex package has the same functions as re and knows Unicode properties. It is a dependency of this module, and your pretokenize needs it:

import regex

text = "Grüße, 你好! नमस्ते 42 ½ Ⅻ ٣ snake_case"

print(regex.findall(r"\p{L}+", text))  # letters, in any script
print(regex.findall(r"\p{N}+", text))  # digits and other numerals, in any script
print(regex.findall(r"[^\s\p{L}\p{N}]+", text))  # neither space, nor letter, nor numeral

['Grüße', '你好', 'नमस', 'त', 'snake', 'case']
['42', '½', 'Ⅻ', '٣']
[',', '!', '्', 'े', '_']

½, the Roman numeral Ⅻ and the Arabic-Indic digit ٣ (three) are numbers. A property can go inside a character class: [^\s\p{L}\p{N}] is "neither white space, nor letter, nor number". The Hindi word नमस्ते ("namaste") came out in pieces, and two of its characters turned up with the punctuation: ् (the virama) and े (the vowel sign e) are marks, which combine with the letter before them, not letters. So GPT-2's pattern cuts Hindi words at their marks, and no merge can join them back: one more way in which text outside English pays for GPT-2's choices. Chapter 6 counts what other scripts cost in tokens.

GPT-2's split pattern, piece by piece

The pattern is given in src/llm101/tokenizer/bpe.py as GPT2_PATTERN, copied from OpenAI's encoder of 2019. Print it, then try each alternative on its own on a sample made for it:

import regex

from llm101.tokenizer.bpe import GPT2_PATTERN

print(GPT2_PATTERN)
print(len(GPT2_PATTERN.split("|")), "alternatives")

samples = [
    (r"'s|'t|'re|'ve|'m|'ll|'d", "it's we'll they'd IT'S"),
    (r" ?\p{L}+", "Hello wörld  你好"),
    (r" ?\p{N}+", "in 2026, ½ of 12"),

    (r"\s+", "a   b"),
]
for alternative, sample in samples:  # one alternative at a time, never the whole pattern
    print(f"{alternative:24} on {sample!r:26} -> {regex.findall(alternative, sample)}")

(GPT2_PATTERN.split("|") is the string method: it cuts the text of the pattern at each bar, to count the pieces.) In the order the engine tries them:

  1. The contractions, 's|'t|'re|'ve|'m|'ll|'d: an apostrophe and one of seven English endings. They come first, so they win over the punctuation rule. They are lower case, and nothing in the pattern ignores case, so the "'S" of "IT'S" is not one.
  2. A word, ?\p{L}+: an optional space, then letters in any script. This is why " wörld" is one chunk. In " 你好", ? takes only one space, the one next to the word.
  3. A number, ?\p{N}+: the same, for numerals.
  4. Everything else, ?[^\s\p{L}\p{N}]+: an optional space, then punctuation, symbols, emoji, and the marks of the last section.
  5. Trailing white space, \s+(?!\S): white space not followed by a non-space. In "a b", three spaces are followed by "b", so the engine backtracks to two, which are followed by a space: " " matches, and the third space is left for " b". At the end of "c " nothing follows, and both spaces match.
  6. Any other white space, \s+: whatever rule 5 left, such as one space or newline right before a word.

Round trips and hypothesis

The first half of this module's "Done when" is round trips are exact on arbitrary Unicode. A round trip goes somewhere and comes back: encode a text, decode the ids, and you must have the text you started with, for every text. You cannot write every text by hand. Hypothesis (met in Module 1) generates them, aimed at the edges, and when one fails it shrinks it to the smallest text that still fails. Here it is on two round trips that are not a tokenizer's: JSON, and ASCII with errors="ignore", which loses data on purpose:

import json

from hypothesis import given
from hypothesis import strategies as st


@given(st.text())
def test_json_round_trip(text):
    assert json.loads(json.dumps(text)) == text


@given(st.text())
def test_ascii_round_trip(text):
    squeezed = text.encode("ascii", errors="ignore")  # drops what ASCII cannot hold
    assert squeezed.decode("ascii") == text


test_json_round_trip()
print("json: every text came back")
test_ascii_round_trip()
print("ascii: every text came back")

    text='\x80',

A function decorated with @given can be called with no arguments: hypothesis calls it with generated values, a hundred by default, which is how this script runs without pytest. JSON brought every text back. The ASCII trip failed, and hypothesis shrank the failure to '\x80', the first character ASCII cannot hold. A failing case of one character tells you what is wrong.

st.text() never makes the lone surrogates of chapter 1, such as "\ud800", which have no UTF-8 bytes, while st.characters() on its own can, which is why test_round_trips_with_bytes_in_another_order asks for st.characters(codec="utf-8").

Trap

A round trip that passes on "Hello world" proves little. The cases that break tokenizers are a character split across two tokens, white space at the end, and characters that are not letters. When hypothesis finds one, add the shrunk case as a plain test of its own, so it stays fixed.

In a real engine

GPT-2's original encoder (src/encoder.py in the openai/gpt-2 repository) splits the text with this same pattern, then applies the merges to each chunk by rank. It also keeps a dict from each chunk it has already encoded to its tokens, because real text repeats its chunks, and a lookup is far cheaper than merging again: stretch goal 1 of the module. In serving, vLLM tokenizes each prompt with the model's Hugging Face tokenizer before it schedules the request, so a request's length in tokens, which decides its cost and its place in a batch, comes from an encoder like yours. A server that streams its answer token by token also meets broken characters, since one token's bytes can end halfway through a character.

Check yourself

With the merges {(98, 99): 0, (97, 98): 1}, what does the chunk "abc" (97 98 99) become by rank, and what would "the leftmost pair that has a merge" give instead?

Answer

By rank: (98, 99) has rank 0, so "bc" merges first: [97, 256], and then (97, 256) has no rank. By position: (97, 98) is leftmost, giving [257, 99]. Different tokens from the same merges; the rank is the right one, because it replays the order in which training learned them.

In finishing_places.py, why places.get(name, math.inf) rather than places[name]? And in a group where nobody finished, what does min return, and how can you tell it is not a real winner?

Answer

places["Sam"] raises KeyError, since Sam has no place; infinity instead loses every comparison with a real place. When nobody finished, every key is infinity, they all tie, and min returns the first name of the group. Only its key says the truth: a place of infinity means nobody qualified.

Encode "eats" (101 97 116 115) with the tea merges.

Answer

Round 1: (101, 97) rank 0 gives 256 116 115. Round 2: (256, 116) rank 2 gives 258 115. Round 3: (258, 115) has no rank, stop. [258, 115], "eat" and "s".

A list of ids ends with a token whose bytes are e4 bd, the first two bytes of 你. What does decoding with errors="replace" put there, and why is "ignore" worse?

Answer

One replacement character, �. "ignore" would drop the two bytes without a trace, so the text would look complete when a character is missing; "replace" shows that something was lost, and where.

What does re.findall(r"in|ink", "inky inn") return, and why?

Answer

['in', 'in']. At each position the first alternative that matches wins, so "in" is taken from "inky" and "ink" is never tried. The "ky" is left over, and "inn" gives "in" and a leftover "n".

How does GPT-2's pattern split "IT'S", and how does it split "it's"? Which rule makes the difference?

Answer

"IT'S": "IT", "'", "S". "it's": "it", "'s". The contractions alternative is written in lower case, so "'S" does not match it, and the apostrophe falls through to the punctuation rule ?[^\s\p{L}\p{N}]+.

Why does "a b" (three spaces) split into "a", " " and " b", and not "a", " " and "b"?

Answer

The rule \s+(?!\S) takes white space that is not followed by a non-space. Three spaces are followed by "b", so it backtracks to two, which are followed by a space. The third space is then taken by ?\p{L}+ together with "b", because a word keeps one space in front of it.

Why does the Done-when test never send your tokenizer the string "\ud800", and why would it fail if it did?

Answer

st.text() draws its characters from st.characters(codec="utf-8"), which leaves out lone surrogates. Encoding needs the UTF-8 bytes of the text, and a lone surrogate has none: "\ud800".encode("utf-8") raises UnicodeEncodeError.
