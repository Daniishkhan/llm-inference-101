The problem: 256 tokens are too few

Chapter 1 turned every text into bytes, numbers from 0 to 255. You could stop there: one token per byte, a vocabulary of 256, and no text is ever out of reach. The price is length. Here is what GPT-2's real tokenizer does to three sentences.

From the oracle: tiktoken's GPT-2 encoding, built from the two files in data/gpt2/ (chapter 4 builds it). The bytes are UTF-8 bytes, as chapter 1 counted them.

SentenceBytesGPT-2 tokensBytes a token
The kettle boiled twice before anyone noticed that the tea had gone cold.73145.2
Der Wasserkocher kochte zweimal, bevor jemand merkte, dass der Tee kalt war.76292.6
Grüße aus der Küche: der Tee ist kalt, die Kekse sind weg.61272.3

The English sentence is 73 bytes and 14 tokens: one token carries about five bytes. With one token per byte it would be about five times as long. Why does length matter? A model does some work at every position of the text: it looks up the id, and runs the numbers through the same layers of sums. That part grows in proportion to the length, so five times the tokens costs about five times as much. One part grows faster. Module 3 builds attention, in which every position of the text looks at every earlier position and gives each a score. Picture a party where every guest shakes hands with every other: ten guests make 45 handshakes, twenty make 190. Double the guests and the handshakes roughly quadruple, because the count grows with the square of the guests. Attention's scores grow the same way with the number of tokens, so on the English sentence byte tokens would cost about 5.2² ≈ 27 times the attention-score work, and about 5 times the rest. At lengths like these the rest is most of what GPT-2 computes, so the whole bill grows by somewhat more than five; the square takes over only on long texts. A model also has a fixed window (GPT-2's is 1,024 positions), which with byte tokens would hold about one kilobyte of English instead of four or five.

The other extreme, one token per word, needs every word of every language, every name and every typo, and still fails on the first new word. Byte-pair encoding (BPE) sits in between: it keeps the 256 bytes, so nothing is out of reach, and adds tokens for common runs of bytes, learned by counting a body of text. GPT-2 added 50,000. It learned them from mostly English text, so German gets about two and a half bytes a token; chapter 6 counts what that costs.

First principle

A model does two things with token ids. It looks each one up in a table that has one row of numbers per id (GPT-2's smallest model has 50,257 rows of 768 numbers), and it then computes at every position of the text. So the size of the vocabulary decides how big the table is, and the number of tokens decides how much computing there is. A tokenizer trades one against the other. 256 tokens make a tiny table and long texts; 50,257 make a big table and English texts four or five times shorter. Training a tokenizer means choosing which extra tokens earn a row.

Analogy

A court reporter who writes every letter cannot keep up with speech, so shorthand gives the commonest combinations a single stroke. BPE builds its shorthand by counting: the pair of symbols that occurs most often gets a new symbol, the text is rewritten with it, and the count starts again, so later symbols are built from earlier ones. Where it breaks: a reporter picks strokes for words that mean something. BPE only counts. Its tokens are often pieces of words (GPT-2 writes " tokenizer" as " token" and "izer"), and it never knows what a token means.

Counting with a dict

Training is counting, done again and again, so start with the plainest count there is: how many times each word appears in a sentence.

Python you need

d.get(key, default) returns d[key] if the key is there and default if it is not, where d[key] would raise KeyError. collections.Counter is a dict made for counting: give it any iterable and it counts each item, a missing key reads as 0, and most_common(n) returns the n largest counts as (item, count) pairs.

from collections import Counter

text = "the cat sat on the mat and the dog sat on the cat"
words = text.split()

counts = {}
for word in words:
    counts[word] = counts.get(word, 0) + 1  # 0 the first time a word is seen
print(counts)

counter = Counter(words)  # the same loop, written in C
print(counter)
print(counter == counts, counter["fish"], counts.get("fish", 0))
print(counter.most_common(2))
print(len(words), "words,", len(counter), "distinct")

{'the': 4, 'cat': 2, 'sat': 2, 'on': 2, 'mat': 1, 'and': 1, 'dog': 1}

13 words, 7 distinct

The loop and the Counter agree, and a Counter compares equal to a plain dict with the same counts. Both keep their keys in the order each word was first seen, 'the' first and 'dog' last; the section on ties needs that. The last line previews count each word once: thirteen words, seven different ones. A key can also be a tuple: {(1, 2): 2} counts the pair (1, 2), the shape your count_pairs returns in src/llm101/tokenizer/train.py.

Trap

Counter(text) on a string counts its characters, spaces included, because iterating over a string gives one character at a time. To count words, give it the list of words: Counter(text.split()). The same holds for bytes: iterating over b"tea" gives the three ints 116, 101 and 97.

Neighbours in a list

BPE does not count single items; it counts pairs of items that sit next to each other. The Python way to walk a list two neighbours at a time is zip(xs, xs[1:]). Here it is on a different question: a week of noon temperatures, and how much each day differs from the day before.

temperatures = [11, 13, 12, 12, 16, 15, 9]  # noon, Monday to Sunday

days = list(zip(temperatures, temperatures[1:], strict=False))  # each day with the next
print(days)
print(len(temperatures), "readings,", len(days), "neighbouring days")

changes = [after - before for before, after in days]
print(changes)
print("biggest rise:", max(changes), "biggest fall:", min(changes))

[(11, 13), (13, 12), (12, 12), (12, 16), (16, 15), (15, 9)]
7 readings, 6 neighbouring days
[2, -1, 0, 4, -1, -6]
biggest rise: 4 biggest fall: -6

Picture the week written on two strips of paper, the second slid one day to the left: temperatures[1:] is that strip, a new list that starts on Tuesday. zip reads the strips side by side, one pair per column, and stops when the shorter runs out: seven readings give six pairs, one reading or none gives none, and no day needs treating specially.

Two things in the output matter for M2. Every reading but the first and last belongs to two pairs: Tuesday's 13 ends one and starts the next. And Wednesday and Thursday make (12, 12): equal neighbours are a pair like any other.

Trap

ruff's rule B905 wants every zip to say strict=; zip(xs, xs[1:]) needs strict=False, because its two lengths differ by one and strict=True would raise ValueError.

Trap

xs[1:] needs something you can slice: a list, a tuple or bytes, but not a generator, which raises TypeError. count_pairs takes a Sequence, so slicing is allowed, and its test passes a tuple. For an iterable that cannot be sliced, itertools.pairwise gives the same pairs.

Ties, and choosing with a key

Each round of training picks the most frequent pair. Often two pairs are equally frequent, and then something has to decide. Here is what Python decides when you do not:

Python you need

max(items, key=f) returns the item whose f(item) is largest, and among equals the first it met; min likewise for the smallest. Tuples compare item by item, from the left: the first items decide, and only if they are equal do the second items get a say. So (91, "Ade") < (91, "Ben"), and (2, "z") < (3, "a").

from collections import Counter

# The same six words, in two orders. "tea" and "cake" are tied at two each.
first = Counter("tea cake jam tea cake bun".split())
second = Counter("cake tea jam cake tea bun".split())
print(first.most_common(1), second.most_common(1))

scores = {"Priya": 82, "Ben": 91, "Ade": 91, "Chen": 77}
print(max(scores, key=scores.get))  # the first 91 in the dict's order
print(max(scores.items(), key=lambda item: (item[1], item[0])))  # 91, then the larger name
print(min(scores.items(), key=lambda item: (-item[1], item[0])))  # 91, then the smaller name

print((91, "Ade") < (91, "Ben"), (116, 256) < (256, 116), (97, 98) < (97, 99))

[('tea', 2)] [('cake', 2)]
Ben
('Ben', 91)
('Ade', 91)
True True True

The first line is the problem: the same words, the same number of times, and most_common(1) names a different winner for each, because among equal counts it keeps the order of first sight. max(scores, key=scores.get) has the same habit, and returns Ben only because Ben comes before Ade in the dict.

A tuple key fixes it. (score, name) makes max compare names only when scores are equal, but max then wants the larger name, "Ben". For "the highest score, and among those the smallest name", flip the score and take the minimum: (-score, name) is smallest for the highest score, then the smallest name. Neither tuple-key line depends on the dict's order.

Trap

"Highest first, ties to the smallest" is two directions at once, and a single max with the key (count, item) breaks ties towards the largest item. Either negate the number and use min, as above, or write the tie rule out and test a tie on purpose.

Training needs exactly this choice. The docstring of train_bpe says: among equally frequent pairs, choose the smallest pair, compared as tuples. Why not "whichever was counted first"? Because a dict's order depends on the order the chunks arrived in and on how you built the counts, so two correct trainers could learn different merges from the same text, and no test could name the right answer. The smaller pair depends only on the counts. (Some trainers do use "first seen"; decision 3 in the module README records the choice.)

The tuples hold ids, not letters: (116, 256) < (256, 116) because 116 < 256. In the next section those pairs spell "t" + "ea" and "ea" + "t". As strings "eat" would come first; as ids, (116, 256) does, and the ids are what count.

Try it

Type ties.py into scratch/, then swap Ben and Ade in the dict, so that Ade comes first. Before you run it, predict lines 2, 3 and 4.

Show the answer

Line 2 becomes Ade: the first 91 in the dict's order is now Ade's. Lines 3 and 4 do not change, ('Ben', 91) and ('Ade', 91), because a tuple key decides every tie from the values alone. That is the property the training rule needs.

Byte-pair encoding by hand

Now the whole idea, on a corpus small enough for paper. The rule, from the docstring of train_bpe: every chunk starts as its bytes, byte b being the token with id b. Each round, count every pair of neighbours in every chunk, choose the most frequent (the smaller pair on a tie), give it the next free id from 256, and replace it with that id everywhere. Merges never join one chunk to the next.

The corpus is eight words, tea eat seat tea teas eat seat tea, each word one chunk, as in the test that trains on a paragraph split on spaces. The bytes: a is 97, e 101, s 115 and t 116. Counting the words first (the reason comes two sections down):

Each round counts the words as they are now, and the counts change after every merge. Merges build on merges: 257 is made of 116 and 256, and 260 of 257 and 115. And training stopped after five merges because nothing was left to merge. Asked for a vocabulary of 300, this corpus gives five merges, not 44.

Overlapping pairs

Pairs can overlap. "aaa" holds two pairs "a a", at positions 0 and 1 and at 1 and 2, sharing the middle a. Counting finds both; merging cannot use both, since once the first two a's are one token the middle a is gone. The contract's rule is the one you know from strings: scan from the left, the left occurrence wins, and the scan goes on after it. str.replace follows exactly that rule:

for text in ["aaa", "aaaa", "aaaaa", "banana"]:
    target = "ana" if text == "banana" else "aa"
    print(f"{text!r:9} {target!r}: replace -> {text.replace(target, 'X')!r:8} "
          f"count -> {text.count(target)}")

'aaa'     'aa': replace -> 'Xa'     count -> 1
'aaaa'    'aa': replace -> 'XX'     count -> 2
'aaaaa'   'aa': replace -> 'XXa'    count -> 2
'banana'  'ana': replace -> 'bXna'   count -> 1

"aaa" becomes "Xa", never "aX". "banana" holds "ana" twice, at positions 1 and 3, but they share an a, so replace takes the left one and str.count counts only the occurrences that do not overlap. Your merge_pair follows the same rule on lists of ids, and its docstring gives the examples: [7, 7, 7] becomes [9, 7], and [7, 7, 7, 7] becomes [9, 9].

Counting is different. count_pairs counts every position, overlapping or not, so [7, 7, 7] has the pair (7, 7) twice. For a run of equal ids the two numbers drift apart:

A run ofPairs counted (every position)Merges made (left to right)After the merge
2 a's11X
3 a's21X a
4 a's32X X
5 a's42X X a

That is not a contradiction: the count is how training chooses a pair, the merge how it applies one, and the contract fixes both, so every correct trainer agrees. After the scan no "a a" is left at all; a run of odd length leaves one lone a at its end.

Trap

Scanning from the right gives a different answer: "aaa" would become "aX", and [7, 7, 7] would become [7, 9]. Both are fair rules, but they make different tokens, and only one matches the tests (and tiktoken, in milestone M5). Test the overlapping cases on purpose; they are where a wrong scan shows.

Count each word once

Real text repeats itself. The tea corpus had eight words but four different ones, and the tables counted "tea" once with a weight of 3. That does not change the answer: every copy of "tea" has the same pairs, and every merge changes every copy the same way. The docstring of train_bpe asks for it, and the saving decides whether training takes seconds or minutes.

Python you need

What can be a dict key. A dict files each key under a number worked out from its contents, its hash. A list can change after it is stored, which would leave it filed under the wrong number, so a list cannot be a key: Python raises TypeError: unhashable type: 'list'. A tuple cannot change, so it can, and tuple(ids) turns a list into one. A string cannot change either, so another way is a dict keyed by the word itself, with its list of ids as the value.

times_seen = {(116, 101, 97): 3}  # a tuple of ids can be a key
print(times_seen[(116, 101, 97)])
try:
    times_seen[[116, 101, 97]] = 3  # a list cannot
except TypeError as error:
    print("TypeError:", error)

ids_of = {"tea": [116, 101, 97]}  # a str key, and a list as the value
print(ids_of["tea"])

A worked example: the letter e in a short text

Here is the same trick on a different count: how many times the letter e appears in a short text of your own, five lines about a kitchen with no punctuation, so that split() gives clean words. First walk every word; then walk each distinct word once and multiply by its count.

from collections import Counter

text = """
the kettle is on the stove and the tea is in the pot
the cat is on the mat and the mat is by the stove
when the tea is ready the cat wakes and the dog wakes
the dog wants the tea and the cat wants the mat
and the kettle wants the stove and the stove is hot
"""

words = text.split()  # split on spaces and newlines
counts = Counter(words)
print(len(words), "words,", len(counts), "distinct")
top, n = counts.most_common(1)[0]
print(f"the most common, {top!r}, is {n} of them")

# How many times does the letter e appear? Walk every word, or each distinct word once.
every_word = sum(word.count("e") for word in words)
weighed = sum(word.count("e") * times for word, times in counts.items())
print("e:", every_word, "walking every word,", weighed, "weighing each distinct word")
letters_all = sum(len(word) for word in words)
letters_distinct = sum(len(word) for word in counts)
print("letters read:", letters_all, "the first way,", letters_distinct, "the second")

60 words, 18 distinct
the most common, 'the', is 18 of them
e: 33 walking every word, 33 weighing each distinct word
letters read: 197 the first way, 62 the second

Sixty words, but only eighteen different ones, and "the" alone is eighteen of the sixty, three words in ten. Both ways count 33 e's, and the weighed way reads 62 letters instead of 197, about a third. A real text repeats far more, because its common words come back on every line while its vocabulary grows slowly: the longer the text, the bigger the saving.

Then the saving is multiplied by the rounds, since training counts again for every merge. The test test_train_bpe_three_hundred_merges_on_a_million_characters_in_ten_seconds trains 300 merges on argparse's source ten times over: about 92,000 words, but only about 2,600 distinct. Its comment puts the difference at about one second when each distinct word is counted once, against about thirty-five when every word is walked, and the test stops your function after ten seconds ("still training after 10 s"). That difference is the difference between passing and not.

In the real tokenizer, chunks come from GPT-2's split pattern, which keeps the space in front of a word, so " world" is one chunk: chapter 3's business. For training, a chunk is simply the unit that merges never cross.

What training gives you

When the rounds stop, training returns one thing: the list of the pairs it merged, in the order it merged them. For the tea corpus:

merges = [(101, 97), (116, 256), (256, 116), (115, 258), (257, 115)]

Position r in that list is the merge's rank, and the rule of the whole module is that merge r makes the token whose id is 256 + r:

Rank rmerges[r]Makes id 256 + rIts bytes
0(101, 97)256e a
1(116, 256)257t e a
2(256, 116)258e a t
3(115, 258)259s e a t
4(257, 115)260t e a s

Neither the ids nor the bytes are stored: the ids follow from the positions, and a token's bytes are its left part's followed by its right part's, so the last column follows from the list, top to bottom. The vocabulary has 256 + 5 = 261 tokens. The order matters: merge 1 uses token 256, which merge 0 made, so merge r may only use ids below 256 + r (the constructor of Tokenizer checks it), and chapter 3 replays the merges in exactly this order to encode new text.

In a real engine

Your train_bpe counts every pair again after each merge, which is the clearest way and fast enough for a few hundred merges. The BPE trainer of Hugging Face's tokenizers library does not recount: after each merge it updates only the pair counts that the merge changed, which saves most of the counting on a large corpus and tens of thousands of merges. That is stretch goal 2 in the module README. A serving engine never trains at all. Training happens once, before the model is trained, and the merges travel with the model as files; vLLM tokenizes each prompt with the model's Hugging Face tokenizer before it schedules the request.

Check yourself

Why not give a model just the 256 byte tokens? Use the English sentence from the oracle's table in the problem in your answer.

Answer

Texts get long. The sentence is 73 bytes but 14 GPT-2 tokens, about five bytes a token, so byte tokens would make it about five times as long. The work done at every position (the lookups and the layers, most of GPT-2's computing at this length) grows with the length: about 5 times. Attention's pairwise scores grow with the square of the length: about (73 / 14)² ≈ 27 times the attention-score work. And the model's fixed window would hold a fifth as much text.

What does Counter("tea tea cake") count, and what should you write to count the words?

Answer

Its characters, spaces included: t 2, e 3, a 3, space 2, c 1, k 1. A string iterates one character at a time. To count words: Counter("tea tea cake".split()), which gives tea 2, cake 1.

How many pairs does zip(xs, xs[1:], strict=False) give when xs has 7 items? 1 item? None?

Answer

6, 0 and 0. It pairs each item with the next and stops when the shorter strip, xs[1:], runs out.

A round's counts are {(101, 114): 9, (97, 98): 7, (32, 116): 9}. Which pair wins under the module's rule? Why is max(counts, key=counts.get) not good enough?

Answer

(32, 116): it is tied for the most frequent with (101, 114), and it is the smaller tuple, since 32 < 101. max with that key returns the first of the tied pairs in the dict's order, here (101, 114), and the dict's order depends on how the counts were built.

In the ids [5, 5, 5, 5, 5], how many times does the pair (5, 5) occur by the counting rule, and what does replacing it with 9 by the merging rule give?

Answer

Four times: every position counts, overlaps included. Merging from the left gives [9, 9, 5]: two merges, and the last 5 has no partner left.

A text has 92,000 words, of which 2,600 are distinct. Roughly how many word visits do 300 rounds of training make if each round walks every word, and how many if it walks each distinct word once?

Answer

300 × 92,000 = 27.6 million, against 300 × 2,600 = 780,000: about 35 times fewer. Every copy of a word has the same pairs, so its pairs are counted once and multiplied by its frequency.

Training returned [(104, 105), (256, 33)]. Byte 104 is "h", 105 is "i" and 33 is "!". Which ids exist now, and what does each new one stand for?

Answer

Ids 0 to 257: the 256 bytes, then 256 for merge 0, "hi", and 257 for merge 1, "hi" followed by "!", so "hi!". A vocabulary of 258.

Why can merge number 3 never contain the id 260?

Answer

Merge 3 makes 259, and 260 is only made by merge 4, later. When merge 3 is learned, the ids that exist are 0 to 258, so a merge r may only use ids below 256 + r.
