Five rules hold for every milestone:

  • One rule for every id. Ids 0 to 255 are the single bytes, in some order, and merge number r makes the token whose id is 256 + r. For a tokenizer you train, byte b has id b. For GPT-2 the bytes have other ids (! is 0), its 50,000 merges make ids 256 to 50,255, and 50,256 is <|endoftext|>, which no merge makes.
  • Three files are read by the tests. utf8.py may not call .encode() or .decode(), import codecs, or hand a string and an encoding to bytes() or bytearray(); gpt2.py may not import tiktoken; fast.py may not call apply_merges. tiktoken is the tests' oracle, the trusted answer your ids are compared with; it is not your tool.
  • The tests are fixed. If you believe one is wrong, say so to Claude: it fixes the test, never your code, and only when the test contradicts the spec.
  • One milestone at a time, in this order. M4 uses M2's merge_pair idea, M5 builds a Tokenizer from M4, and M6 is checked against M4's apply_merges.
  • One commit per milestone, with the message the milestone gives. M7 has two: its prediction, committed before the measurement, and the Experiment.

Milestone 1: utf8_encode

Goal. utf8_encode(text) returns the UTF-8 bytes of a string, worked out from each character's code point with shifts and masks, exactly as text.encode("utf-8") would. A surrogate code point (0xD800 to 0xDFFF) raises ValueError.

Re-read. Chapter 1: Characters and code points, Bits, shifts and masks, The UTF-8 table, Reading UTF-8 by hand and Surrogates, and text that is not text. The docstring of utf8_encode in utf8.py, which has the table.

Turns green. uv run pytest tests/m02/test_utf8.py, twenty tests.

The hint ladder.

Rung 1: where to look

Read test_utf8_encode_each_length_at_its_edges: ten code points, each at the edge of a row of the table. Then test_utf8_encode_rejects_a_surrogate and test_utf8_encode_is_done_by_hand, which says exactly what the file may not contain. Work "€" (U+20AC) on paper: the row of the table it falls in, its code point written in exactly as many bits as that row has x slots (16), with zeros in front, and those bits shared out over the slots from left to right. You should get e2 82 ac.

Rung 2: the idea in words

Take the characters one at a time and get each one's code point. Refuse a surrogate first. The size of the code point picks the row of the table, which says how many bytes it takes. The last byte carries the lowest six bits of the code point, the byte before it the next six, and so on; the first byte carries whatever bits are left, behind its marker (0, 110, 1110 or 11110), with zeros in front when the code point has fewer bits than the row has slots. Every byte after the first is 10 followed by six bits. Collect the bytes of every character in order, and turn them into a bytes once, at the end.

Rung 3: the shape

A bytearray (or a list of ints) for the output, made before the loop. One loop over the text, with ord. Inside it, the surrogate check, then an if and elif chain with one branch per row of the table, each comparing the code point against that row's top edge, from the docstring. In each branch, one value per byte, built the same way every time: a shift right by a multiple of six, which brings the bits that byte carries down to the bottom; a mask, which keeps only those bits; and an OR with the byte's marker. The markers (one for the first byte of each row, and one for every continuation byte) and the mask of a continuation byte are named constants at the top of the file. Work their values out from the table yourself: a marker is a byte's fixed bits with zeros in its x slots, and a mask has ones in the slots. Write each in binary in a comment beside its hex. The last line turns the collected numbers into bytes with one argument. Test "A", "é", "€" and "🙂" first, then the edges.

Rung 4: the same mechanism on a different problem

Old FAT file systems pack a date into 16 bits: seven for the year since 1980, four for the month, five for the day. Packing puts each field in its place with a shift and an OR; unpacking takes it out again with a shift and a mask. To store the 16 bits on disk, the number is cut once more, into two bytes.

"""A date in 16 bits, the way old FAT file systems store it: yyyyyyym mmmddddd.

    bits 15 to 9   the year minus 1980 (7 bits: 1980 to 2107)
    bits  8 to 5   the month (4 bits)
    bits  4 to 0   the day (5 bits)
"""


def pack_date(year, month, day):
    if not 1980 <= year <= 2107:
        raise ValueError(f"year {year} does not fit in 7 bits from 1980")
    return (year - 1980) << 9 | month << 5 | day


def unpack_date(packed):
    year = (packed >> 9) + 1980  # the top 7 bits: shift the other 9 away
    month = (packed >> 5) & 0b1111  # shift the day away, then keep 4 bits
    day = packed & 0b11111  # keep the lowest 5 bits
    return year, month, day


packed = pack_date(2026, 11, 23)
print(packed, f"{packed:016b}")
print(f"{2026 - 1980:07b} {11:04b} {23:05b}")
print(unpack_date(packed))

# Stored on disk as two bytes, the low byte first.
low, high = packed & 0xFF, packed >> 8
print(f"{high:08b} {low:08b}", hex(high), hex(low))
print(unpack_date(high << 8 | low))

for date in [(1980, 1, 1), (1999, 12, 31), (2107, 12, 31)]:
    assert unpack_date(pack_date(*date)) == date
print("every date comes back")

23927 0101110101110111
0101110 1011 10111
(2026, 11, 23)
01011101 01110111 0x5d 0x77
(2026, 11, 23)
every date comes back

The second line prints the three fields side by side, and they are the packed number's sixteen bits cut at the field edges. Your utf8_encode cuts a code point the same way, with three differences: every group has six bits except the first, the number of groups depends on the size of the number, and every byte gets marker bits in front of its group.

Common bugs.

  • assert 2 == 3 at U+0800, or 3 == 2 at U+07FF: a row's edge is off by one. The rows end at 0x7F, 0x7FF and 0xFFFF, and each edge belongs to the lower row.
  • A byte like 0x29 where 0xa9 belongs: the continuation marker, the 10 in front of six bits, is missing.
  • ValueError: byte must be in range(0, 256) (or bytes must be, from bytes()): a shifted value kept bits from the groups above it, because the mask is missing.
  • The right bytes in the wrong order: the lowest six bits went first. In UTF-8 the first byte carries the highest bits.
  • Failed: DID NOT RAISE for 0xDFFF: the surrogate check misses an end of the range, which includes both 0xD800 and 0xDFFF.
  • work the bytes out yourself: the test found .encode or .decode somewhere in utf8.py, even in a line you added to print while debugging. It reads the whole file.
  • return bytes, not a list or a bytearray: the collected numbers were returned as they are.

Milestone 2: count_pairs and merge_pair

Goal. count_pairs(ids) returns a dict from each pair of neighbouring ids to how often it occurs, overlaps included. merge_pair(ids, pair, new_id) returns a new list in which every occurrence of the pair is replaced by new_id, scanning from the left, so that of two overlapping occurrences the left one wins. Neither changes the sequence it was given.

Re-read. Chapter 2: Counting with a dict, Neighbours in a list and Overlapping pairs. The docstrings of both functions in train.py.

Turns green. uv run pytest tests/m02 -k "count_pairs or merge_pair", eleven tests.

The hint ladder.

Rung 1: where to look

Put the two docstrings side by side and read their [7, 7, 7] lines: count_pairs counts (7, 7) twice, and merge_pair makes one merge. Why do they disagree? Then read test_merge_pair_returns_a_new_list (three asserts: equal, not the same object, and a list even when it is given a tuple) and test_merge_pair_can_be_undone. Work merge_pair([7, 7, 7, 7], (7, 7), 9) by hand, writing down the position you are at after each step.

Rung 2: the idea in words

count_pairs: every position except the last starts one pair, the item there and the item after it. Add one to that pair's count, and move on by one, whatever you found. merge_pair: walk the ids from the left with a position. If the item there and the next one form the pair, write the new id and jump two places, because both items are used up; otherwise copy the item and step one place. The jump of two is what makes the left occurrence win. The last item has no next item, so it can only be copied.

Rung 3: the shape

count_pairs: a dict, and one loop over the neighbouring pairs, made with zip of the ids and the ids without their first item; inside, dict.get with a default of 0. A Counter works too, since it is a dict. merge_pair: a new list made first, a position that starts at 0, and a while loop, not a for, because a for cannot jump ahead by two. Inside, one if whose test checks that there is a next item before it reads it, and an else. Test [], [5], [7, 7, 7] and [1, 2] with the pair (2, 1) first.

Rung 4: the same mechanism on a different problem

Chapter 2's day-to-day temperature changes are the counting half: neighbours made with zip, and a dict that counts. For the scanning half, here is a scan whose step is sometimes one and sometimes two: laying dominoes along a row of squares, from the left. A domino covers two neighbouring free squares; a blocked square, or a free one with no free square after it, is stepped over.

"""Dominoes on a row of squares, laid from the left.

"." is a free square and "#" a blocked one. A domino covers two neighbouring free squares.
Walk from the left, and lay one wherever the square you stand on and the next are both free.
"""


def domino_starts(row):
    """Where each domino starts, from left to right."""
    starts = []
    i = 0
    while i < len(row):
        if row[i] == "." and i + 1 < len(row) and row[i + 1] == ".":
            starts.append(i)  # a domino on squares i and i + 1
            i += 2  # jump past both: the second square is covered now
        else:
            i += 1  # blocked, or a free square with no free square after it
    return starts


def drawn(row, starts):
    squares = list(row)
    for i in starts:
        squares[i], squares[i + 1] = "[", "]"
    return "".join(squares)


for row in ["....", "...", ".#..#...", "#.#.#", "......#.", ""]:
    starts = domino_starts(row)
    print(f"{row!r:11} {drawn(row, starts)!r:11} {len(starts)} at {starts}")

'....'      '[][]'      2 at [0, 2]
'...'       '[].'       1 at [0]
'.#..#...'  '.#[]#[].'  2 at [2, 5]
'#.#.#'     '#.#.#'     0 at []
'......#.'  '[][][]#.'  3 at [0, 2, 4]
''          ''          0 at []

The second line is the left-first rule: three free squares hold one domino, and the scan lays it on the left two, so the third stays free. The jump of two is what stops a square from being covered twice, and the test i + 1 < len(row) comes before row[i + 1] is read, so the last square never reaches past the end. Your merge_pair has the same while loop and the same two step sizes; what it asks of two neighbours, and what it builds, are different.

Common bugs.

  • IndexError: list index out of range in count_pairs: the loop ran to the last position, which has no item after it.
  • {(7, 7): 1} for [7, 7, 7]: count_pairs jumped ahead after a pair. Counting looks at every position; only merging skips.
  • More new ids than there should be, such as [9, 9, 7] for [7, 7, 7]: after a merge the scan stepped one place, not two, so the middle 7 was used twice.
  • The last id is missing, as in [1, 2] for [1, 2, 3] with a pair that is not there: the loop stopped one place early, because its test is the one for reading a pair, not the one for copying an item.
  • return a new list, even when nothing changes: merge_pair returned the list it was given when the pair was not in it.
  • type(...) is list fails: given a tuple, the function returned a slice or a copy of the tuple.
  • test_..._does_not_change_its_input fails: the list was changed in place, with del, pop or an assignment to an item.

Milestone 3: train_bpe

Goal. train_bpe(chunks, vocab_size) learns byte-pair merges from chunks of text: each round counts every neighbouring pair in every chunk, merges the most frequent one (the smallest pair on a tie) into the next free id, and repeats until the vocabulary has vocab_size tokens or nothing is left to merge. It returns the merges in the order they were learned, and it trains 300 merges on a million characters in under ten seconds.

Re-read. Chapter 2: Ties, and choosing with a key, Byte-pair encoding by hand, Count each word once and What training gives you. The three numbered steps in the docstring of train_bpe.

Turns green. uv run pytest tests/m02 -k train_bpe, ten tests.

The hint ladder.

Rung 1: where to look

Work train_bpe(["abab", "ab"], 258) by hand as a table, one row per round: the counts of every pair, the winner, its new id, and the chunks after the merge. Then read test_train_bpe_a_chunk_that_repeats_counts_each_time and its comment, test_train_bpe_on_a_paragraph_learns_these_merges (its comments say what each merge is), and the failure message of the speed test. How many words does argparse's source have ten times over, and how many different ones?

Rung 2: the idea in words

Refuse a vocabulary below 256. Count how often each distinct chunk occurs, and turn each distinct chunk into the list of its UTF-8 byte values. Then, once per merge you have room for: count every pair in every distinct chunk, adding each chunk's counts as many times as the chunk occurs; if there is nothing to count, stop early; choose the pair with the highest total, and on a tie the smallest pair; give it the next free id; record it; and replace it in every chunk, as merge_pair does. The chunks are never joined, so no pair ever spans two of them.

Rung 3: the shape

A Counter of the chunks. A list of the distinct chunks as lists of ids, with a matching list of how often each occurs (or pairs of the two). A list of merges. One for loop over the number of merges to make, vocab_size - 256. Inside it: a dict of totals, filled by your count_pairs on each chunk, each count multiplied by that chunk's frequency; an early break when the dict is empty; one call to max or min with a key that is a tuple, whose first part makes higher totals win and whose second part makes smaller pairs win (a number and its negative sort in opposite orders); the new id from the number of merges so far; and your merge_pair on every chunk. Make the three docstring examples green first, then the repeat test, then the paragraph, then the speed test.

Rung 4: the same mechanism on a different problem

A radio request show. Each round the presenter plays the most requested song, ties going to the title that comes first in the alphabet, and playing a song halves what is left of its requests. A greedy loop: count, choose by a key with two parts, change the counts, repeat, and stop early when there is nothing left to choose.

"""A radio request show. Each round the presenter plays the most requested song (ties: the title
that comes first in the alphabet), and playing it halves what is left of its requests, rounded
down. A song with no requests left drops off the list."""

requests = {"Yellow": 9, "Africa": 6, "Heroes": 9, "Valerie": 4, "Wonderwall": 2}

for show_round in range(1, 8):
    if not requests:
        print("no requests left")
        break
    # Most requests first; among equal counts, the earlier title. One key, two parts.
    title = min(requests, key=lambda t: (-requests[t], t))
    print(f"round {show_round}: {title:10} ({requests[title]} requests)")
    requests[title] //= 2
    if requests[title] == 0:
        del requests[title]

print(requests)

round 2: Yellow     (9 requests)
round 3: Africa     (6 requests)
round 4: Heroes     (4 requests)
round 5: Valerie    (4 requests)
round 6: Yellow     (4 requests)
round 7: Africa     (3 requests)
{'Yellow': 2, 'Africa': 1, 'Heroes': 2, 'Valerie': 2, 'Wonderwall': 2}

Heroes and Yellow both start with 9, and Heroes goes first because (-9, "Heroes") is smaller than (-9, "Yellow"). The key turns "most requests" into "smallest negative", so that one min settles both parts. Your train_bpe differs in what it counts: all the pairs of every chunk, counted again each round, because a merge changes the pairs around it.

Common bugs.

  • The docstring's tie example returns [(98, 97)]: on a tie the pair seen first won, by the order of a dict, instead of the smallest pair.
  • test_train_bpe_a_chunk_that_repeats_counts_each_time returns [(97, 98)]: each distinct chunk was counted once with no weight, so the two pairs tied.
  • test_train_bpe_three_hundred_merges_on_a_million_characters_in_ten_seconds fails with still training after 10 s: every one of about 92,000 words is counted each round, instead of about 2,600 distinct ones, each weighed by its frequency.
  • A merge such as (98, 97) appears in test_train_bpe_merges_never_cross_from_one_chunk_to_the_next: the chunks were joined into one list.
  • ValueError: max() iterable argument is empty (or min()): nothing checks for a round with no pairs left.
  • test_train_bpe_works_on_utf8_bytes fails with 233 in the answer: the chunks became lists of code points, not of UTF-8 bytes. "é" is one code point and two bytes.
  • a pair is merged once fails: the new id came from somewhere other than 256 plus the number of merges so far, so two merges got the same id.

Milestone 4: pretokenize, apply_merges and Tokenizer

Goal. pretokenize(text) splits text into GPT-2's chunks. apply_merges(ids, ranks) replays merges on the ids of one chunk, the lowest rank first. Tokenizer checks its byte ids and merges, and turns text into ids (encode) and ids back into text (decode), with token_bytes for one token. With it, the first half of the module's "Done when" passes: round trips are exact on arbitrary Unicode.

The hint ladder.

Rung 1: where to look

Three parts, in this order. pretokenize: its four docstring examples, and the cases of test_pretokenize_splits_like_gpt2 ("a b", "end " and "one\n\ntwo" are the subtle ones); which module knows \p{L}? apply_merges: the docstring's "The order is the rank, not the position", and test_apply_merges_a_merge_can_use_an_earlier_merge. Rung 2: the idea in words

pretokenize: every match of GPT2_PATTERN, in order, found with the regex package. apply_merges: work on a copy. Repeat: among the neighbouring pairs, find the one with the lowest rank, where a pair that has no rank counts as never; if even the best has no rank, stop; otherwise replace every occurrence of it with 256 plus its rank, as merge_pair does. Tokenizer: the constructor checks the byte ids and the merges, then builds what the methods need: the ranks of the merges, and the bytes of every token. Token 256 + r is the bytes of its left part followed by the bytes of its right part, and both exist already, because merge r only uses ids below 256 + r. A special token stands for the UTF-8 bytes of its text. encode turns each chunk into ids through the byte ids, merges each chunk on its own, and joins the results. decode joins the bytes of all the tokens first, and only then decodes, with errors="replace".

Rung 3: the shape

pretokenize: import regex at the top of bpe.py, and one call that returns every match as a list. apply_merges: a list made from the ids, a while True loop, and inside it one min over the neighbouring pairs with a key that looks the pair up in ranks with a default of math.inf; a break when the list is shorter than two or the best rank is infinite; then a merge. Tokenizer.__init__: two checks that raise ValueError (the byte ids, sorted, must be exactly 0 to 255; each id of merge r must be below 256 + r); then attributes on self: the byte ids as a list, a dict of ranks, a dict (or a list) from id to bytes filled in rank order, and the special tokens. encode: one loop over the chunks; a comprehension through the byte ids; extend. decode: b"".join over token_bytes of each id, then .decode. token_bytes: a lookup, and a ValueError for an id it does not know. Make the docstring examples green first, then Tokenizer(range(256), []), then the backwards tokenizer.

Rung 4: the same mechanism on a different problem

Two of this milestone's mechanisms on arithmetic. A regular expression whose alternatives, tried left to right, cut an expression into its pieces, with nothing lost; and a table of ranks in which anything missing ranks as infinity, so that one min finds the leftmost of the lowest.

import math
import re

# Every piece of an arithmetic expression, in order. The alternatives are tried left to right at
# each place, and the first one that matches wins, so "**" must come before "*".
PIECE = re.compile(r"\d+(?:\.\d+)?|[a-z_]+|\*\*|[-+*/()]|\s+|.")

# Which operator to work out first: the lowest number wins. Anything else has no precedence.
PRECEDENCE = {"**": 0, "*": 1, "/": 1, "+": 2, "-": 2}

for text in ["2 * width + 3.5", "x**2-1", "10 - 4 - 3 ?"]:
    pieces = PIECE.findall(text)
    assert "".join(pieces) == text  # nothing is lost: the pieces join back into the text
    print(pieces)
    ranks = [PRECEDENCE.get(piece, math.inf) for piece in pieces]
    print(" ", ranks)
    first = min(range(len(pieces)), key=lambda i: ranks[i])  # the leftmost of the lowest
    print("  work out first:", repr(pieces[first]), "at piece", first)

  [inf, 0, inf, 2, inf]

Rung 2: the idea in words

Never move a token. Keep them in a list by their starting position, and keep two more lists: for each position, the position of the token on its left and of the token on its right. A merge then keeps the left token's position, gives it the new id, and takes the right token out by linking its neighbours to each other. Put on a heap one entry for each neighbouring pair that has a rank: the rank first, then the position of the pair's left token, so that the top is always the lowest rank and, among equal ranks, the leftmost, which is merge_pair's order. Pop an entry and check that it is still true: the left position is still a token, it still has a right neighbour, and the two tokens there still make a pair with exactly that rank. If not, it went stale; skip it. If it is, merge, and push entries for the two new pairs the merge made, with its left neighbour and with its right neighbour, if they have ranks. When the heap is empty, walk the links from the first position and collect the tokens.

Rung 3: the shape

A list of tokens copied from the ids, and two lists of positions, one for the left neighbour and one for the right, with a value that means "none" (and a way to tell that a position has been merged away: a list of flags, or a mark in one of the link lists). The heap: a list of (rank, position) tuples from one loop over the neighbouring pairs that have a rank, then heapify. One while loop over the heap. Inside it: heappop; the checks that skip a stale entry, with continue; the merge, which is one assignment of the new id and a few changes of links; and up to two pushes. Position 0 is never merged away, because a merge always keeps its left token, so the final walk starts there. Rung 4: the same mechanism on a different problem

Simplifying a line. A walking route is a list of points, and you want fewer of them without losing its shape. Again and again, remove the point that matters least: the one whose triangle with its two neighbours has the smallest area, because a point on a straight stretch makes almost no triangle. This is Visvalingam's algorithm. It needs exactly this milestone's two structures: a heap, to find the smallest area at once, and a linked list of neighbours in two lists, so that removing a point is two link changes. After a removal, the two neighbours have new triangles, so their old heap entries go stale; a version number per point recognises them.

"""Simplify a walking route: remove, again and again, the point that matters least.

A point matters as much as the area of the triangle it makes with its two neighbours: a point on
a straight stretch makes almost no triangle, a sharp corner makes a big one. This is Visvalingam's
algorithm. The two ends are never removed.
"""

import heapq

route = [(0, 0), (1, 0.1), (2, -0.1), (3, 5), (4, 6), (5, 7), (6, 8.1), (7, 2), (8, 0), (9, 0)]
KEEP = 5  # stop when this many points are left

n = len(route)
# prev[0] is -1 and nxt[n - 1] is n, "none" at the two ends. Neither is ever read: the ends are
# never removed, and area() is only asked about the points between them.
prev = [i - 1 for i in range(n)]  # prev[i]: the point before i on the line
nxt = [i + 1 for i in range(n)]  # nxt[i]: the point after i
removed = [False] * n
version = [0] * n  # bumped each time a point's area changes; older heap entries are stale


def area(i):
    """The area of the triangle that point i makes with its current neighbours."""
    (ax, ay), (bx, by), (cx, cy) = route[prev[i]], route[i], route[nxt[i]]
    return abs((bx - ax) * (cy - ay) - (cx - ax) * (by - ay)) / 2


heap = [(area(i), i, 0) for i in range(1, n - 1)]  # (area, point, version): no entry for the ends
heapq.heapify(heap)

left = n
while left > KEEP:
    a, i, v = heapq.heappop(heap)
    if removed[i] or v != version[i]:
        print(f"  skip a stale entry for {route[i]}")
        continue  # stale: the point is gone, or its area changed after this entry was pushed
    print(f"remove {route[i]}, area {a:.2f}")
    removed[i] = True
    left -= 1
    before, after = prev[i], nxt[i]
    nxt[before] = after  # unlink i: its two neighbours now point at each other
    prev[after] = before
    for j in (before, after):  # their triangles have changed; the ends have none
        if 0 < j < n - 1:
            version[j] += 1
            heapq.heappush(heap, (area(j), j, version[j]))

kept = []
i = 0
while i < n:  # walk the links from the first point
    kept.append(route[i])
    i = nxt[i]
print(kept)
print(len(heap), "entries still on the heap, some of them stale")

remove (4, 6), area 0.00
  skip a stale entry for (5, 7)
remove (5, 7), area 0.10
remove (1, 0.1), area 0.15
remove (8, 0), area 1.00
  skip a stale entry for (3, 5)
  skip a stale entry for (7, 2)
  skip a stale entry for (2, -0.1)
  skip a stale entry for (6, 8.1)
  skip a stale entry for (3, 5)

[(0, 0), (2, -0.1), (3, 5), (6, 8.1), (9, 0)]

(4, 6) goes first: it lies on the straight line from (3, 5) to (5, 7), so its triangle has no area at all. Removing it changes the triangle of (5, 7), whose old entry is then skipped as stale before its new one comes off. The heap still holds entries at the end, for points that are gone or whose areas changed; nothing has to clean them up. Your apply_merges_fast differs in three ways. It merges two neighbours into one new token instead of removing a point, it checks that an entry is still true by looking at the tokens themselves instead of keeping a version number, and among equal ranks the leftmost position must win, which is why the position is the second item of its entries.

"""Predict, then measure: build one long string from many short pieces, with += and with join.

Prediction, written before the first run: += copies the whole string so far at every step, so
its time should quadruple each time the number of pieces doubles, and at 400,000 pieces join
should be at least 50 times faster.
"""

import statistics
import time


def with_add(pieces):
    text = ""
    for piece in pieces:
        text += piece
    return text


def with_join(pieces):
    return "".join(pieces)


def median_ms(how, pieces, runs=7, warmup=2):
    times_ns = []
    for _ in range(warmup + runs):
        start = time.perf_counter_ns()
        how(pieces)
        times_ns.append(time.perf_counter_ns() - start)
    return statistics.median(times_ns[warmup:]) / 1e6  # the warm-up runs are left out


print(f"{'pieces':>8} {'+=':>9} {'join':>9} {'ratio':>6}")
for n in (100_000, 200_000, 400_000):
    pieces = [f"w{i % 97} " for i in range(n)]  # made outside anything timed
    assert with_add(pieces) == with_join(pieces)  # first, the two must agree
    add, join = median_ms(with_add, pieces), median_ms(with_join, pieces)
    print(f"{n:8,} {add:7.2f}ms {join:7.2f}ms {add / join:6.1f}")

In a real engine

vLLM tokenizes every prompt, with the model's Hugging Face tokenizer, before the scheduler sees it, and turns the generated ids back into text a few at a time while it streams. Because a token can end in the middle of a character, its incremental detokenizer (in vllm/v1/engine/detokenizer.py) holds back bytes that do not yet make a whole character instead of printing "�": the errors="replace" question of your decode, in a server. tiktoken does GPT-2's split and merges in Rust, and your tests have just checked every id you make against it.

Check yourself

"€" is U+20AC. How many bytes does UTF-8 give it, and how many bits of the code point go into each byte?

Answer

Three bytes, because 0x20AC lies between 0x800 and 0xFFFF. Sixteen bits are cut 4, 6, 6: four behind the first byte's 1110, and six behind each 10. That gives e2 82 ac.

What do count_pairs([7, 7, 7, 7, 7]) and merge_pair([7, 7, 7, 7, 7], (7, 7), 9) return?

Answer

{(7, 7): 4}, because every one of the four positions that has a next item starts a pair. And [9, 9, 7]: the scan merges positions 0 and 1, jumps to 2, merges 2 and 3, and copies the last 7.

argparse's source ten times over has about 92,000 words and 2,600 distinct ones. Why does counting each distinct word once, weighed by its frequency, give the same merges as counting every word?

Answer

Every copy of a word has the same pairs, and a merge changes every copy in the same way. So the pairs of a word seen 40 times are its pairs counted once, times 40, in every round. The totals are equal, the winners are equal, and the work per round falls roughly in the ratio of 92,000 to 2,600.

A tokenizer has one merge, (100, 32), "d" then a space. Why does it encode "d d" as [100, 32, 100] and never use the merge?

Answer

GPT-2's split makes the chunks "d" and " d": a word keeps the space in front of it. No chunk holds a "d" followed by a space, and merges never cross from one chunk into the next.

In apply_merges_fast, the entry (rank 3, position 7) comes off the heap. What must be true before you merge, and what do you push afterwards?

Answer

Position 7 must still hold a token, it must still have a right neighbour, and those two tokens must still make the pair whose rank is 3. Otherwise the entry is stale and you skip it. After the merge, push an entry for the new pair with the left neighbour and one for the new pair with the right neighbour, each only if it has a rank.

Why is -1 a dangerous way to say "no neighbour" in a Python list of positions?

Answer

Because tokens[-1] is not an error: it is the last item. Code that forgets to check reads a real token from the far end and goes on with a wrong answer, silently. None fails loudly when used as an index, and a value such as n can be checked against the length.

Why does M7's prediction get its own commit before the measurement?

Answer

So that git can show it was written first. A prediction edited after the run is a description, and it cannot surprise you. The surprise, a number far from what you predicted, is what tells you that your picture of the machine was wrong.
