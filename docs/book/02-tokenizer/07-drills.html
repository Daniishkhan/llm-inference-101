How the drills work

A drill is a small, classic problem solved by hand against a clock: a statement in a docstring, a function whose body says TODO(you), and a test file beside it. The rules are the ones you used in Module 1, and they are written out in full in docs/methodology.md, under "Drills and the ledger":

  • Hands only. No agent, no completion, no paste. The Python docs are allowed, and every lookup is written down.
  • A time box, given at the end of each stub's docstring. At the bell, ask for one rung of the ladder or log a timeout.
  • Out loud. Say what you are doing while you do it.
  • Dry-run before you run. When you think you are done, walk two inputs through your code on paper, one of them an edge case (an empty chain, a list of one). Then run the tests, and count the runs until green.
  • The ledger. One row per attempt in ledger.md: minutes, the highest rung, lookups, runs, and the result (green, green+hint or timeout).
  • Two redos, at +2 and +7 days, cold, from an emptied function. A redo that falls on a Sunday moves to the Monday.
  • No reveal after a timeout. The problem stays open and comes back at its +2 day redo with the rungs you have not used.
  • One commit per solved drill, with the minutes in the message: reverse_list: 14 min, no hints.

Following links: a chain of nodes

A Python list is very good at one thing: finding the item at a position. It is poor at another: putting an item in at the front, or taking one out of the middle, because everything after that place has to move along by one. For a list of a million items, an insert at the front is a million moves. Some programs insert and remove in the middle all the time and almost never ask for "the item at position 500,000". For them there is a different way to keep a sequence: each item in its own small object, a node, that holds the item and a link to the node after it. A chain of such nodes is a linked list. The first node is its head, and the last node's link is None.

First principle

A Python list keeps, in one block of memory, the addresses of its items one after another. The address of item i is found by arithmetic (the start of the block plus 8 bytes times i), which is why xs[i] is instant, and why inserting at the front means shifting every address one slot along. A node is an object that can live anywhere in memory; its next attribute holds the address of one other node. Nothing is side by side, so nothing has to shift when you insert. And nothing can be found by arithmetic, so reaching the 500,000th node means following 499,999 links, one at a time.

Analogy

A treasure hunt. Each clue tells you where the next clue is hidden, and the last one says "the end". To add a clue in the middle, you rewrite one clue to point at the new one, and the new one to point where the old one did; no other clue changes. Where it breaks: a person on a treasure hunt can look around and spot clue 7 under a bench. A program sees only the nodes it holds a name for. Lose the name of the only node that leads to the rest, and the rest is gone.

A bus route, three stops, built by hand and walked from the first stop to the last:

from __future__ import annotations

from dataclasses import dataclass


@dataclass(eq=False)
class Stop:
    name: str
    next: Stop | None = None


# Build the route Mill Lane -> Market -> Station by hand, back to front.
station = Stop("Station")
market = Stop("Market", station)
first = Stop("Mill Lane", market)

# Walk it: follow the links until there is no next stop.
stop = first
while stop is not None:
    print(stop.name)
    stop = stop.next

count = 0
stop = first
while stop is not None:
    count += 1
    stop = stop.next
print(count, "stops")
print(first.next.next.name)

The route is built back to front, so that each stop exists before the stop in front of it links to it. The walk is the loop you will write in every linked-list problem: start a variable at the head, do something with the node it names, move it with stop = stop.next, and stop when it is None. The walk uses its own variable, stop, and leaves first alone. Walk with first itself and, at the end, nothing names the start of the route any more. Counting is the same walk with a counter: there is no len for a chain, unless you keep one yourself.

Python you need

A dataclass can link to its own kind. The annotation Stop | None names the class while it is still being defined, which from __future__ import annotations allows: it keeps annotations as text instead of working them out at once. The drills' Node is written the same way.

@dataclass also writes an __eq__ that compares the fields, so two different nodes with equal fields are ==. For nodes you almost always mean "the same node", which is is. eq=False leaves Python's own ==, which is is:

from __future__ import annotations

@dataclass
class Carriage:  # eq is left on: == compares the fields
    seats: int
    next: Carriage | None = None


@dataclass(eq=False)
class Wagon:  # eq=False: == asks whether it is the same object, like `is`
    seats: int
    next: Wagon | None = None


print(Carriage(40) == Carriage(40), Carriage(40) is Carriage(40))
print(Wagon(40) == Wagon(40), Wagon(40) is Wagon(40))

The last line shows the other problem with the default: the printed form of a node includes the node after it, and that one the next, all the way down the chain. That is why the drills' Node has its own __repr__, which prints only its value.

Trap

Field-by-field == on a long chain compares the first nodes, which compares their next nodes, which compares theirs: one Python call inside another for every node. Python stops a chain of calls at about a thousand deep, with a RecursionError, and so does any function that calls itself once per node (the appendix shows one, in Heaps and linked lists). The drills' tests use chains of 100,000 nodes on purpose: a loop is the safe shape.

A wider version: build a route from a Python list front to back, then change it in the three ways a linked list does cheaply.

from __future__ import annotations

from dataclasses import dataclass


@dataclass(eq=False)
class Stop:
    name: str
    next: Stop | None = None


def build(names):
    """A route through names, in order: its first stop, or None."""
    first = last = None
    for name in names:
        stop = Stop(name)
        if first is None:
            first = stop  # the very first stop: nothing to link it from
        else:
            last.next = stop  # hang the new stop on the end
        last = stop
    return first


def show(first):
    names = []
    stop = first
    while stop is not None:
        names.append(stop.name)
        stop = stop.next
    print(" -> ".join(names) if names else "(no stops)")


route = build(["Market", "Station", "Bridge"])
show(route)

route = Stop("Mill Lane", route)  # a new first stop: one link, nothing moves
show(route)

market = route.next
school = Stop("School", market.next)  # first: the new stop points at what follows
market.next = school  # then: Market points at the new stop
show(route)

market.next = market.next.next  # remove the stop after Market
show(route)
print(school.name, "still exists, but no stop leads to it")
show(build([]))

Market -> Station -> Bridge
Mill Lane -> Market -> Station -> Bridge
Mill Lane -> Market -> School -> Station -> Bridge
Mill Lane -> Market -> Station -> Bridge
School still exists, but no stop leads to it
(no stops)

build keeps two names: first, which never changes after the first stop, and last, the stop at the end, so that each new stop is hung on the end with one assignment instead of a walk from the front. Then three edits, each one or two assignments however long the route is:

  • Insert at the front: a new stop whose next is the old first stop. The new stop is now the head, so the name route moves to it.
  • Insert after a stop: the new stop first points at what follows, then the stop before it points at the new stop.
  • Remove the stop after a stop: point past it. The removed stop still exists for as long as something names it (here school), but no walk will ever reach it again.
Trap

In "insert after", the order of the two assignments is the whole trick. Write market.next = school first, and then school.next = market.next makes School point at itself: the rest of the route is lost, and a walk goes round School for ever. Before you change a link, make sure something else already names the node it pointed at.

One more shape, for removing nodes that may include the first one. Take out every closed stop of a route. Removing a stop in the middle is "point past it" from the stop before. But the first stop has no stop before it, so removing it is a different operation: the head itself moves. A placeholder node (also called a dummy or a sentinel) put in front of the head gives every real stop a stop before it, and the special case disappears:

from __future__ import annotations

from dataclasses import dataclass


@dataclass(eq=False)
class Stop:
    name: str
    closed: bool = False
    next: Stop | None = None


def build(stops):
    first = last = None
    for name, closed in stops:
        stop = Stop(name, closed)
        if first is None:
            first = stop
        else:
            last.next = stop
        last = stop
    return first


def names(first):
    out = []
    while first is not None:
        out.append(first.name)
        first = first.next
    return out


def skip_closed(first):
    """Unlink every closed stop. Returns the new first stop, which may be a different one."""
    placeholder = Stop("(placeholder)", next=first)  # a stop in front of the first one
    before = placeholder
    while before.next is not None:
        if before.next.closed:
            before.next = before.next.next  # unlink it; stay where you are
        else:
            before = before.next  # keep it; step on
    return placeholder.next


route = build([("Mill Lane", True), ("Market", False), ("School", True), ("Park", True), ("Station", False)])
print(names(route))
print(names(skip_closed(route)))
print(names(skip_closed(build([("Depot", True), ("Yard", True)]))))
print(names(skip_closed(None)))

['Mill Lane', 'Market', 'School', 'Park', 'Station']
['Market', 'Station']
[]
[]

The loop always looks one stop ahead, at before.next, because to unlink a stop you must stand on the stop before it. After an unlink it does not step on: the stop that has moved up into before.next has not been looked at yet, and Park, right after School, is closed too. The new head is whatever the placeholder points at in the end, which is None when every stop was closed. The placeholder is never part of the answer.

Walking two chains at once

Some questions are about two chains: do they hold the same items, how do their items interleave, which comes first. The shape is one name per chain, like a finger on each, and a loop that moves the fingers by the rule of the question. The loop runs while both fingers are on a node. When it stops, at most one chain has nodes left, and the question decides what happens to them.

Two piles of cards, each kept as a chain from the top card down. Do they hold the same cards in the same order?

from __future__ import annotations

from dataclasses import dataclass


@dataclass(eq=False)
class Card:
    label: str
    next: Card | None = None


def pile(labels):
    """A pile of cards, top first: its top card, or None."""
    top = last = None
    for label in labels:
        card = Card(label)
        if top is None:
            top = card
        else:
            last.next = card
        last = card
    return top


def same_cards(a, b):
    """True when both piles hold the same labels in the same order."""
    while a is not None and b is not None:
        if a.label != b.label:
            return False
        a, b = a.next, b.next  # both fingers move together
    return a is None and b is None  # both ran out at once, or one pile is longer


print(same_cards(pile(["7♠", "Q♥", "2♦"]), pile(["7♠", "Q♥", "2♦"])))
print(same_cards(pile(["7♠", "Q♥", "2♦"]), pile(["7♠", "K♥", "2♦"])))
print(same_cards(pile(["7♠", "Q♥"]), pile(["7♠", "Q♥", "2♦"])))
print(same_cards(None, None))

True
False
False
True

Inside the loop the two fingers always move together. The interesting line is the last: when the loop ends, either both fingers fell off at the same moment (the piles are the same length, and every card matched), or one is still on a card, and then one pile is longer. Leave that line out and the third pile, which is the second one with its last card missing, would count as the same.

A wider version, where the fingers move in turn: a perfect riffle shuffle, one card from the left pile, then one from the right, into a new Python list.

from __future__ import annotations

from dataclasses import dataclass


@dataclass(eq=False)
class Card:
    label: str
    next: Card | None = None


def pile(labels):
    top = last = None
    for label in labels:
        card = Card(label)
        if top is None:
            top = card
        else:
            last.next = card
        last = card
    return top


def riffle(left, right):
    """The labels of a perfect riffle: one card from the left pile, then one from the right, and
    so on. When one pile runs out, the rest of the other follows as it is. The piles are not
    changed: this reads the links and builds a new Python list."""
    labels = []
    while left is not None and right is not None:
        labels.append(left.label)
        labels.append(right.label)
        left, right = left.next, right.next
    rest = left if left is not None else right  # at most one pile has cards left
    while rest is not None:
        labels.append(rest.label)
        rest = rest.next
    return labels


left = pile(["A♠", "2♠", "3♠"])
right = pile(["A♥", "2♥", "3♥", "4♥", "5♥"])
print(riffle(left, right))
print(riffle(left, None))
print(riffle(None, None))
print(left.label, left.next.label)  # the left pile is as it was

['A♠', 'A♥', '2♠', '2♥', '3♠', '3♥', '4♥', '5♥']
['A♠', '2♠', '3♠']
[]
A♠ 2♠

While both piles have cards, each round takes one from each. When the shorter pile runs out, the leftovers of the other follow as they are, in a second loop that walks whichever finger is not None. The piles themselves are not changed: the function reads their links and copies their labels. A problem that asks you to relink the nodes, instead of copying their values, keeps this shape: two fingers, a loop while both are on a node, and the leftovers after it.

A heap as a to-do list

A triage desk in a hospital. Patients arrive in any order, each with an urgency from 1 (most urgent) upwards, and the nurse always calls the most urgent patient next. Kept in order of arrival, every call means looking at everyone who is waiting. Kept sorted by urgency, every arrival means finding its place and shifting everyone behind it. Either way, one of the two operations costs about n steps for n patients. A heap does both in about log₂ n: for a thousand patients, about 10 steps instead of a thousand.

First principle

A heap is an ordinary list, read as a tree. Position 0 is the top. The two children of position i sit at positions 2i + 1 and 2i + 2, so the parent of position i is at (i − 1) // 2. There is one rule, and only one: no item is smaller than its parent. So the smallest item is always at position 0, and nothing else is promised: two children can be in either order, and the list as a whole is not sorted. A push puts the new item at the end and swaps it with its parent for as long as it is smaller, at most once per level of the tree. A pop takes the item at position 0, moves the last item into its place, and swaps it down with its smaller child until the rule holds again. A tree of n items has about log₂ n levels, so each costs about log₂ n swaps.

Here are seven numbers made into a heap with heapq.heapify, and the rule checked at every position:

import heapq

minutes = [40, 15, 32, 8, 27, 5, 19]
heapq.heapify(minutes)  # rearrange the list in place into heap order, in time proportional to n
print(minutes)

for i in range(1, len(minutes)):
    parent = (i - 1) // 2
    print(f"position {i} holds {minutes[i]:2}; its parent, position {parent}, holds {minutes[parent]:2}")

print(all(minutes[(i - 1) // 2] <= minutes[i] for i in range(1, len(minutes))))
print(minutes == sorted(minutes))

The list is a heap and it is not sorted: 19 sits before 15. Only the top is known to be the smallest. heapify rearranges a whole list in time proportional to its length, which is cheaper than pushing the items one at a time.

Analogy

An organisation chart in which every manager is senior to the two people who report to them. The most senior person is at the top, but two colleagues side by side can be in either order, and someone near the bottom of one branch may be more senior than a manager in another. Where it breaks: when the person at the top leaves, a heap moves whoever sits in the last place of the list up to the top and lets them sink, swapping with the more senior of their two reports at each level. No company fills a post that way.

Python you need

The heapq module works on a plain list that you keep: it has no heap class. heapq.heappush(heap, item) adds, heapq.heappop(heap) removes and returns the smallest, and heap[0] looks at the smallest without taking it. heapq.heapify(xs) turns a list into a heap in place. heapq.heapreplace(heap, item) pops the smallest and pushes item in one go, which is cheaper than the two calls. heapq keeps the smallest on top; it has no option for the largest. Items can be tuples, which compare item by item, the first items first (chapter 5, heapq, and how tuples compare), so (urgency, name) puts the lowest urgency on top.

import heapq

# (urgency, name): 1 is the most urgent. The heap is an ordinary list.
waiting = []
for urgency, name in [(3, "sprained wrist"), (1, "chest pain"), (4, "splinter"), (2, "deep cut")]:
    heapq.heappush(waiting, (urgency, name))
    print("arrives:", name.ljust(15), "next up:", waiting[0][1])

print(waiting)  # heap order, not sorted order

heapq.heappush(waiting, (0, "cardiac arrest"))
while waiting:
    urgency, name = heapq.heappop(waiting)
    print("seen:", urgency, name)

The pops come out in order of urgency all the same, because each pop repairs the heap. The patient who arrives last with urgency 0 goes straight to the top.

Trap

The rule holds only while every change goes through heapq. Append to the list yourself, or change the priority of an entry already inside, and heap[0] may no longer be the smallest. Nothing raises an error:

import heapq

heap = [1, 5, 3]
heapq.heapify(heap)
heap.append(0)  # added by hand, not with heappush: nothing moved it up
print(heap, "top:", heap[0])
print(heapq.heappop(heap), "came off first, though 0 was in the heap")

[1, 5, 3, 0] top: 1
1 came off first, though 0 was in the heap

A wider version: a to-do list that grows while you work through it. A bakery's day is a list of events, each at a minute. Handling one event can set another in motion later: bread that comes out of the oven must cool, then be sliced. The heap always hands you the earliest event that is still to happen, whatever order the events were added in:

import heapq

# What happens next, and what it sets in motion: (minutes until the follow-up, the follow-up).
FOLLOW_UP = {
    "bread in the oven": (35, "bread out"),
    "cake in the oven": (25, "cake out"),
    "bread out": (20, "slice the bread"),
    "cake out": (16, "ice the cake"),
    "ice the cake": (12, "cake on the counter"),
}

events = [(0, "bread in the oven"), (7, "cake in the oven")]  # (minute, event)
heapq.heapify(events)

while events:
    minute, event = heapq.heappop(events)  # always the earliest thing still to happen
    print(f"minute {minute:3}: {event}")
    if event in FOLLOW_UP:
        delay, next_event = FOLLOW_UP[event]
        heapq.heappush(events, (minute + delay, next_event))  # it joins the to-do list

minute   0: bread in the oven
minute   7: cake in the oven
minute  32: cake out
minute  35: bread out
minute  48: ice the cake
minute  55: slice the bread
minute  60: cake on the counter

The cake went into the oven after the bread and came out before it, and its icing (minute 48) was handled before the bread was sliced (minute 55), although the slicing was added to the heap first. The loop does not know about bread or cakes: it takes the earliest event, does it, and pushes whatever that event causes. This is how a discrete-event simulation works, and a simulation of a server, with requests that arrive and finish, is the same loop with other events.

In a real engine

vLLM's scheduler can run with a priority policy (--scheduling-policy priority): each request carries a priority number, a lower one is served first, and the requests waiting to be admitted are kept on a heap with heapq, so finding the next one costs about log₂ n however many are waiting. In recent versions it is in vllm/v1/core/sched/request_queue.py. The default policy, first come first served, needs no heap: a plain queue in order of arrival.

But each step now looks at every waiting event, once to find the smallest and again to remove it, so a step costs about n instead of about log₂ n. With seven events nobody can tell. With a million events waiting, it is the difference between twenty steps and a million.

The smallest of many

A supermarket has k tills and a queue of n customers. Each customer, in turn, goes to the till that will be free first. Asking "which till is free first?" by looking at every till costs k steps per customer, n × k in all. But between two customers only one till changes: the one the last customer went to, which is now busy until later. So keep the tills on a heap, keyed by the minute each one is free. The top is the answer to the question. After you use it, the same till goes back with its new minute. The heap never holds more than k entries, one per till, so each customer costs about log₂ k.

That is the pattern of this section: a heap of a fixed number of candidates, one for each source (here, each till), whose top is the one to use next, and the one you use is replaced by its successor.

import heapq

# Three tills open at minutes 0, 1 and 2. Customers queue in this order, each with the minutes
# their shopping takes to scan, and each goes to the till that is free first.
OPENS = [0, 1, 2]
customers = [("Ana", 4), ("Ben", 9), ("Cy", 3), ("Dee", 5), ("Eli", 2), ("Fay", 7), ("Gus", 6)]


def with_a_heap(customers, opens):
    tills = [(minute, till) for till, minute in enumerate(opens)]  # (minute it is free, till)
    heapq.heapify(tills)
    plan = []
    for name, minutes in customers:
        free_at, till = tills[0]  # the till that is free first is on top
        heapq.heapreplace(tills, (free_at + minutes, till))  # pop it, push it back busy
        plan.append((name, till, free_at))
    return plan


def by_looking_at_every_till(customers, opens):
    free = list(opens)
    plan = []
    for name, minutes in customers:
        till = free.index(min(free))  # the first till with the earliest minute
        plan.append((name, till, free[till]))
        free[till] += minutes
    return plan


for name, till, start in with_a_heap(customers, OPENS):
    print(f"{name:3} goes to till {till} at minute {start}")
print(with_a_heap(customers, OPENS) == by_looking_at_every_till(customers, OPENS))

Ana goes to till 0 at minute 0
Ben goes to till 1 at minute 1
Cy  goes to till 2 at minute 2
Dee goes to till 0 at minute 4
Eli goes to till 2 at minute 5
Fay goes to till 2 at minute 7
Gus goes to till 0 at minute 9
True

tills[0] is read first, because its minute and its number are needed for the new entry. Then heapreplace pops that entry and pushes the till back with the minute it will next be free. The slow version, which looks at every till for every customer, gives the same plan, and the last line checks it. A slow, obviously right version is the oracle of a fast one, here as in the tests.

How much does it save? Count the steps. With 200 tills, looking at every till is 200 steps per customer; the heap is about log₂ 200, about 8. On a real machine the gap is smaller than 25 times, because min and index walk the tills in C while each heap step compares two tuples in Python, but it grows with k: ten times as many tills make the scan ten times as long, and the heap a few steps longer.

Try it

In checkout_lanes.py, what happens with one till? And with as many tills as customers, all open at minute 0?

Show the answer

With one till the heap has one entry, and every customer waits for it in turn: the plan is the queue in order, each customer starting when the one before finishes. With as many tills as customers, all open at 0, every customer gets a till at minute 0, and the heap is as big as the queue: k is n, and the saving is gone, because no customer ever had to wait.

Rung 2: the idea in words

Walk the chain from the head, one node at a time. Each node's link must end up pointing at the node you came from, the one before it. But its link is also your only way forward, so take note of the next node before you change the link. Then step on: the node you are standing on becomes "the one before", and the noted node becomes the one you stand on. The head has nobody before it, so its link becomes None, and it becomes the end. When you step off the end of the chain, the last node you turned round is the new head.

Rung 3: the shape

Three names: the node before (it starts as None), the node you are on (it starts as the head), and the next node (set inside the loop). One while loop that runs while the node you are on is not None. Inside it, four assignments in a fixed order: note the next node, turn the link, move "before" up, move "current" up. Return "before". No recursion, no new Node, no Python list of the nodes. Rung 2: the idea in words

The pattern is a stack (Module 1, A stack), here kept in a particular order, which is sometimes called a monotonic stack. Read the days from left to right, and keep the days that are still waiting for a warmer one. Their temperatures always fall from the oldest to the newest: a waiting day that was warmer than an older waiting day would already have answered it. So when a new day arrives, compare it with the newest waiting day. If the new day is warmer, that waiting day has its answer, the distance between the two days, and it stops waiting; compare again with the next newest, until the newest waiting day is as warm or warmer, or none is left. Then the new day joins the waiting days. Each day joins once and leaves at most once, so the whole walk is about 2n steps. Days still waiting at the end keep 0.

Rung 3: the shape

An answer list of zeros, as long as the temperatures, made first: a day that is never answered is then already right. A list of the positions of the waiting days, not their temperatures: the gap needs the position, and the temperature is one lookup away. One for loop over the positions with enumerate. Inside it, a while loop that runs while the list is not empty and today is strictly warmer than the day at its last position; inside that, take the last position off the end of the list and write today's position minus it into the answer. After the inner loop, add today's position at the end. Say out loud why a while inside a for is still proportional to n here. The debugging drill

The other drills start from an empty function. A debugging drill starts from a finished program that is wrong: some of its tests fail. In 20 minutes you find the fault, say in one sentence why it is a fault, and fix it with the smallest change you can. Interviews ask for this as well, and so does every week of real work. The skill is not guessing: it is narrowing down, one hypothesis at a time.

  1. Read the failing message first, all of it, before you read the code: the exception on the last line, and the line of the program it points at. The message usually says what happened; your job is to find out why.
  2. Reproduce the smallest case. In scratch/, call the function on the smallest input that still fails. Compare it with the tests that pass: what do the failing inputs have that the passing ones do not?
  3. Form one hypothesis, as a sentence: "it fails when ..., because ...".
  4. Test the hypothesis before you fix anything: an input that should fail if you are right, and one that should pass.
  5. Change as little as you can. One line, if one line does it. A rewrite may make the tests pass without telling you what the fault was, and it can bring faults of its own.
  6. Say why, in one sentence, and write that sentence in the ledger's Pattern column. Then run all the tests: the ones that passed before must still pass.

The commit names what you found, with the minutes: print_queue: 12 min, fault found and fixed.

Then list the two tests that pass and the three that fail in test_print_queue.py. Look at the priorities of the jobs in each. What do all three failing tests have that neither passing test has?

Rung 2: the idea in words

heapq keeps its list in heap order by comparing whole entries with <, and an entry here is the tuple (job.priority, job). Tuples compare item by item: the first items first, and only when those are equal, the second items. Two jobs with different priorities are settled by the priorities, and the comparison never looks at the jobs. Two jobs with the same priority make Python go on to compare the two Job objects, and a dataclass has no < unless you ask for one: that is the TypeError. So the fault is that the entry gives the heap nothing to settle a tie with except the jobs themselves. Before you change anything, read the docstring's second rule again: what should settle a tie?

Rung 3: the shape

The shape of the fix, in words. Give each entry a middle item, between the priority and the job, that is different for every job and grows in the order the jobs were sent. The position of the job in the list, from enumerate, is such a number. A tie on priority is then settled by that number, and the comparison never reaches a Job. That is one changed line where the entries are pushed, and one where they are popped, because the entry now has three items. Why not @dataclass(order=True) on Job instead? It makes jobs comparable field by field, so a tie would go to the name in alphabetical order, and test_jobs_with_the_same_priority_print_in_the_order_they_were_sent (zebra, apple, mango) would fail in a new way. Write the one-sentence why before you commit.

Check yourself

A Python list and a linked list each hold a million items. Roughly how many steps does each take to read the item at position 500,000, and to put a new item in at the front?

Answer

The list reads position 500,000 in one step, by arithmetic on addresses, and inserts at the front with a million moves, because every address shifts along. The linked list follows 500,000 links to reach the item, and inserts at the front with one link: the new node points at the old head.

In route_edits.py, School goes in after Market with school = Stop("School", market.next) and then market.next = school. What goes wrong if you make School first with no link and then write market.next = school and school.next = market.next, in that order?

Answer

By the time the second line runs, market.next is already School, so School links to itself. Station and Bridge are no longer reachable from the head, and a walk goes round School for ever. Note where a link pointed before you change it.

Why does a placeholder node in front of the head make removing the first node the same as removing any other?

Answer

Removing a node means changing the link of the node before it. The head has no node before it, so without a placeholder removing the head is a special case: the head itself has to move. With a placeholder every real node has a node before it, the same loop handles them all, and the new head is whatever the placeholder points at in the end.

heap[0] is the smallest item of a heap. At which positions can the second smallest be, and why only there?

Answer

At position 1 or 2. Its parent cannot be larger than it, and the only item smaller than it is the smallest, at position 0; so its parent is position 0, and the children of position 0 are 1 and 2. Which of the two it is, the heap does not say.

Predict what heapq.heapify(xs) makes of xs = [9, 4, 7, 1], then check that the rule holds at every position.

Answer

[1, 4, 7, 9]. Position 1 (4) and position 2 (7) have the parent 1 at position 0, and position 3 (9) has the parent 4 at position 1. This one happens to be sorted, but heapify promises only the rule, as heap_shape.py's list showed.

A shop has 100 tills and a million customers. Roughly how many steps does "look at every till" take for the whole day, and the heap of tills?

Answer

Looking at every till: 100 per customer, about 100 million. The heap: about log₂ 100, which is about 7, per customer, so about 7 million, plus 100 to build it. The heap holds 100 entries all day, because each customer replaces an entry instead of adding one.

Why does a debugging drill ask for the smallest change, when a rewrite would also make the tests pass?

Answer

A small change tests one hypothesis: if the tests turn green, you know what the fault was, and you can say it in one sentence. A rewrite can turn them green without anyone knowing why, can hide the fault rather than remove it, and brings new code with new faults of its own.
