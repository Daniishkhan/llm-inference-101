The problem: a model reads numbers

A language model is arithmetic. Its first step takes a whole number, an id, and looks up the row with that number in a table of learned values (Module 3 builds the table). So something has to turn text into a list of ids from a fixed range, and the model's ids back into text at the end. That is the tokenizer, and its numbers are token ids. What should one id stand for?

  • A word? Then there is always a word missing from the table: a name, a typo, a word from a language it left out. The tokenizer must answer "unknown", and the model never sees what was there.
  • A character? Unicode has room for over a million, and adds more every year. The table would be mostly rows never seen in training, and next year's emoji would still be unknown.
  • A byte? Every stored text is already a list of bytes, and a byte has 256 possible values. A table of 256 rows covers every text in every script, now and later. Nothing is ever unknown.

GPT-2's tokenizer starts from the bytes, and then learns to glue frequent runs of them together (chapter 2), so that a common word is one token instead of five. Here is what it makes of one sentence, Tea is ready 🫖. The table comes from the oracle: tiktoken's GPT-2 encoding, built from the two files in data/gpt2/, the same files you load yourself in M5. The tests check your ids against it, and chapter 4 shows you how to build it. Each token's bytes are written as Python prints a bytes value, which the next sections explain.

The sentence became six ids, each standing for a run of bytes. Tea, is and ready are one token each, with the space in front of the word. The teapot is one character and three tokens, and none of the three is a character: a space and two bytes, then one byte, then one byte. Joined, they are the teapot again, and decoding the six ids gives back the sentence exactly. The oracle's vocabulary has 50,257 tokens: the 256 single bytes, 50,000 runs that training glued together, and one special token, <|endoftext|>.

First principle

Memory, files and network messages hold only bytes. A byte is eight bits, eight switches that are each off (0) or on (1), so it has 28 = 256 values, 0 to 255. Text is not a separate kind of thing inside the machine. It is bytes plus an agreement about what they mean: an encoding. The agreement almost every file, web page and protocol uses today is UTF-8, and it is the one GPT-2's tokenizer reads.

Characters and code points

Before bytes come numbers. Unicode gives every character a number, its code point, written in hexadecimal after U+: the euro sign is U+20AC. ord gives the code point of a one-character string, and chr goes the other way.

Python you need

f-string formats. After the colon in {value:spec} comes how to write the value. :>6 pads to six characters, right-aligned. :04X writes an int in hexadecimal, capital letters, padded with zeros to four digits. :08b writes it in binary, padded to eight digits. :, puts commas between thousands. Literals come in the same bases: 0x20AC and 8364 are the same int.

Code points run from 0 to 0x10FFFF: 1,114,112 places, of which about 150,000 hold a character in Unicode 15.1, the version Python 3.13 knows. The first 128 are the old ASCII table, so A is 65 in both.

The last two lines are the surprise. A str is a sequence of code points, and len counts code points, not what you see. The second café spells é as a plain e followed by a combining accent, U+0301, which the screen draws on the letter before it: same look, different string. The Hindi greeting नमस्ते reads as three syllables and is six code points, one of them (U+094D) a mark that joins स and त into one cluster. A tokenizer never sees letters. It sees code points, and then their bytes.

Analogy

Unicode is a vast catalogue with a numbered entry for every character: entry 8364 is the euro sign. It says nothing about how a number is written down; that is the encoding's job. Where it breaks: a catalogue entry is a thing you can pick up on its own. A code point is sometimes only part of what you see: an accent, a joining mark, or half of a flag, which is two code points side by side.

Bytes in Python

A code point can be as large as 1,114,111, and a byte holds at most 255. Python keeps the two apart: str is a sequence of code points, bytes a sequence of whole numbers from 0 to 255. To get bytes to look at, this section calls str.encode("utf-8"), Python's own encoder. Milestone M1 may not call it, because M1 is an encoder.

data = "café".encode("utf-8")  # Python's encoder, used here only to look
print(data, type(data).__name__)
print(len("café"), "characters,", len(data), "bytes")
print(data[0], data[3], data[-1])  # one byte: an int from 0 to 255
print(data[1:3])  # a slice of bytes: bytes again
print(list(data))
print(data.hex(" "))
print(hex(data[3]), bin(data[3]), f"{data[3]:08b}")

print(bytes([84, 101, 97]))  # bytes from a list of ints
print(b"\x54\x65\x61" == b"Tea")

pot = bytearray(b"tea")  # a bytearray can change; bytes cannot
pot[0] = ord("s")
pot.append(0x21)
print(pot, bytes(pot))

try:

Where a byte is a printable ASCII character, Python prints the character; any other byte prints as \x and two hex digits. So b'caf\xc3\xa9' is five bytes, and C3 A9 is the é. Indexing gives an int (data[0] is 99, the code of c); slicing gives bytes. .hex(" ") prints the bytes as most tools do, and :08b shows that C3, 195, is 11000011. bytes([84, 101, 97]) builds bytes from ints. A bytes value cannot change, like a str; a bytearray is the same sequence of ints, but you can assign to it and append to it, like a list.

Trap

data[0] == b"c" is False, and Python does not warn you: data[0] is the int 99, and an int never equals a bytes value. Compare an int with an int, data[0] == ord("c"), or a slice with bytes, data[0:1] == b"c". A for loop over bytes gives you ints, too.

Bits, shifts and masks

UTF-8 packs a code point into bytes a few bits at a time, so you need to handle the bits inside a number. Picture a byte as a row of eight light switches, worth 128, 64, 32, 16, 8, 4, 2 and 1 from left to right. Its value is the sum of the switches that are on: 11000011 is 128 + 64 + 2 + 1 = 195. Four switches make one hex digit (0 to F), so a byte is two hex digits: 1100 is C, 0011 is 3, and 195 is 0xC3.

  • Shift left, x << n, slides every bit n places left, with zeros coming in on the right. Each place doubles: 1 << 3 is 8.
  • Shift right, x >> n, slides them right; the n bits that fall off the end are lost.
  • And, x & m, keeps a bit only where both have it. With a mask, a number chosen for its pattern of ones, it keeps the bits under the ones and clears the rest: x & 0xFF keeps the lowest eight bits.
  • Or, x | m, switches on the mask's bits and leaves the others alone.

A screen colour is three bytes, red, green and blue, often kept side by side in one int: orange is 0xFF8800. Taking it apart and putting one together is all shifts and masks:

print(1 << 3, 0b1011 >> 1, bin(0b1011 >> 1))  # left doubles, right halves
print(f"{0b10110110 & 0b00001111:08b}")  # a mask keeps the bits where it has a 1

orange = 0xFF8800  # red FF, green 88, blue 00: three bytes in one int
print(orange, hex(orange), f"{orange:024b}")

red = (orange >> 16) & 0xFF  # move the red byte to the bottom, keep 8 bits
green = (orange >> 8) & 0xFF
blue = orange & 0xFF
print(red, green, blue)

teal = (0 << 16) | (128 << 8) | 128  # put three bytes back into one int
print(f"#{teal:06X}", teal)

# A field need not be a whole byte. RGB565 keeps a colour in 16 bits: red 5, green 6, blue 5.
print(bin((1 << 5) - 1), bin((1 << 6) - 1))  # a mask of n ones is (1 << n) - 1
pixel = 0xFC40  # orange again, in 16 bits
print(f"{pixel:016b}")
red5 = (pixel >> 11) & ((1 << 5) - 1)  # slide past green's 6 bits and blue's 5
green6 = (pixel >> 5) & ((1 << 6) - 1)  # slide past blue's 5
blue5 = pixel & ((1 << 5) - 1)
print(red5, green6, blue5)

print(1 << 5 - 1, (1 << 5) - 1)  # the trap: - is worked out before <<

To read green, shift right by 8 so that green lands in the lowest eight places, then mask with 0xFF to drop the red that came along above it. Putting a colour together is the same backwards: shift each byte up to its place and | them together. The three places do not overlap, so | never mixes them.

The second half drops the byte boundaries. Small screens often keep a colour in 16 bits, as RGB565: five bits of red at the top, six of green in the middle, five of blue at the bottom. Written out, orange is 11111 100010 00000. The fields no longer line up with hex digits or bytes, so 0xFF is the wrong mask; you need a mask with exactly as many ones as the field is wide. Here is how to make one. 1 << 5 is 100000, a one with five zeros after it, and one less than that is 11111, the way 1,000 − 1 is 999 on a counter that rolls back. So a mask of n ones is (1 << n) - 1: 31 for five bits, 63 for six. The shifts are counted the same way: red sits above 6 + 5 = 11 bits of other fields, so it is shifted right by 11. Red reads 31, the most five bits can hold: full red. Green reads 34 of a possible 63, a little over half, as 0x88 (136 of 255) was.

Trap

Python works out + and - before << and >>, so 1 << 5 - 1 is 1 << 4, 16, not the mask 31. Bracket every shift that sits next to arithmetic, and join bit fields with |. (x & m == v does mean (x & m) == v in Python, unlike in C, but write the brackets anyway.)

A mask can also test bits. "Is this switch on?" is & with a mask that has only that switch: the answer is 0 if it is off. "Do the top two switches read 01?" is & with 0b11000000, which keeps those two and clears the other six, compared with 0b01000000.

The UTF-8 table

Now the encoding. A code point can need 21 bits (0x10FFFF is 21 binary digits), and a byte holds 8. Four bytes for every character would waste three of every four on English and break every program that expects one byte per ASCII letter. UTF-8 uses one to four bytes, as few as each code point needs, and leaves ASCII exactly as it was. Here are the bits of five characters, with Python's encoder used once more only to look:

for character in ["A", "é", "€", "你", "🙂"]:
    data = character.encode("utf-8")  # Python's encoder, used only to look
    bits = " ".join(f"{byte:08b}" for byte in data)
    code = f"U+{ord(character):04X}"
    print(f"{code:7}  {len(data)}  {bits:35}  {character}")

U+4F60   3  11100100 10111101 10100000           你
U+1F642  4  11110000 10011111 10011001 10000010  🙂

Look at how each byte starts. A one-byte character starts with 0. The first byte of a two-byte character starts with 110, of three bytes 1110, of four 11110. Every byte after the first starts with 10. Those leading bits are fixed; the bits after them, the payload, are the code point's bits. The whole rule, with an x for each payload bit:

Code pointsBytesByte 1Byte 2Byte 3Byte 4Payload bits
U+0000 to U+007F10xxxxxxx7
U+0080 to U+07FF2110xxxxx10xxxxxx5 + 6 = 11
U+0800 to U+FFFF31110xxxx10xxxxxx10xxxxxx4 + 6 + 6 = 16

The x boxes hold the code point written in binary with exactly as many bits as its row has boxes (7, 11, 16 or 21), with zeros in front, shared out over the boxes from left to right. Check it on é above: 0xE9 is eight bits, and written in eleven it is 00011 101001, which are the boxes of 11000011 10101001. Without the zeros in front, the bits would land in the wrong boxes. The box counts set the ranges: 7 bits reach 0x7F, 11 reach 0x7FF, 16 reach 0xFFFF. So a byte that starts with 0 is a whole ASCII character; one that starts with 11 is the first byte of a longer character and says how long; one that starts with 10 is a continuation byte, and never starts anything.

Analogy

A UTF-8 character is a short train. The engine, the first byte, has a sign that says how many carriages follow: 110 for one, 1110 for two, 11110 for three. Every carriage carries the sign 10, so nobody mistakes a carriage for an engine, and if you step onto the platform halfway along, you walk back past the carriages to find the engine. Where it breaks: a real engine carries no cargo. A UTF-8 engine carries some of the code point too, and fewer bits than a carriage: three to five, against six.

That last property makes UTF-8 self-synchronising: from any byte you can tell whether a character starts there, without reading what came before. Some byte values never appear at all. 0xF5 to 0xFF would start a code point above 0x10FFFF. 0xC0 and 0xC1 would start a two-byte spelling of a code point below 0x80, and UTF-8 allows only the shortest form.

Surrogates, and text that is not text

Not every code point is a character. The 2,048 from U+D800 to U+DFFF are surrogates, kept for UTF-16, an older encoding with two bytes per unit that reaches code points above U+FFFF by writing a pair of them. A surrogate alone is half of a pair, not a character, and UTF-8, which writes U+1F642 directly in four bytes, has no bytes for one. Python lets a str hold one anyway (a broken JSON escape can produce it), but its encoder refuses it, and the docstring of utf8_encode says yours must raise ValueError. The other direction has its own trouble: not every list of bytes is UTF-8.

half = chr(0xD800)  # a surrogate: Python lets a str hold one
print(len(half), hex(ord(half)))
try:
    half.encode("utf-8")
except UnicodeEncodeError as error:
    print("encode:", error.reason)

for data in [b"\xff", b"\x80", b"\xe4\xbd", b"\xc0\xaf", b"\xed\xa0\x80"]:
    try:
        data.decode("utf-8")
    except UnicodeDecodeError as error:
        print(f"{data!s:16} {error.reason}")

Each byte string breaks one rule. FF never appears in UTF-8. 80 is a continuation byte with no first byte. E4 BD promises three bytes and has two. C0 AF is an overlong spelling of /, refused because two spellings of one character let text slip past a check that looks for the short one. ED A0 80 is the table applied blindly to U+D800. (error.reason is the short message; !s turns data into a str so that :16 can pad it.)

So there is a gap on each side. Every str has UTF-8 bytes except one that holds a lone surrogate, and many lists of bytes are the UTF-8 of no str. A byte-level tokenizer lives on the bytes side, which is why no text is unknown to it: whatever the text, its bytes are numbers from 0 to 255, and each is a token.

When bytes are not a whole character

The gap matters as soon as tokens come out one at a time. 水, "water", is the bytes E6 B0 B4. From the oracle: GPT-2 writes it as two tokens, ids 36365 and 112, which stand for E6 B0 and B4. A model that has produced the first and not yet the second holds two bytes that are not a character. Decoding them on their own fails, as E4 BD did in not_text.py: "unexpected end of data". (bytes.decode can be told to do something other than raise; chapter 3 takes its errors= argument apart.) A program that streams a reply needs a decoder that waits instead:

import codecs

water = "水".encode("utf-8")
first, last = water[:2], water[2:]  # where GPT-2's tokens cut it
print(water, first, last)
print("joined:", (first + last).decode("utf-8"))

decoder = codecs.getincrementaldecoder("utf-8")()  # holds back an unfinished character
for piece in [first, last, b" is water"]:
    print(repr(decoder.decode(piece)))

b'\xe6\xb0\xb4' b'\xe6\xb0' b'\xb4'
joined: 水
''
'水'
' is water'

An incremental decoder keeps unfinished bytes between calls. Given E6 B0 it returns nothing yet, the empty string; given B4 it returns the whole 水; given whole characters it passes them straight through. It can, because of the table: E6 starts with 1110, so it knows two more bytes are owed after it, and it waits for exactly that many.

How many bytes a script takes

The table also fixes how many bytes a text takes, and a byte-level tokenizer starts from that number. The same greeting in eight scripts:

In a real engine

Both halves of this chapter meet in a serving engine. Because GPT-2's tokenizer, and later models' byte-level tokenizers, start from the 256 bytes, every prompt can be tokenized: no input is refused as unknown. And because a token is bytes, a reply streamed token by token can stop in the middle of a character, as 水 did above. vLLM turns the ids it generates back into text a few tokens at a time as it streams, and when the newest bytes do not yet make a whole character, its detokenizer holds them back until the rest arrives, so the reader never sees half a character. That is half_a_character.py's incremental decoder, in a server.

Check yourself

Why does GPT-2's tokenizer start from the 256 bytes, rather than from words or characters?

Answer

Every text is a list of bytes, and there are only 256 byte values, so a vocabulary that starts with all of them encodes any text in any script with nothing unknown. Words always leave some word out; characters need a table for over a million code points, most never seen in training, and still miss next year's.

How many code points and how many UTF-8 bytes does "naïve" have, when its ï is the single code point U+00EF?

Answer

Five code points and six bytes. U+00EF is between U+0080 and U+07FF, so it takes two bytes; the four ASCII letters take one each.

You meet the byte 0b10110001 in the middle of some UTF-8. What do you know about it, and how many bits of a code point does it carry?

Answer

It starts with 10, so it is a continuation byte: the second, third or fourth byte of a character, never the first. It carries six payload bits, 110001.

The first byte of a character is 0xF0. How many bytes does the character take, and how many payload bits does it have?

Answer

0xF0 is 11110000; the prefix 11110 means four bytes. The payload is 3 bits in the first byte and 6 in each of the other three: 21.

Work out (0x3C4A >> 8) & 0x0F on paper.

Answer

0x3C4A >> 8 drops the lowest byte and leaves 0x3C. & 0x0F keeps its lowest hex digit: 0xC, which is 12.

Why can a Python str hold chr(0xD800), when UTF-8 cannot encode it?

Answer

A str is a sequence of code points, and 0xD800 is a code point. But it is a surrogate, half of a pair that only UTF-16 uses, not a character. UTF-8 writes every code point directly and never needs pairs, so it has no bytes for a lone half.

A server is streaming a reply, and the last token ended after the bytes E6 B0. What should it send the reader now, and why?

Answer

Nothing yet for those two bytes. E6 starts with 1110, so the character needs one more byte. Decoding now would raise "unexpected end of data". Holding the bytes back, as an incremental decoder does, sends the whole character when the next token brings its last byte.
