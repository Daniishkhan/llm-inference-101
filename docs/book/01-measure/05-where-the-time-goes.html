The problem: 1.2 milliseconds, but where?

By the end of this module your harness will tell you that a function takes 1.2 ms at p50. That is a fact about the whole function, and it does not say what to change. Nine of its ten lines might cost almost nothing while the tenth costs nearly all of it; or the cost might be spread evenly, and no single change will help. Before you rewrite anything, you want to know which.

A profiler answers "where did the time go?" without you editing the function. This chapter shows how one piece of Python can watch another, because Milestone 6 asks you to build such a watcher.

Two ways to watch a program

A tracing profiler is told about every event as it happens: a function starts, a line is about to run, a function returns. Its counts are exact, and it pays for that with some work at every event, of which a busy program has millions.

A sampling profiler is told nothing. Every few milliseconds it looks at the program and writes down where it is. After a few thousand looks it has a statistical picture: if the program was inside one function in 80 of 100 samples, that function takes about 80% of the time. It misses events, but between samples it costs nothing.

Analogy

A factory floor. Tracing is a stopwatch on every worker, clicked at every start and stop of every task. Sampling is a photographer on the balcony who photographs the whole floor every ten milliseconds; afterwards you count the photos that show each worker at each machine. Where it breaks: a real stopwatch does not slow the worker down, but a tracer does, because it runs on the same processor, in between the program's own steps. And the camera is not free either: py-spy, the sampler at the end of this chapter, briefly pauses the program for each sample unless you ask it not to.

First principle

A profiler can only report what it can see, and seeing has a cost. A tracer sees every event and pays at every event; a sampler sees a few snapshots and pays only for those. Whichever you use, the program you measure is not quite the program that runs without the profiler.

cProfile on two Fibonaccis

Python ships with a tracing profiler, cProfile, written in C to keep it cheap. Here is a toy for it: two ways to compute the 25th Fibonacci number (each is the sum of the two before it: 0, 1, 1, 2, 3, 5, 8, and so on). The slow way calls itself twice for every number, recomputing the same small numbers over and over; the fast way walks forward once with two variables.

def fib_slow(n):
    if n < 2:
        return n
    return fib_slow(n - 1) + fib_slow(n - 2)


def fib_fast(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a


print("slow:", fib_slow(25))
print("fast:", fib_fast(25))

slow: 75025
fast: 75025

Reading ncalls, tottime and cumtime

After your program's own output come a summary line and one row per function:

  • ncalls: how many calls. 242785/1 means 242,785 in all, of which 1 was a primitive call, one that did not come from the function itself; the rest were fib_slow calling itself.
  • tottime: seconds spent in the function's own code, over all its calls, not counting the functions it called.
  • cumtime: seconds from entering the function to leaving it, everything it called included (for a recursive function, from the outermost call, so nothing is counted twice).
  • percall: the first is tottime divided by ncalls, the second cumtime divided by the primitive calls.
  • filename:lineno(function): where the function is defined. Rows in braces, such as {built-in method builtins.print}, are functions written in C.

The top level of your file, <module>, has a tottime of 0.000 and a cumtime of 0.019: its own lines cost nothing, and everything happened in what they called. fib_slow is the opposite, its two times equal, because it calls nothing but itself. fib_fast rounds to 0.000: same answer, 242,785 calls against 1.

Sorting by cumtime (-s cumulative) puts the big containers on top, so you can walk down from "the whole program" to "this function". Sorting by tottime (-s tottime) puts on top the functions that do the work themselves.

You can also switch the profiler on and off inside a program, and print the table with pstats, the module that reads cProfile's records. This profiles one call, not the whole file:

import cProfile
import pstats


def fib_slow(n):
    if n < 2:
        return n
    return fib_slow(n - 1) + fib_slow(n - 2)


def fib_fast(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a


def both(n):
    return fib_slow(n), fib_fast(n)


profiler = cProfile.Profile()
profiler.enable()
both(25)
profiler.disable()

stats = pstats.Stats(profiler)
stats.strip_dirs().sort_stats("cumulative").print_stats(4)

cProfile counts functions, not lines

cProfile listens for two things only: a function starts, a function ends. That keeps it cheap, and it is also its limit. Here two lines both call sum, one on a thousand numbers and one on three million:

import cProfile
import pstats


def weigh_parcels():
    light = sum(range(1_000))
    heavy = sum(range(3_000_000))
    return light + heavy


profiler = cProfile.Profile()
profiler.enable()
weigh_parcels()
profiler.disable()
pstats.Stats(profiler).strip_dirs().sort_stats("cumulative").print_stats()

How tracing works: sys.settrace

The CPython interpreter runs your program one step at a time, and at certain moments it can stop, call a function of yours with a description of where it is, and carry on. sys.settrace(tracer) switches that on, where tracer takes three arguments, (frame, event, arg); sys.settrace(None) switches it off.

The event is a string that says what is happening:

  • "call": a Python function is starting; the frame is the new function's frame.
  • "line": the interpreter is about to run a new line of the frame's code.
  • "return": the function is about to return. arg is the value it returns, or None if it is leaving because of an exception.
  • "exception": an exception has been raised in this frame. arg is a tuple of the exception's type, the exception and its traceback.

(A fifth, "opcode", for each bytecode instruction, is off unless you ask for it; bytecode is in chapter 6.)

A frame is the interpreter's record of one running call: its code, its current line, its local variables and its caller. Every call gets a new frame, so a recursion 25 calls deep has 25 frames alive at once. The attributes you need:

  • frame.f_code: the function's compiled code. f_code.co_name is the function's name and f_code.co_filename is the file it was defined in.
  • frame.f_lineno: the line the frame is on now, numbered as in the file.
  • frame.f_back: the caller's frame, or None at the very top. Following it again and again walks the call stack, which is how a traceback is built.

The function you pass to sys.settrace is the global tracer. It is called with "call" events only, once per new frame, and what it returns decides that frame's fate. A function becomes the frame's local tracer, which receives the frame's "line", "return" and "exception" events. None means the frame is not traced at all. The local tracer, in turn, returns the function to use for the frame's next event, normally itself.

A tracer that prints every event

The simplest tracer prints what it is told and returns itself, so that it is both the global and the local tracer. Point it at a three-line function:

import sys


def brew(cups):
    water = cups * 250
    leaves = cups * 3
    return water, leaves


def show(frame, event, arg):
    name = frame.f_code.co_name
    print(f"{event:<7} {name:<6} line {frame.f_lineno}  arg={arg!r}")
    return show


sys.settrace(show)
brew(2)
sys.settrace(None)
print("done")

call    brew   line 4  arg=None
line    brew   line 5  arg=None
line    brew   line 6  arg=None
line    brew   line 7  arg=None
return  brew   line 7  arg=(500, 6)
done

The call event reports line 4, the def line: the function has started, but none of its body has run. Then a line event for each of lines 5, 6 and 7, and return on line 7 with the return value as arg. print made no events, because it is written in C and sys.settrace reports only Python frames. Nor did the file's own lines after brew(2): that frame was already running when the tracer was installed, and only frames that start later are offered to it.

Now an exception. careful calls risky, which fails to turn "tea" into a number:

import sys


def risky(text):
    number = int(text)
    return number * 2


def careful(text):
    try:
        return risky(text)
    except ValueError:
        return 0


def show(frame, event, arg):
    print(f"{event:<9} {frame.f_code.co_name:<7} line {frame.f_lineno}")
    return show


sys.settrace(show)
result = careful("tea")
sys.settrace(None)
print("result:", result)

Choosing which frames to trace

A tracer that returns itself for every frame traces everything, the standard library included. Usually you want one function or one file, and the global tracer is where you decide. Here the global and local tracers are separate functions, and the global one also looks one frame back to see who made the call:

import os
import sys


def boil(cups):
    return cups * 250


def brew(cups):
    water = boil(cups)
    leaves = cups * 3
    return water, leaves


def on_line(frame, event, arg):
    print(f"    {event:<6} line {frame.f_lineno}")
    return on_line


def on_call(frame, event, arg):
    code = frame.f_code
    caller = frame.f_back
    print(f"call {code.co_name} in {os.path.basename(code.co_filename)}", end="")
    print(f", called from {caller.f_code.co_name} line {caller.f_lineno}")
    if code.co_name == "brew":
        return on_line
    return None


sys.settrace(on_call)
brew(2)
sys.settrace(None)

call brew in choose_frames.py, called from <module> line 31
    line   line 10
call boil in choose_frames.py, called from brew line 10
    line   line 11
    line   line 12
    return line 12

on_call is offered both new frames. It returns on_line for brew, whose lines and return are then reported, and None for boil, which runs without line events. The f_back of boil's frame is brew's frame, on line 10, the line that made the call.

Two smaller facts: sys.settrace covers only the calling thread, and a frame is a live record whose f_lineno keeps changing, so to remember a line, copy the number out.

Worked example: counting calls per function

Now a useful tracer: how many times is each function called? It needs only "call" events, so it returns None for every frame and never asks for a line. Its counts live in a dictionary from a function's name to a number.

Python you need

counts.get(key, 0) is the value under key, or 0 if there is none, so counts[key] = counts.get(key, 0) + 1 adds one either way. A dictionary keeps its keys in the order they were first added. And try/finally: the finally block runs however the try block ends, normally, by return or by an exception, which then carries on to the caller.

try:
    print("opening the shop")
    raise ValueError("no change in the till")
finally:
    print("locking the door")

Its output, with the start of the path shortened: the finally block ran, and then the exception went on.

opening the shop
locking the door
Traceback (most recent call last):
  File "/…/scratch/finally_runs.py", line 3, in <module>
    raise ValueError("no change in the till")
ValueError: no change in the till

import sys


def fib_slow(n):
    if n < 2:
        return n
    return fib_slow(n - 1) + fib_slow(n - 2)


def fib_fast(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a


def both(n):
    return fib_slow(n), fib_fast(n)


calls = {}


def count_call(frame, event, arg):
    name = frame.f_code.co_name
    calls[name] = calls.get(name, 0) + 1
    return None  # no local tracer: this frame's lines are not traced


old = sys.gettrace()
sys.settrace(count_call)
try:
    both(15)
finally:
    sys.settrace(old)

for name, count in calls.items():  # in the order of each first call
    print(f"{name:<9} {count:>6,} calls")
print("tracer back to:", sys.gettrace())

both           1 calls
fib_slow   1,973 calls
fib_fast       1 calls
tracer back to: None

One call of both, one of fib_fast, 1,973 of fib_slow, as cProfile would say. Copy the program's pattern whenever you install a tracer:

  1. Remember the tracer that was there before: sys.gettrace() returns the current global tracer, or None.
  2. Install yours.
  3. Run the code you want to watch inside try.
  4. In finally, put back what you remembered.

The last line shows the tracer back to what it was, None.

Put the old tracer back

Two things go wrong without that ceremony. The first is an exception: the code being watched raises, and the line that would switch the tracer off never runs.

import sys

calls = {}


def count_call(frame, event, arg):
    name = frame.f_code.co_name
    calls[name] = calls.get(name, 0) + 1
    return None


def parse_order(text):
    return int(text)


def later_work():
    return "nobody asked to trace this"


try:
    sys.settrace(count_call)
    parse_order("two")  # raises ValueError
    sys.settrace(None)  # never runs
except ValueError as error:
    print("caught:", error)

later_work()
print("still tracing:", sys.gettrace() is not None)
print("calls counted:", calls)

caught: invalid literal for int() with base 10: 'two'
still tracing: True
calls counted: {'parse_order': 1, 'later_work': 1}

The program carried on, and so did the tracer: it counted later_work, which nobody asked it to watch, and it slows every call from here on. In a test suite, the next test runs under a tracer it knows nothing about.

The second is someone else's tracer. Debuggers and coverage tools are tracers too, and there is one global tracer at a time. sys.settrace(None) does not mean "remove mine"; it means "remove whatever is there". Here outer, a stand-in for a debugger, is tracing when a helper installs its own:

import sys

seen_by_outer = []


def outer(frame, event, arg):
    # Stands in for a tool that was already tracing: a debugger, or a coverage counter.
    seen_by_outer.append(frame.f_code.co_name)
    return None


def inner(frame, event, arg):
    return None


def step_one():
    return 1


def step_two():
    return 2


def rude():
    sys.settrace(inner)
    step_one()
    sys.settrace(None)  # switches off whoever was tracing before


def polite():
    old = sys.gettrace()
    sys.settrace(inner)
    try:
        step_one()
    finally:
        sys.settrace(old)  # puts back whoever was tracing before


for helper in (rude, polite):
    seen_by_outer.clear()
    sys.settrace(outer)
    helper()
    step_two()
    sys.settrace(None)
    print(f"{helper.__name__:<6} outer saw: {seen_by_outer}")

rude   outer saw: ['rude']
polite outer saw: ['polite', 'step_two']

After rude, the outer tracer had been switched off and never saw step_two; after polite, it was back and did. (It missed step_one both times, while the inner tracer was installed: one at a time is a real limit.)

Trap

Never end with a bare sys.settrace(None), and never switch back without a finally. Remember sys.gettrace() first and restore it in finally: the one shape that is safe both when the code raises and when another tool was tracing before you.

What tracing costs

A tracer is a Python function call at each event, and calls are what fib_slow showed to be expensive. This times two kinds of work once each way, with time.perf_counter_ns from chapter 1: fib_slow(25), almost all calls, and a loop that computes the 25th Fibonacci number ten thousand times, almost all lines. Each runs with no tracer, with the call counter, and with a tracer that asks for every event and does nothing with it.

import sys
import time


def fib_slow(n):
    if n < 2:
        return n
    return fib_slow(n - 1) + fib_slow(n - 2)


def fib_fast_many(times):
    total = 0
    for _ in range(times):
        a, b = 0, 1
        for _ in range(25):
            a, b = b, a + b
        total += a
    return total


calls = {}


def count_call(frame, event, arg):
    name = frame.f_code.co_name
    calls[name] = calls.get(name, 0) + 1
    return None


def ignore_everything(frame, event, arg):
    return ignore_everything  # asks for every event of every frame, and does nothing with it


def run_once(work, tracer):
    old = sys.gettrace()
    sys.settrace(tracer)
    try:
        start = time.perf_counter_ns()
        work()
        return time.perf_counter_ns() - start
    finally:
        sys.settrace(old)


jobs = [
    ("fib_slow(25)", lambda: fib_slow(25)),
    ("fib_fast_many(10_000)", lambda: fib_fast_many(10_000)),
]
for label, work in jobs:
    plain = run_once(work, None)
    counted = run_once(work, count_call)
    every = run_once(work, ignore_everything)
    print(label)
    print(f"  no tracer:     {plain / 1e6:6.1f} ms")
    print(f"  call counter:  {counted / 1e6:6.1f} ms  {counted / plain:5.1f} times")
    print(f"  every event:   {every / 1e6:6.1f} ms  {every / plain:5.1f} times")

One run on the M5; yours will differ:

fib_slow(25)
  no tracer:        4.4 ms
  call counter:    23.7 ms    5.4 times
  every event:     25.8 ms    5.9 times
fib_fast_many(10_000)
  no tracer:        2.5 ms
  call counter:     4.6 ms    1.9 times
  every event:     11.6 ms    4.7 times

Three things to read. On call-heavy work even the call counter costs about five times: each of 242,785 calls also runs count_call. On the loop, asking for every event costs nearly five times, while the call counter costs under two. And the call counter slowed the loop at all, though it never asked for a line: since Python 3.12, sys.settrace is built on the newer monitoring machinery (next section), and while any tracer is installed the interpreter checks at each line whether the frame has a local tracer. Quick, but not free.

The lesson for any tracer, yours in Milestone 6 included: what it reports is real, about a program running several times slower than normal. It is good at "which part is slow compared with the others", and poor at "how many milliseconds without me". For that, go back to the harness.

sys.monitoring, the newer API

Python 3.12 added sys.monitoring. Instead of one global function that hears everything, a tool registers for the events it wants, and the interpreter switches on only those. A callback can also answer "do not tell me about this spot again", and the interpreter stops reporting that event there, so a tool stops paying for what it has already seen. It was designed for debuggers, coverage tools and profilers cheap enough to leave on, and cProfile now uses it. This module uses sys.settrace; a line timer on sys.monitoring is one of its stretch goals.

Sampling a running program: py-spy

Everything so far traces from inside: the program installs the tracer itself. That does not help with a server that has run for an hour and just became slow. You cannot add a tracer without restarting it, and one that slows it fivefold would change what you are looking at.

A sampling profiler such as py-spy works from outside. It is a separate program that reads the running process's memory, finds the interpreter's frames, and writes down each thread's call stack, 100 times a second by default. The program is not changed or restarted. You do not need py-spy this module and it is not installed; these are the commands (12345 stands for the process id that ps or Activity Monitor shows; on macOS py-spy needs sudo):

$ sudo py-spy dump --pid 12345
$ sudo py-spy top --pid 12345
$ sudo py-spy record -o profile.svg --pid 12345

dump prints every thread's stack once: "what is it doing right now?", for a server that seems stuck. top is a live table of the functions seen most often. record samples until Ctrl-C and draws a flame graph: one bar per function, as wide as its share of the samples, stacked on the function that called it.

The trade is the one from the start of the chapter. py-spy is cheap and needs no change, but it reports shares of samples, not exact counts, and something shorter than one sampling interval may never appear. Use the tracer on a function you can call in a test; use the sampler on a program you cannot stop.

In a real engine

In vLLM and SGLang, most of a forward pass runs on the GPU, where neither of this chapter's tools can see. For that there is the PyTorch profiler (torch.profiler), which records the operators the Python code launched and the GPU kernels that ran for them, with each one's duration, and can save it as a timeline for a trace viewer. The scheduler, the tokenizer and the API layer are ordinary Python, and for a server already running under load, a sampling profiler such as py-spy is the usual way to see where its threads spend their time.

Check yourself

In a cProfile table, a function has tottime 0.001 and cumtime 0.950. What does that tell you, and where do you look next?

Answer

Nearly all the time is in functions it calls, not in its own code. Look below it, sorted by cumtime, for the callee behind the 0.95 s, or sort by tottime.

What does ncalls of 1973/1 mean?

Answer

1,973 calls in all, of which 1 was a primitive call, one that did not come from the function itself. The other 1,972 were the function calling itself: it is recursive.

Your global tracer returns None for every frame. Which events does it receive, and which does it never see?

Answer

Only "call" events, one per new Python frame. Because no frame gets a local tracer, it never sees "line", "return" or "exception" events.

Inside a tracer, how do you find the name of the function that made the call you are being told about, and the line it made it from?

Answer

frame.f_back.f_code.co_name and frame.f_back.f_lineno. f_back is the caller's frame, and its current line is the line of the call.

A colleague's helper ends with sys.settrace(None). Name two ways this goes wrong.

Answer

If the code before it raises, it never runs and the tracer stays installed. And if a debugger or coverage tool was tracing before, None switches that off too.

Your call counter made fib_slow(25) about five times slower. Does that mean the counts are wrong?

A web server has been slow for ten minutes and you may not restart it. Tracer or sampler, and why?

Answer

A sampler such as py-spy: it attaches from outside, needs no change and costs little. A tracer would need installing from inside and would slow the server several times over.
