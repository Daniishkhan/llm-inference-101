How the drills work

A drill is a small, classic problem that you solve by hand against a clock: a statement in a docstring, a function whose body says TODO(you), and a test file beside it. Interviews are made of problems like these, and so is a lot of the code inside an inference engine: a dict that counts, a stack that checks nesting, a window that slides along a stream of numbers. The point of a drill is not the answer, which is on a thousand websites. The point is that your hands produce it, from an empty function body, in a fixed time, while you say what you are doing.

The full rules are in docs/methodology.md, under "Drills and the ledger". In short:

  • Hands only. No agent, no completion, no paste. The Python docs are allowed, and every lookup is written down: the list of lookups is the next morning's warm-up.
  • A time box. Each stub's docstring ends with its time box. Start a timer when you open the stub. At the bell, ask Claude for one rung of the hint ladder, or log a timeout.
  • Out loud. Say what you are doing as you do it. An interviewer grades what they hear, and saying a plan out loud is how you notice that it has a hole.
  • The ledger. Every attempt gets a row in ledger.md: the minutes, the highest rung you used, the number of lookups, and the result (green, green+hint or timeout). The pattern column is filled in after you solve it: naming the pattern is part of the exercise.
  • Two redos. Two days and seven days after the first attempt, empty the function (git keeps your first version) and type it again, cold. A problem you cannot redo is not solved yet.
  • No reveal after a timeout. A timed-out drill stays open. It comes back at its +2 day redo, with the rungs you have not used yet.
  • One commit per solved drill, with the minutes in the message: pair_with_sum: 11 min, no hints.

Run one drill's tests from the repository root:

$ uv run pytest drills/00-diagnostic/test_run_length.py
$ uv run pytest drills/01-arrays-hashing

Drills never run in CI: a redo empties a function, and an empty function is meant to be red.

The hint ladder in this chapter

Each drill below has three rungs, folded: Rung 1, where to look (a test to read, a line of the docstring), Rung 2, the idea in words (plain English, no code), and Rung 3, the shape (which data structure, which loop goes where, what to test first). Open one rung at a time, and only at the bell or when you are truly stuck; write the rung in the ledger. Rung 4, the same mechanism on a different problem, you get from Claude by asking for it. Remembering what you have seen

A surprising number of problems have the same core: as you walk through the input once, you need to know whether you have met something before, or how many times, or where. Without a memory, the only way to answer "have I seen this word before?" is to walk back over everything behind you, and that walk gets longer with every step. With a set (which remembers only that you saw a thing) or a dict (which remembers a value for each thing: a count, a position), the question costs the same small amount of time however much you have seen.

First principle

A set or a dict does not search. It turns the key into a number, its hash, and uses that number to jump to one slot of a table in memory. That is why word in seen takes about the same time with ten words in seen as with a million, and why only things that cannot change (strings, numbers, tuples) can be keys: if a key could change after it was stored, its hash would change, and the slot it was filed under would be the wrong one.

Two small questions about text: which word is the first to appear a second time, and how many times does each letter appear?

def first_repeated_word(sentence):
    seen = set()
    for word in sentence.lower().split():
        if word in seen:
            return word
        seen.add(word)
    return None


def letter_counts(word):
    counts = {}
    for letter in word:
        counts[letter] = counts.get(letter, 0) + 1
    return counts


print(first_repeated_word("The cat saw the dog chase the cat"))
print(first_repeated_word("every word here is new"))
print(letter_counts("banana"))
print(letter_counts(""))

the
None
{'b': 1, 'a': 3, 'n': 2}
{}

first_repeated_word asks the set before it adds to it. If it added first, every word would be "seen" the moment it arrived, and the first word would always be the answer. In letter_counts, counts.get(letter, 0) reads the count so far, or 0 for a letter met for the first time, so one line handles both cases. The dict comes back in the order the letters were first met: a dict keeps its keys in insertion order (since Python 3.7, a promise of the language).

Analogy

A cloakroom. You hand in a coat and get a ticket with a number; the attendant goes straight to that hook, never along the rail. The hook number is the hash. Where it breaks: two coats can get the same hook number (a collision), and then the attendant has to check a few coats. Python's tables are kept less than two-thirds full so that this stays rare, which is why "about the same time" is an average, not a promise.

A wider version: a dict that remembers where each word was last seen, so that a repeat can say how far back its twin was.

sentence = "to be or not to be that is the question to ask"

last_seen = {}
for position, word in enumerate(sentence.split()):
    if word in last_seen:
        gap = position - last_seen[word]
        print(f"{word!r} at {position}: seen {gap} words earlier")
    last_seen[word] = position

print(last_seen)

'to' at 4: seen 4 words earlier
'be' at 5: seen 4 words earlier
'to' at 10: seen 6 words earlier
{'to': 10, 'be': 5, 'or': 2, 'not': 3, 'that': 6, 'is': 7, 'the': 8, 'question': 9, 'ask': 11}

Again the order inside the loop matters: look up first, then store. Storing first would overwrite the old position with the new one before you had used it, and every gap would come out as 0.

Python you need

collections.Counter is a dict made for counting: give it anything you can loop over and it counts the items. A missing key reads as 0 instead of raising KeyError.

from collections import Counter

A Counter prints its biggest counts first, and among equal counts it keeps the order of first appearance ("i" before "s"). It does not order them alphabetically.

In a real engine

vLLM's prefix cache is this pattern at its centre. Each full block of a prompt's tokens gets a hash, built from the tokens and the hash of the block before it, and the block pool (vllm/v1/core/block_pool.py) keeps a dict from that hash to the cached block. A new request that starts with the same system prompt looks its blocks up and skips their computation. You build the same thing in Module 11.

Grouping by a key into a dict of lists

Counting tells you how many of each kind there are. Grouping keeps the things themselves: every item goes into the list of its kind. The shape is a dict whose keys are the kinds and whose values are lists. The whole skill is choosing the key: a value you can compute from one item alone, which is the same for every item that belongs together and different for items that do not.

Fruit, grouped by the length of the name:

words = ["fig", "apple", "kiwi", "pear", "plum", "banana", "date", "lime"]

by_length = {}
for word in words:
    if len(word) not in by_length:
        by_length[len(word)] = []
    by_length[len(word)].append(word)

print(by_length)
print(list(by_length.values()))

{3: ['fig'], 5: ['apple'], 4: ['kiwi', 'pear', 'plum', 'date', 'lime'], 6: ['banana']}
[['fig'], ['apple'], ['kiwi', 'pear', 'plum', 'date', 'lime'], ['banana']]

One pass over the words, and each word does one lookup and one append. Because a dict keeps insertion order, the groups come out in the order of the first word of each group (3, then 5, then 4), and inside a group the words keep the order they arrived in. Nothing was sorted; the order is a side effect of walking the input once from the front.

The if ... not in ... step, which makes an empty list the first time a key appears, is so common that the standard library has a dict that does it for you. A defaultdict(list) calls list() to make the missing value whenever you read a key that is not there yet:

from collections import defaultdict

words = ["pear", "apple", "plum", "avocado", "banana", "peach", "apricot"]

by_first_letter = defaultdict(list)
for word in words:
    by_first_letter[word[0]].append(word)

for letter, group in by_first_letter.items():
    print(letter, group)
print(len(by_first_letter), "groups for", len(words), "words")

p ['pear', 'plum', 'peach']
a ['apple', 'avocado', 'apricot']
b ['banana']
3 groups for 7 words

A set for constant-time membership

"Is this number in my collection?" is a question with two very different prices. A list answers it by looking at its items one by one until it finds a match or runs out: for an absent number, that is every item. A set answers it with one hash and one jump. If you ask once, the difference does not matter. If you ask once for every item of the input, the list version does about n times n steps, and the set version about n.

Which numbers from 1 to n are missing from a list?

def missing(numbers, n):
    present = set(numbers)
    return [k for k in range(1, n + 1) if k not in present]


print(missing([3, 7, 1, 2, 8, 4, 5], 10))
print(missing([2, 2, 2], 3))
print(missing([], 2))

[6, 9, 10]
[1, 3]
[1, 2]

Building the set costs one pass over the numbers. After that, each of the n questions costs about the same small amount, so the whole function is proportional to n plus the length of the list. Repeats vanish on the way in ([2, 2, 2] becomes the set {2}), which is usually what you want when the question is only "is it there?".

How big is the difference? One lookup of an absent number, timed in a list and in a set of 100,000 numbers. One run on the M5; yours will differ:

import time

numbers = list(range(100_000))
as_set = set(numbers)
absent = -1  # never there: the worst case for a list

start = time.perf_counter_ns()
for _ in range(200):
    absent in numbers
list_ns = (time.perf_counter_ns() - start) / 200

start = time.perf_counter_ns()
for _ in range(200):
    absent in as_set
set_ns = (time.perf_counter_ns() - start) / 200

print(f"list: {list_ns:12,.0f} ns per lookup")
print(f"set:  {set_ns:12,.0f} ns per lookup")
print(f"the set is about {list_ns / set_ns:,.0f} times faster here")

list:      199,697 ns per lookup
set:            19 ns per lookup
the set is about 10,535 times faster here

Thousands of times faster at this size, and the gap grows with the size of the list, because the list's price grows and the set's does not. Chapter 3 (Partition and select) puts names on these growth rates: the list lookup is O(n), the set lookup is O(1) on average.

Predict, then measure: what does the list line print if absent is 0 instead of -1? And if it is 99_999?

With 0 the list finds it at the first item, so the list is about as fast as the set (tens of nanoseconds). With 99_999 it is the last item, and the list costs about as much as for an absent number. A list's price depends on where the item is; a set's does not. That is the difference between the best case and the worst case, and benchmarks that only try the best case lie.

Runs in a sequence

Some questions are about neighbours: is each value the same as the one before, bigger, smaller? A stretch of neighbours that agree is a run. The pattern is to walk the sequence once, compare each item with the one before it, and keep a little state about the run you are in. The traps are always at the edges: the first item has nobody before it, and when the sequence ends, the run you were in ends too, without anything telling you.

A temperature series, read once an hour. How many times does it change direction, from rising to falling or back?

temperatures = [12, 14, 15, 15, 13, 11, 12, 16, 16, 14]

changes = 0
previous = 0  # +1 rising, -1 falling, 0 for "no direction yet"
for before, after in zip(temperatures, temperatures[1:]):
    if after == before:
        continue  # a flat step has no direction: skip it
    direction = 1 if after > before else -1
    if previous != 0 and direction != previous:
        changes += 1
    previous = direction

print(changes, "changes of direction")

3 changes of direction

Up to 15, a flat hour, down to 11, up to 16, a flat hour, down to 14: three turns. Two decisions make it right. The flat steps are skipped, so that 15, 15 is neither a turn nor a run of its own. And previous starts at 0, meaning "no direction yet", so that the first real step is never counted as a change.

Python you need

zip(xs, xs[1:]) pairs every item with the one after it. The slice xs[1:] is the list without its first item, and zip stops at the shorter of the two, so the last item is never paired with nothing.

readings = [12, 14, 15]
print(list(zip(readings, readings[1:])))
print(list(zip([12], [])))

[(12, 14), (14, 15)]
[]

A list of one gives no pairs at all, which is often exactly the edge case you would otherwise have to write by hand.

A wider version, with positions instead of zip: where are the peaks and the troughs?

def turning_points(series):
    """(position, "peak" or "trough") wherever the series changes direction."""
    points = []
    previous = 0
    for i in range(1, len(series)):
        if series[i] == series[i - 1]:
            continue
        direction = 1 if series[i] > series[i - 1] else -1
        if previous != 0 and direction != previous:
            points.append((i - 1, "peak" if previous == 1 else "trough"))
        previous = direction
    return points


temperatures = [12, 14, 15, 15, 13, 11, 12, 16, 16, 14]
print(turning_points(temperatures))
print(turning_points([1, 2, 3]))
print(turning_points([5]))

[(3, 'peak'), (5, 'trough'), (8, 'peak')]
[]
[]

A turn is found one step late: you only know that position 3 was a peak when position 4 turns out lower. That is normal for runs, and it is why the end of the input needs thought: a run that is still going when the input stops has not been "finished" by any comparison inside the loop.

A stack

A stack is a pile where you only touch the top: you put a thing on top (push) and take the top thing off (pop). The last thing in is the first thing out. You need one whenever the most recent unfinished business must be finished first: nested brackets, an undo button, the calls of a running program (each call waits for the one it made to return, which is why Python's error reports are called a stack trace).

Analogy

A pile of plates in a canteen: you take from the top and put back on the top, never from the middle. Where it breaks: a real pile is easy to lift and look under. A stack in a program gives you only the top; if you need to look at the rest, you have chosen the wrong structure.

In Python a list is a stack: append pushes onto the end, pop() takes from the end, and both are cheap. Popping an empty list raises an error:

The worked example is reverse Polish notation (RPN), a way to write arithmetic without brackets: the operator comes after its two numbers. 3 4 + 2 * means "3 plus 4, then times 2". To evaluate it, read the tokens from left to right; push every number; at an operator, pop two numbers, combine them, and push the result. The program prints the stack after each token, so you can watch it grow and shrink:

def evaluate_rpn(expression):
    stack = []
    for token in expression.split():
        if token in ("+", "-", "*", "/"):
            if len(stack) < 2:
                raise ValueError(f"{token!r} needs two numbers, found {len(stack)}")
            right = stack.pop()
            left = stack.pop()
            if token == "+":
                stack.append(left + right)
            elif token == "-":
                stack.append(left - right)
            elif token == "*":
                stack.append(left * right)
            else:
                stack.append(left / right)
        else:
            stack.append(float(token))
        print(f"{token:>3}  {stack}")
    if len(stack) != 1:
        raise ValueError(f"{len(stack)} numbers left over, expected 1")
    return stack[0]


print(evaluate_rpn("3 4 + 2 *"))
print()

Intervals

An interval is a stretch between a start and an end: a booking, a request's lifetime, a range of line numbers. Questions about many intervals (do any overlap? how many are open at once?) are hard when the intervals come in any order, because any one of them might overlap any other: n intervals have about n squared over 2 pairs. Sorting by start changes that. Once the intervals are in order of their start, an interval can only overlap ones that started before it and have not ended yet, and the question becomes a walk that compares each interval with what came just before.

First, decide what the ends mean. A room booked from 13 to 15 is free again at 15, so a booking from 15 to 16 does not clash with it: the end is not part of the booking. That is a half-open interval. An interval that includes both of its ends is closed, and then two intervals that touch at one number share that number.

def first_clash(bookings):
    """The first two bookings, in order of start, that use the room at the same time; or None.

    A booking (name, start, end) holds the room from start up to end: at `end` it is free again.
    """
    in_order = sorted(bookings, key=lambda booking: booking[1])
    for earlier, later in zip(in_order, in_order[1:]):
        if later[1] < earlier[2]:
            return earlier[0], later[0]
    return None


week = [("Ana", 9, 11), ("Ben", 13, 15), ("Cy", 10, 12), ("Dee", 15, 16)]
print(first_clash(week))
print(first_clash([("Ben", 13, 15), ("Dee", 15, 16)]))
print(week)

('Ana', 'Cy')
None
[('Ana', 9, 11), ('Ben', 13, 15), ('Cy', 10, 12), ('Dee', 15, 16)]

In order of start the bookings are Ana (9 to 11), Cy (10 to 12), Ben (13 to 15), Dee (15 to 16). Cy starts at 10, before Ana's end at 11: a clash. Ben and Dee touch at 15 and do not clash, because < and not <= is the test of half-open intervals. And the list week is unchanged: sorted() returns a new list and leaves the one it was given alone, while list.sort() would reorder it in place.

Python you need

sorted(items, key=f) sorts by f(item) instead of by the items themselves. lambda booking: booking[1] is a function with no name that takes one booking and returns its start. A key can also return a tuple, and tuples compare item by item: (2, "b") < (2, "c") < (3, "a").

Neighbours are enough to answer whether there is a clash. They are not enough to list every clash:

day = [("Long meeting", 9, 17), ("Ed", 10, 11), ("Flo", 12, 13)]
in_order = sorted(day, key=lambda booking: booking[1])

for earlier, later in zip(in_order, in_order[1:]):
    print(earlier[0], "and", later[0], "clash:", later[1] < earlier[2])

Long meeting and Ed clash: True
Ed and Flo clash: False

The long meeting also clashes with Flo, and no neighbouring pair says so: Ed ended before Flo started, but the long meeting had not. When a question needs more than "is there any overlap?", ask yourself what an interval should really be compared with.

Try it

Convince yourself that neighbours are enough for whether. Suppose two bookings A and C clash, and A starts first, and B starts between them in the sorted order. Why must A and B clash too?

Show the answer

B starts no earlier than A, so it starts at or after A's start. B starts no later than C, and C starts before A ends (that is what "A and C clash" means). So B starts before A ends, and A and B clash. Repeat the argument for each booking between A and C, and you reach a neighbouring pair that clashes. If any two bookings clash, some two neighbours do.

A sliding window

A window is a run of consecutive items of a fixed width: three days of rain, the last hundred requests. As it slides one step along the sequence, one item comes in at the front and one goes out at the back, and everything in the middle stays. So a sum over the window never needs to be added up from scratch: add the one that comes in, subtract the one that goes out. That turns "width steps per position" into "two steps per position".

The largest rainfall over any three consecutive days:

rain_mm = [0, 4, 12, 3, 0, 0, 9, 15, 2, 1]
width = 3

total = sum(rain_mm[:width])  # the first window, added up once
best, best_start = total, 0
for end in range(width, len(rain_mm)):
    total += rain_mm[end]  # the day that comes in
    total -= rain_mm[end - width]  # the day that goes out
    if total > best:
        best, best_start = total, end - width + 1

print(f"wettest {width} days: day {best_start} to day {best_start + width - 1}, {best} mm")
print("checked the slow way:", max(sum(rain_mm[i : i + width]) for i in range(len(rain_mm) - width + 1)))

wettest 3 days: day 6 to day 8, 26 mm
checked the slow way: 26

The first window is added up once. After that, the window that ends at day end is the previous one plus rain_mm[end] minus the day that fell off the back, rain_mm[end - width]. The last line checks the answer the slow way, adding up every window from scratch. A slow, obviously correct version to check a fast one against is called an oracle, and it is how the tests of this module treat numpy.

Trap

A running total of floats can drift. Adding a number and later subtracting the same number does not always bring you back exactly where you were, because each step rounds to the nearest float:

total = 0.0
total += 0.1
total += 0.2
total -= 0.1
print(total)
print(total == 0.2)
print(abs(total - 0.2) < 1e-9)

0.20000000000000004
False
True

That is why tests compare floats with a tolerance (pytest.approx) and not with ==. Chapter 2 has more of these surprises.

Python you need

When items arrive one at a time and leave from the other end, you need a queue: first in, first out. A list is a poor queue, because pop(0) moves every remaining item one place to the left. collections.deque (say "deck", a double-ended queue) adds and removes at both ends in constant time.

from collections import deque

queue = deque(["Ana", "Ben"])
queue.append("Cy")  # joins at the back
print(queue)
served = queue.popleft()  # leaves from the front
print(served, "is served;", len(queue), "waiting:", list(queue))

A running total

How much rain fell from day 1 to day 3? You can add those days up each time you are asked. Or you can keep, once, the total so far after every day. Then the rain of any stretch is one subtraction: the total at its end, minus the total just before its start.

rain_mm = [0, 4, 12, 3, 0, 0, 9, 15, 2, 1]

so_far = [0]  # so_far[k] is the rain of the first k days
for mm in rain_mm:
    so_far.append(so_far[-1] + mm)
print(so_far)


def rain_between(first_day, last_day):
    return so_far[last_day + 1] - so_far[first_day]


print("days 1 to 3:", rain_between(1, 3), "mm; checked the slow way:", sum(rain_mm[1:4]))
print("days 6 to 8:", rain_between(6, 8), "mm; checked the slow way:", sum(rain_mm[6:9]))
print("the whole list:", rain_between(0, 9), "mm")

[0, 0, 4, 16, 19, 19, 19, 28, 43, 45, 46]
days 1 to 3: 19 mm; checked the slow way: 19
days 6 to 8: 26 mm; checked the slow way: 26
the whole list: 46 mm

The list of totals is one longer than the list of days, because it starts with a 0: the total before any day at all. That 0 is what lets a stretch that begins on day 0 work like every other stretch, with no special case. Building the totals costs one pass. After that every question costs one subtraction, however long the stretch.

A sliding window answers "how much in each stretch of this one width". Running totals answer "how much in any stretch", and they still work when some numbers are negative, where a window that grows and shrinks does not.

The three piles of a partition

The last pattern of this module has its own chapter, Partition and select, so here is only the picture. Take a hand of cards and choose one of them, the pivot. Now deal every card onto one of three piles: smaller than the pivot, equal to it, larger than it.

The handPivotSmallerEqualLarger
9, 4, 7, 2, 7, 10, 574, 2, 57, 79, 10

Nothing inside a pile is in order, and yet you already know a lot: every card in the first pile comes before every card in the others in sorted order, and the 7s sit at positions 3 and 4 of the sorted hand, because exactly three cards are smaller. That one deal, which looks at each card once, is the step that quickselect repeats, and the step that the drill sort_colours asks you to do with a list of 0s, 1s and 2s: the pivot is 1, and the three piles must be made inside the list itself, by swapping, in one pass. How to keep three piles inside one list without a second list is the drill; chapter 3 draws the piles, and the rungs below say where to look.

moving_average

Pattern: a sliding window with a running total, kept inside a small class (A sliding window).

Stub: drills/00-diagnostic/moving_average.py · Time box: 20 minutes.

Rung 1: where to look

Read test_the_oldest_number_drops_out_once_the_window_is_full, test_two_windows_do_not_share_their_numbers and test_a_size_below_one_is_refused in test_moving_average.py, and the docstring's "remembers the most recent size numbers".

Rung 2: the idea in words

Each window remembers its own numbers in the order they arrived, oldest at one end. A new number joins at the newest end; if that makes more than size, the oldest leaves from the other end. Keep the total as you go: add what arrives, subtract what leaves, so you never add the whole window up again. The mean is that total divided by how many numbers the window holds right now, which is fewer than size until it has filled.

Rung 3: the shape

All the state is set in __init__, on self: the size, a deque (or a list) of the numbers, and the running total. A list written in the class body instead would be shared by every window, which is what test_two_windows_do_not_share_their_numbers catches. __init__ checks the size before anything else and raises ValueError. add appends, removes the oldest when there are too many, updates the total for both, and returns a division, which is already a float in Python 3. Check yourself

The list of running totals is one longer than the list of numbers, and it starts with a 0. What breaks if you leave that 0 out?

Answer

Every stretch that begins at the first number. The sum of a stretch is the total at its end minus the total just before its start, and before the first number that total is 0. Without it there is nothing to subtract, so you need a special case for those stretches, or you silently miss them.

Why can a tuple be the key of a dict, and a list not?

Answer

A dict files each key under its hash. A list can change after it is stored, and its hash would change with it, so the dict would look in the wrong slot. A tuple cannot change, so its hash is fixed. Python refuses lists as keys with TypeError: unhashable type: 'list'.

In last_seen.py, what would every gap be if the line last_seen[word] = position moved to the top of the loop body, and why?

Answer

0. The dict would already hold the current position when it was asked for the previous one, and position - position is 0. Every "seen before?" question must be asked before the memory is updated.

You need to answer "is x in my collection?" 50,000 times against 50,000 numbers. Roughly how many steps does a list take, and a set?

Answer

A list looks at up to 50,000 items per question (about half of them on average for numbers that are there, all of them for numbers that are not): up to 2.5 billion steps. A set does about one hash and one jump per question: about 50,000 steps, plus 50,000 to build it.

Evaluate 6 2 / 1 - in reverse Polish notation, writing the stack after each token.

Answer

[6], [6, 2], [3.0] (the first pop is the right-hand number, so 6 / 2), [3.0, 1], [2.0]. The answer is 2.

Two closed intervals (both ends included) are (1, 4) and (4, 6). Do they overlap? And as half-open intervals?

Answer

Closed: yes, both contain 4. Half-open: no, the first stops just before 4. The test changes from <= to <; decide which one a problem means before you write it.

A window of width 100 slides along 1,000,000 readings. How many additions does adding each window up from scratch take, and the running sum?

Answer

From scratch: about 100 per position, so about 100 million. Running sum: one addition and one subtraction per position, so about 2 million, 50 times fewer, and the gap grows with the width.

A hand of cards is 8, 3, 8, 1, 9, 5 and the pivot is 5. Deal the three piles. At which position (from 0) does the 5 sit in the sorted hand, and how do you know without sorting?

Answer

Smaller: 3, 1. Equal: 5. Larger: 8, 8, 9. Two cards are smaller than 5, so in sorted order it sits at position 2.
