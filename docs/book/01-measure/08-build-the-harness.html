Chapter 8

Build the harness

The page for your build block. Each day you open one milestone and take it from its first red test to its commit. By Saturday, python -m llm101.bench --profile times a function, draws the spread of its times and names its slowest line, and every line that does it is one you typed.

How to use this chapter

Do not read it from top to bottom. On day 1, read the next two sections, about five minutes, then start Milestone 1. On every other day, open only that day's milestone: each one stands on its own.

The harness, one piece a day

The harness is the package src/llm101/bench/. Its stubs and its two dataclasses, Timings and Report, are given, and you write the functions. Here is the path a measurement takes through them, with the milestone that writes each one (└ means "calls"):

A build block, step by step

Every milestone runs the same loop. Setup, and your first look at the red, were in chapter 0 (First-time setup).

  1. Before you type: ten minutes, no code. Read the milestone down to its questions, open the stub and read its docstring, then answer the questions on paper.
  2. Run the milestone's tests with -x. It stops at the first failure, so you see one problem at a time. That red test is your first job.
  3. Read the failure, then the test. The lines that start with E show what was false, with the value on each side. The test is a few lines long and says exactly what it wants.
  4. Make that one test pass, and run again. The next red test is the next job. Stuck for ten minutes: open the milestone's common bugs, or the next rung of its ladder.
  5. All green: commit, with the message the milestone gives. If the pre-commit hook refuses the formatting, uv run ruff format on the file it names fixes it.

Two rules hold every day. The tests are fixed: if one looks wrong, tell Claude, who fixes a test only when it contradicts the spec, and never touches your code. The block ends on time, even mid-bug: write the bug in log.md and stop. A bug you sleep on goes faster.

The hint ladder

Each milestone has four rungs, folded away: where to look, the idea in words, the shape, and the same mechanism on a different problem. None of them is the answer. Open one, then try for ten minutes before you open the next. With the tutor on, the button under the ladder copies a prompt that asks Claude for your next rung instead; it counts the same. Write the highest rung you used in log.md. There is no rung 5: after rung 4, reread the milestone's "Read first" and make the problem smaller (When a test will not turn green).

Milestone 1: time_calls

What you build. A stopwatch for any function. time_calls(fn, n, warmup) calls fn warmup + n times and keeps the wall time and the CPU time of each of the last n calls, in whole nanoseconds. Every number the harness prints starts here. Day 1, in src/llm101/bench/timing.py.

Read first. Chapter 1's Three clocks in the time module, Warm-up and Functions are values. Then the docstring of time_calls, and the Timings dataclass above it.

Before you type. On paper, from the docstring:

  1. time_calls(f, n=5, warmup=3): how many times is f called, and how many numbers does each list hold?
  2. Which function reads each clock, and in what unit?
  3. What does time_calls(f, n=0) do? And why does the docstring pass lambda: f(x), not f(x)?
Answers

1. Eight calls, and five numbers in each list: one per recorded call, from the last five.

2. time.perf_counter_ns() for the wall clock and time.process_time_ns() for the CPU clock, both in whole nanoseconds.

3. It raises ValueError, because n is below 1. fn takes no arguments, so a call that needs one is packed into a lambda; f(x) would call f at once and hand over its result (chapter 1, "Functions are values").

The tests.

$ uv run pytest tests/m01 -k time_calls -x

If you are stuck.

Common bugs: the symptom, then the cause
  • assert 5 == 8 in the warm-up test: the warm-up loop is missing.
  • A recorded time of about 50 ms in test_time_calls_does_not_record_the_warmup_calls: the warm-up calls went into the lists.
  • test_time_calls_records_whole_nanoseconds fails: you used time.perf_counter(), which gives seconds as a float, instead of time.perf_counter_ns(), which gives whole nanoseconds. Or you divided somewhere.
  • The busy function shows almost no CPU time: the CPU clock is read once around the whole loop, or not at all.
  • Failed: DID NOT RAISE for n = 0: there is no check, or it tests n < 0 where the docstring says below 1.
  • You used time.time_ns(): the clock test fails, and chapter 1 says why it is the wrong clock for durations.
Rung 1: where to look

Read test_time_calls_calls_fn_warmup_plus_n_times and test_time_calls_does_not_record_the_warmup_calls side by side. One counts the calls and the other times them. Which calls happen, and which are kept? Then read test_time_calls_reads_the_two_clocks_its_docstring_names. It looks for two names in your code, and the docstring does not count.

Rung 2: the idea in words

Refuse bad counts before anything else. Call the function warmup times and keep nothing. Then, n times: read both clocks, make the call, read both clocks again, and keep the two differences, one in each list. Keep the readings as close to the call as you can, so that nothing but the call sits between them.

Rung 3: the shape

One check at the top that raises ValueError. Then two loops, one after the other. The first is for the warm-up, with a loop variable you never use (call it _). The second is for the recorded calls, with two empty lists made before it. Inside the second loop: four clock readings around one call, and two appends. Return Timings(wall_ns=..., cpu_ns=...) with keywords. Make test_time_calls_records_n_calls green first: it times a function that does nothing.

Rung 4: the same mechanism on a different problem

A lap timer. One clock, one reading per lap, and each lap is the difference between two readings. Like time_calls, it records a list of durations. Unlike it, it does not call a function you hand it, it has no warm-up, and it has one clock.

import random
import time

rng = random.Random(7)
laps_ns = []
previous = time.perf_counter_ns()
for lap in range(5):
    time.sleep(rng.uniform(0.010, 0.030))  # the runner runs one lap
    now = time.perf_counter_ns()
    laps_ns.append(now - previous)  # this lap: from the last reading to this one
    previous = now

for number, lap_ns in enumerate(laps_ns, start=1):
    print(f"lap {number}: {lap_ns / 1e6:5.1f} ms")
print(f"total: {sum(laps_ns) / 1e6:.1f} ms")

One run on the Mac (Apple M5); yours will differ:

lap 1:  23.4 ms
lap 2:  19.6 ms
lap 3:  32.6 ms
lap 4:  16.0 ms
lap 5:  29.5 ms
total: 121.1 ms

Your time_calls differs in three ways. The thing timed is fn(). The readings come in pairs around each call, not in a chain. And there are two clocks, not one.

Milestone 2: histogram

What you build. The shape of a spread. histogram(values, bins) cuts the range of the values into bins of equal width and counts the values in each, exactly as numpy.histogram does. M5 draws one bar per bin from these counts. Day 2, in src/llm101/bench/stats.py.

stats.py has two rules of its own, each checked by a test that reads the file: it imports no numpy, and it never calls sorted() or .sort(). numpy is the tests' oracle, the trusted answer yours is compared with; it is not your tool.

Read first. Chapter 2's Histograms: the shape of a distribution, with Looking with numpy.histogram and Floating-point surprises. Then the docstring of histogram: four rules and one example.

Before you type. On paper:

  1. Work the docstring's example by hand: histogram([1, 2, 2, 3, 9], 4). Write lo, hi and the step, then the five edges, then the bin of each value. Do you get [3, 1, 0, 1]?
  2. histogram([7], 4): what are the edges, and which bin holds the 7?
Answers

1. lo is 1, hi is 9 and the step is 2, so the edges are 1, 3, 5, 7 and 9. The values 1, 2 and 2 fall in the first bin, from 1 up to 3; the 3 sits on an edge and goes right, into the second; the 9 is the last edge, which the last bin includes. That gives [3, 1, 0, 1].

2. lo equals hi, so the range widens to 6.5 to 7.5, and the step is 0.25: edges 6.5, 6.75, 7.0, 7.25 and 7.5. The 7 sits exactly on the inner edge 7.0 and goes to the bin on its right, the third: [0, 0, 1, 0].

The tests.

$ uv run pytest tests/m01/test_histogram.py -x

Fifteen tests. The first is the example you have just worked by hand, and the last two compare yours with numpy on random input. test_stats_does_not_import_numpy passes already: keep it green.

If you are stuck.

Common bugs: the symptom, then the cause
  • The counts add up to one less than the number of values: the largest value fell outside. The last bin includes its right edge.
  • IndexError: list index out of range on the largest value: its division gives exactly bins. Clamp it into the last bin.
  • test_histogram_decides_membership_with_the_edges fails, or counts are off by one in two neighbouring bins in the hypothesis tests: a floating-point division put a value in the neighbouring bin. Check the guess against the edges (chapter 2).
  • Counts off by one although the edges look right: the tests compare edges to within a millionth of a millionth but counts exactly, so edges that differ from numpy's in the last digits show up as a value in the wrong bin. Compute the step once and use lo + i * step. Adding the step again and again, or computing lo + i * (hi - lo) / bins, rounds differently.
  • ZeroDivisionError when all the values are equal: widen the range first.
  • test_stats_does_not_import_numpy turns red: numpy crept into stats.py. It belongs in the tests only.
Rung 1: where to look

The docstring has four rules, and each one has a test: pair them up. Then work test_histogram_a_value_on_an_inner_edge_goes_to_the_right on paper, the way you worked the docstring's example: the edges first, then the bin of each value. Which rule does it check, and which bin does your code choose for the 1?

Rung 2: the idea in words

Find the smallest and the largest value. If they are equal, widen the range by a half on each side. Make the edges from the start and one step, with the last edge exactly the end of the range. For each value, make a first guess at its bin with a division, and keep the guess inside the list of bins. Then check the guess against the edges on either side, and move it by one bin if the edges disagree. Count it.

Rung 3: the shape

min() and max() once each, before the loop, not inside it. The edges in one comprehension over range(bins), then hi appended. A list of bins zeros for the counts. One loop over the values. Inside it: an index from the division; a clamp, so that the largest value lands in the last bin; one comparison with the edge on the left and one with the edge on the right; then the count. Make the docstring example green first, and leave the hypothesis tests for last.

Rung 4: the same mechanism on a different problem

Counting events per hour of the day is a histogram with 24 bins of 60 minutes. The bin comes from a division, and the very end of the day closes the last bin, like the last edge. The numbers are whole, so nothing goes wrong with rounding. Your histogram adds the check against the edges, because its numbers are not whole.

"""Count events per hour of the day: 24 bins of 60 minutes each."""

timestamps = ["00:15", "00:59", "01:00", "07:30", "07:45", "23:59", "24:00"]

counts = [0] * 24
for stamp in timestamps:
    hours, minutes = stamp.split(":")
    minute_of_day = int(hours) * 60 + int(minutes)  # 0 to 1440
    hour = minute_of_day // 60  # which 60-minute bin
    if hour == 24:  # 24:00 is the very end of the day: it closes the last bin
        hour = 23
    counts[hour] += 1

for hour, count in enumerate(counts):
    if count:
        print(f"{hour:02d}:00 to {hour + 1:02d}:00  {count}")

00:00 to 01:00  2
01:00 to 02:00  1
07:00 to 08:00  2
23:00 to 24:00  2

Done. All fifteen green: commit M2: histogram green.

Milestone 3: quickselect

What you build. One position of a list in order, found without sorting the list. quickselect(values, k) returns the k-th smallest value, counting from 0. Your percentiles stand on it: the p99 of a thousand timings is the value at one position of them in order. Day 3, in stats.py.

Read first. Chapter 3's Selection, by hand and Why three piles, again, just before you start, and the drill sort_colours from this morning: its three piles are the step this milestone repeats. Then the docstring of quickselect.

Before you type. On paper, from the docstring:

  1. What is quickselect([7, 1, 5, 3], 2)? And quickselect([2, 2, 1], 1)?
  2. Which error does quickselect([], 0) raise, and which does quickselect([1, 2, 3], 3)?
Answers

1. In order, the first list is 1, 3, 5, 7, and position 2 holds 5. The second is 1, 2, 2 in order, so position 1 holds 2: repeats count.

2. ValueError for no values at all, and IndexError for a k outside range(3), which runs from 0 to 2.

The tests.

$ uv run pytest tests/m01/test_quickselect.py -x

Fifteen tests. The docstring's examples come first. The last is a speed test: it fails if numbers in rising or in falling order take ten times as long as the same numbers shuffled. test_stats_does_not_sort passes already: keep it green.

If you are stuck.

Common bugs: the symptom, then the cause
  • A RecursionError, or the speed test fails on input in rising or in falling order: the pivot is the first or the last value. Choose it at random.
  • The loop never ends when values repeat: with only two groups (smaller, and larger or equal), a list of equal values never shrinks. Use three.
  • Off by one: k counts from 0, so quickselect([7, 1, 5, 3], 0) is 1.
  • test_quickselect_does_not_change_its_input fails: you partitioned the caller's list. Work on list(values), which also turns a tuple into a list.
  • stats.py selects; it never sorts: there is a sorted() or .sort() somewhere in stats.py, even in a helper.
  • ValueError against IndexError: no values is a ValueError. A k outside range(len(values)), negative ones included, is an IndexError.
Rung 1: where to look

Read test_quickselect_all_values_equal and test_quickselect_with_many_repeats. What happens to your piles when every value is the same? Then read the message in test_quickselect_ordered_input_is_not_the_worst_case: it asks you a question.

Rung 2: the idea in words

Work on a copy. Pick a pivot at random from the values you still have. Split them into three groups: smaller than the pivot, equal to it, and larger. If the position you want lies among the smaller ones, keep only those and look again. If it lies among the equal ones, the pivot is the answer. Otherwise keep only the larger ones, and move the position you want down by the number of values you threw away. Repeat until you find it.

Rung 3: the shape

The checks first: ValueError when there are no values, IndexError when k is outside range(len(values)). Then a while True loop, which cannot hit the recursion limit the way a recursive version can. Inside the loop: one random.choice, then the three groups (three comprehensions over the values you still have, or your sort_colours partition run on the current part of the copy), then if, elif and else on k against the sizes of the first two groups. k changes only in the last branch. Test it by hand first, on [7, 1, 5, 3], for every k from 0 to 3.

Rung 4: the same loop, on paper

This rung stays on paper, because any program for it would be quickselect under another name. Here is the loop, done by hand. The task is to find position 4, the fifth smallest, of [8, 3, 9, 1, 5, 7, 2, 6, 4]. In order those numbers are 1 to 9, so the answer is 5. The pivots happened to come out as 7, then 2, then 5:

RoundValues you still havePivotSmallerEqualLargerPosition you wantWhat happens
18 3 9 1 5 7 2 6 473 1 5 2 6 4 (6)7 (1)8 9 (2)44 is less than 6: keep the smaller ones
23 1 5 2 6 421 (1)2 (1)3 5 6 4 (4)44 is past 1 + 1: keep the larger ones; the position becomes 4 − 2 = 2
33 5 6 453 4 (2)5 (1)6 (1)22 is not less than 2, but less than 2 + 1: the answer is the pivot, 5

Count the work. Each round looked once at every value it still had: 9 + 6 + 4 = 19 looks. Sorting nine values takes about 9 × log₂ 9, which is about 29. Now take the same task on the ordered list 1 to 9, with the first value as the pivot every time. Each round throws away one value: the rounds look at 9, 8, 7, 6 and 5 values, 35 in all, and the answer comes in round 5. On a million ordered values that pattern costs about 375,000 million looks (chapter 3's 3n²/8). That is the question the speed test asks.

Done. All fifteen green: commit M3: quickselect green.

Milestone 4: percentile

What you build. p50, p95 and p99. percentile(values, q) gives the value q% of the way along the list in order, by numpy's default method, and finds the one or two values it needs with your quickselect. Day 3 or 4, in stats.py.

Read first. Chapter 2's Percentiles by rank and Reading between two readings. Then the docstring of percentile, which works its numbers for you.

Before you type. On paper:

  1. Work the docstring's q = 90 on [40, 10, 30, 20] by hand: n, then h, then the two neighbours by rank, then how far along the gap. Do you get 37.0?
  2. q = 0 and q = 100 on the same list: what is h, what is the answer, and how many values does each need?
Answers

1. n is 4, so h = 3 × 0.90 = 2.7. In order the values are 10, 20, 30, 40: positions 2 and 3 hold 30 and 40, and 0.7 of the way from 30 to 40 is 37.0.

2. q = 0 gives h = 0, the smallest value, 10; q = 100 gives h = 3, the largest, 40. Each h is a whole number, so each needs one value, not two.

The tests.

$ uv run pytest tests/m01/test_percentile.py -x

Fourteen tests. The docstring's examples come first. Near the end, one test reads your code for a call to quickselect, and the last two compare yours with numpy. The first of those two, test_done_when_percentiles_match_numpy_on_random_data, is half of the module's "Done when".

If you are stuck.

Common bugs: the symptom, then the cause
  • IndexError at q = 100: h is n - 1, the largest rank, and there is no rank after it to ask for.
  • h computed as n * q / 100: at q = 100 it asks for rank n, which does not exist. Positions run from 0 to n - 1.
  • percentile finds its values with your quickselect(): percentile sorted a copy, or found its values some other way.
  • No ValueError for q = 100.1: check q before anything else.
  • The docstring's q = 90 example gives 33 where it should give 37, and hypothesis finds more: the two weights are the wrong way round. At h = 2.7 the answer is 0.7 of the way from the value at position 2 to the value at position 3, so the value at 3 gets the weight 0.7.
Rung 1: where to look

Read test_percentile_between_two_values and test_percentile_on_an_exact_position, and work each one by hand the way you worked the docstring's q = 90. What is h in each, and how many values do you need to find?

Rung 2: the idea in words

Check the values and q first. Work out the position h from n and q. Its whole part names the lower neighbour by rank, and the rank after it is the upper neighbour; ask quickselect for each. The answer is the lower value plus the fraction of the gap between the two. When h is whole, or the lower neighbour is already the largest value, there is no upper neighbour to ask for.

Rung 3: the shape

math.floor for the whole part, and a subtraction for the fraction. At most two calls to quickselect. One if for the case with no upper neighbour. The checks on q (below 0, above 100) and on an empty list come before everything else.

Rung 4: the same mechanism on a different problem

Chapter 2 reads a temperature between two hourly readings: the earlier reading, plus the fraction of the hour that has passed, times the change over that hour. Percentile is the same interpolation. The two readings are the values at two ranks, found by quickselect, and the fraction of the hour is the fraction part of h.

Milestone 5: summarise, render_report and main

What you build. The program, in three small pieces, in this order. summarise turns Timings into a Report, in timing.py. render_report draws a report as a table and a histogram and returns it without printing, in report.py. main reads the command line, times demo() and prints the report, in __main__.py. Day 4.

Read first. For summarise: its docstring and the Report dataclass. For render_report: chapter 4's Table, Group, Bars that mean something, Choosing a unit and the weather report, then its docstring. For main: chapter 4's argparse and Running a package as a program, and the Spec section of the module README.

Before you type. On paper:

  1. Work the docstring example of summarise by hand: Timings(wall_ns=[1_000_000, 3_000_000], cpu_ns=[1_000_000, 1_000_000]). What are the mean, the p95, the throughput and the CPU share?
  2. A histogram's four bins hold 80, 20, 1 and 0 values. With a bar_width of 40, how long is each bar?
Answers

1. The mean is 2,000,000 ns. The p95 sits at h = 0.95, 0.95 of the way from 1,000,000 to 3,000,000: 2,900,000 ns. Two calls in 4,000,000 ns, which is 0.004 s, make 500 calls per second, and the CPU share is 2,000,000 / 4,000,000 = 0.5.

2. 40 for the fullest bin, then round(20 / 80 * 40), which is 10. The third is round(0.5), which is 0, but a count that is not zero gets at least one character, so 1. The empty bin gets no bar.

Milestone 6: slowest_lines

What you build. Where the time goes inside one function. slowest_lines(fn, *args, **kwargs) runs fn once under a line tracer that you build on sys.settrace, and returns the seconds of each line of fn's own body, slowest first. Then --profile in main prints the slowest lines of demo(), at most five. Day 5, in lines.py and __main__.py.

Read first. Chapter 5's How tracing works, Choosing which frames to trace, Counting calls per function and Put the old tracer back; chapter 1's Functions are values, for closures and nonlocal. Then the docstring of slowest_lines.

Before you type. Open demo() in __main__.py: four lines. On paper:

  1. Which line do you expect to be the slowest, and why?
  2. slowest_lines(demo) returns pairs of a line number and its seconds. Which line should come first, and can any line of " ".join or sum appear?
Answers

1. squares = [i * i for i in range(20_000)]: twenty thousand multiplications, each one run by the interpreter. The other lines make a short list, join a thousand strings and add up a list, and all of that work happens inside fast C code.

2. The squares line comes first. No line of join or sum can appear: only fn's own lines are listed, and the time of a function that fn calls counts toward the line of fn that called it.

The tests.

$ uv run pytest tests/m01/test_slowest_lines.py -x
$ uv run python -m llm101.bench --n 100 --profile

Nine tests. The first is the "Done when" test, and the last runs the program with --profile, so it waits for your change to main. The functions they time sit at the top of the test file, each with its slow line marked. The second command is for your eyes.

If you are stuck.

Common bugs: the symptom, then the cause
  • helper's own lines appear in the callee test: the global tracer follows every frame. Follow only fn's code.
  • The slow line shows almost no time, and the line after it shows a lot: the time between two events went to the line that was starting, not to the one that had just run.
  • The loop test fails: each run of a line replaced its total instead of adding to it.

Rung 2: the idea in words

Follow only fn's own frame. When the tracer hears about a new frame, it follows it only if that frame is running fn's code. Inside that frame, each event is a moment in time, and the time from one event to the next belongs to the line that was running between them; add it to that line's total. When fn has finished, whatever happened, put the old tracer back. Then order the totals from slowest to fastest.

Rung 3: the shape

A dict from line number to seconds. Two variables in slowest_lines that remember which line is running and when its time started. The tracer is a function inside slowest_lines, so it needs nonlocal to change them. A global tracer that compares frame.f_code with fn.__code__, and returns the local tracer or None. A local tracer that, at every event, adds the time since the last event to the line that was running, then remembers the new line and the new time, and returns itself. try and finally around the call. At the end, the dict's items ordered by their seconds, largest first. Sorting is allowed here: this is lines.py, not stats.py.

Rung 4: the same mechanism on a different problem

Chapter 5's call counter is the same mechanism. It is a tracer installed with sys.settrace, put back with try and finally, that keeps a total per key in a dict. It counts calls per function name, from the call event. Yours adds up time per line number, from the events inside one frame.

When a test will not turn green

You have read the test and the docstring twice, and the red will not move. Make the problem smaller: three values instead of a thousand, in a file in scratch/. Four tools help:

  • uv run pytest tests/m01 -x -vv -k NAME runs one test and prints all it can about the failure.
  • uv run pytest --lf runs only the tests that failed last time.
  • breakpoint() on a line of your function stops the test there, at the debugger's prompt: p name prints a variable, n runs the next line, c carries on and q quits.
  • A hypothesis failure prints a failing test case (older versions call it the falsifying example): the smallest input it found that breaks your code. Call your function on it in a scratch file, and print each step.
Trap

Do not make a test pass by bending your code around one failing example, such as an if for values == [0.0, 1.0]. Hypothesis will find the next one, and the review will find the if. A failing test case is a clue to the rule your code gets wrong.

For quickselect and histogram, a table on paper often beats a print: one row per round or per value, one column per thing your code knows at that step. The appendix has the rest: Reading pytest's output, Reading hypothesis output, and The errors of this module, with each message's cause and fix.

Check yourself

Why does time_calls read the clocks inside the loop, around each call, rather than once before the loop and once after it?

Answer

Two readings around the whole loop give only the total, and so only the mean. Percentiles and histograms need the time of each call, and the slow ones are exactly what a total hides.

summarise belongs to M5, but its tests cannot all pass before two earlier milestones are green. Which two, and why?

Answer

M4 and M3. summarise computes p50, p95 and p99 with your percentile, and percentile finds its values with your quickselect. A test reads summarise's code to check that it calls percentile, so a shortcut through numpy or a sort fails too.

You time 50 calls. Which calls decide the p99?

Answer

The position is h = 49 × 0.99 = 48.51, between ranks 48 and 49, so the p99 lies between the second-slowest and the slowest call, a little past halfway. Two calls decide it, which is why 50 calls give a shaky p99.

Why does a random pivot make an ordered list harmless? Is there still an input that makes your quickselect slow?

Answer

The random choice does not depend on the order of the input, so no order is bad on purpose: every list gets the same average, about four times n looks. Any single run can still be unlucky, but a long unlucky streak is as rare as a long run of sixes, and gets rarer the longer it is.

If the slow line of demo() moved into a helper function that demo() calls, which line would slowest_lines(demo) name?

Answer

The line of demo() that calls the helper. The tracer leaves the helper's frame alone, so the helper's whole time falls between two events of demo's frame.

Why are the warm-up calls left out of the report?

Answer

First calls pay one-off costs: imports, caches filling, memory being found for the first time. The report describes the steady state, the calls that come after, which is what a server lives in.
