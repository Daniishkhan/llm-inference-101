What you will build: a benchmark harness

Every module after this one asks a question about speed. Is the tokenizer you write in Module 2 fast enough? How much does a KV cache save per token? What does batching do to the slowest request? Each of those questions ends in a number, and every number in this course comes from the program you build this week: a benchmark harness, a small tool that calls a function many times, times every call, and summarises what it saw.

You run it as uv run python -m llm101.bench. When it is finished it does four things:

  • It calls a given function, demo(), a thousand times after fifty warm-up calls, and times each call with two clocks: one that keeps running while the program waits, and one that runs only while it computes (chapter 1).
  • It prints a table: the number of calls, the fastest, the mean, the p50 (the typical call), the p95 and p99 (the slow calls a user notices), the slowest, the calls per second, and the share of the time spent computing (chapter 2).
  • Under the table it draws a histogram: one line per range of times, with a bar for how many calls fell into it.
  • With --profile, it adds the slowest lines inside demo(), at most five: where the time goes, not only how much there is (chapter 5).

You write all of it, including the parts a library would normally do. The percentiles come from your own selection algorithm; numpy is only the tests' oracle, used to check your answers.

Why measure first

A claim about speed without a measurement is a guess. A measurement taken once is an anecdote, because a computer never runs the same code in exactly the same time twice. And "12 ms" means nothing until you know on which machine, on which day, plugged in or not, after how many warm-up calls: a number without its machine and date is not evidence (docs/setup.md). Every later module has a Measure step that runs this harness, and every BENCH.md has a row for the machine and the date. So the harness comes first, before any part of an inference engine exists.

First principle

A computer is not a stopwatch-perfect machine. Other programs share its cores, its chips speed up and slow down to save power, its memory caches warm up and go cold, and Python itself pauses now and then to tidy memory. Each of those changes how long the same line takes. The only honest answer to "how fast is it?" is a distribution of many timings, summarised, with the conditions written next to it.

The rule: you type every line

This course rebuilds one skill above all: writing code with your own hands. So the rule of CLAUDE.md holds everywhere: you type every solution. The tutor writes the problems, the tests and the explanations, never the code that solves them.

For this book, that means three things.

  • The book teaches on different problems. Timing is taught on a kettle and a sum, interpolation on temperatures. Each mechanism is shown complete, one step away from your task, with its own names; the last step is yours.
  • Hints come one rung at a time. Chapter 8 has a hint ladder per milestone, folded away: four rungs, from "where to look" to "the same mechanism on a different problem". Open one, close the book, try again. There is no fifth rung.
  • There is no live tutor. The tutor panel on each page composes a prompt, with the chapter and milestone filled in, for you to paste into Claude Code, which answers under the same rules: an explanation, a question back, or one rung.

Done when

The module is not done at the end of the week. It is done when every box of the "Done when" list in the module README is ticked. goal.md puts it in one sentence: its percentiles match numpy's on random data, and its profile points to the right slow line in a test function. In full:

  • test_done_when_percentiles_match_numpy_on_random_data and the rest of test_percentile.py are green.
  • test_done_when_it_names_the_slow_line_of_a_test_function and the rest of test_slowest_lines.py are green.
  • uv run pytest tests/m01 is green from end to end.
  • uv run python -m llm101.bench --profile prints the table, the histogram and the slowest lines.
  • modules/01-measure/BENCH.md has its Experiment: a prediction written before the run, the measurement, and two sentences on why.
  • One commit per milestone, M1 to M7, each through the pre-commit hook, and one more for M7's prediction, made before its measurement.
  • A review of the whole module has been run, and its three questions are answered in log.md.
  • Five lines in log.md, and "m01" added to done under [tool.llm101] in pyproject.toml.

First-time setup

From the repository root, once:

$ cd ~/Desktop/projects/llm-inference-101
$ uv sync
$ tools/install-hooks.sh

uv sync reads pyproject.toml and uv.lock and creates .venv/: Python 3.13 with exactly this module's packages (numpy and rich; pytest, hypothesis and ruff for development). uv run runs a command inside it, so there is nothing to activate. tools/install-hooks.sh installs a pre-commit hook: a script git runs before every commit, which refuses the commit if a file is not formatted or fails the lint check, and says which file and why.

Read the red

Now run the module's tests:

$ uv run pytest tests/m01
...
tests/m01/test_histogram.py FFFFFFFFFFFF.FF                              [ 19%]
tests/m01/test_percentile.py FFFFFFFFFFFFFF                              [ 38%]
tests/m01/test_quickselect.py FFFFFFFFFFF.FFF                            [ 57%]
tests/m01/test_report.py FFFFFF                                          [ 65%]

tests/m01/test_timing.py FFFFFFFFFFFFFFFFF                               [100%]
...
========================= 74 failed, 2 passed in 0.27s =========================

Seventy-six tests, and almost all of them red. That is the starting line, not a problem. Each F is a failed test and each . a passing one, file by file. Narrow it down to the first milestone and read one failure properly:

$ uv run pytest tests/m01 -k time_calls -x
...
_______________________ test_time_calls_records_n_calls ________________________
tests/m01/test_timing.py:19: in test_time_calls_records_n_calls
    timings = time_calls(lambda: None, n=7)
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
src/llm101/bench/timing.py:49: in time_calls
    raise NotImplementedError("TODO(you)")
E   NotImplementedError: TODO(you)

-k time_calls keeps the tests whose name contains time_calls; -x stops at the first failure. Read from the top: the test test_time_calls_records_n_calls, line 19 of tests/m01/test_timing.py, called time_calls with a function that does nothing and n=7; that went into src/llm101/bench/timing.py, line 49, where the stub raised. The line starting with E is the error itself. It reports no bug: the function has not been written. Almost every red test today fails this way.

Four fail differently. Two read your source instead of calling it, checking that summarise calls your percentile and that percentile calls your quickselect; they fail with their own message, such as AssertionError: summarise computes p50, p95 and p99 with your percentile(). Two run the whole program, python -m llm101.bench, and fail because it stops with the NotImplementedError traceback.

Five tests that pass on day one

Before you have typed anything, five tests are green. Two are in tests/m01 (the . in the histogram and quickselect lines above), and three are in the drills, which you see when you run everything with uv run pytest, which ends 5 passed:

  • test_stats_does_not_import_numpy: stats.py must not import numpy.
  • test_stats_does_not_sort: stats.py must not call sorted() or .sort().
  • test_it_does_not_sort, twice: the drills longest_streak and sort_colours must not sort either.
  • test_it_does_not_hand_the_work_to_a_library: the drill tidy_path must not import os, posixpath or pathlib.

Each reads the code and checks for something a correct solution must not do. A stub does nothing, so it never does the forbidden thing. These tests are there to stay green, and they start to mean something the moment you start typing.

How to read this book

  • Cover and retype the examples. Each program is complete and was run before it was printed. Read it until you could explain every line, cover it, and type it into scratch/ from memory, under the name shown with it. Then compare it with the page and run it with uv run python scratch/NAME.py. Copying trains your fingers; rebuilding from memory trains what an interview asks for. If the read block is running out, type the rest with the page open. Typing, not pasting, either way: the typos are part of the lesson.
  • Compare the output. Most programs show their exact output. Where a program prints a time, it is one run on the M5: your numbers will differ, the shape should not.
  • Answer before you open. Say or write your answer to a "Try it" or "Check yourself" before you unfold it. A wrong guess you correct is worth more than a right answer you read.
  • The callouts have one job each. First principle: what the machine does. Analogy: a picture, and where it stops being true. Trap: a mistake, where you would make it. Python you need: a construct refreshed. In a real engine: where vLLM or a similar engine does the same.

How to get unstuck

In the build block, in this order (docs/methodology.md, "When you are stuck in the build"):

  1. Re-read the test that fails and the docstring of the function in the stub. Most of the time the answer is in one of them.
  2. Reproduce the smallest version of the problem in scratch/: three values instead of a thousand, one call instead of a loop.
  3. Ask for one rung of the hint ladder, in chapter 8 or from Claude Code, and say which rung you are on.
  4. Only once the tests are green, ask for a review.

In a drill, the rule is stricter: at the bell, ask for one rung or log a timeout. A timeout has no reveal. The problem stays open and comes back at its +2 day redo.

A contract with yourself

  • One commit per milestone, named: M1: time_calls green. Seven such commits, and M7's prediction committed before its run, are the record a reviewer wants to see.
  • The log, every day: five lines in log.md on what surprised you, in block 5, on the day.
  • The prediction before the measurement, written in BENCH.md before anything runs. Only a written guess can surprise you.

Check yourself

Why is the benchmark harness the first thing you build, before any part of an inference engine?

Answer

Because every later module has a Measure step, and every number in it comes from this harness. A tokenizer, a KV cache or a batching scheduler is only "faster" once it has been measured, many calls at a time, with the machine and the date written next to the result.

A friend says "my function takes 12 ms". What three things would you ask before you believe it?

Answer

How many times it was run (one timing is an anecdote), what was reported (the mean, the median, the slowest?), and on which machine, on which day, under which conditions (power, other programs, warm-up). A number without its machine and date is not evidence.

Five tests pass before you have written anything. What do they check, and why do they pass?

Answer

They read the source and check what it must not do: stats.py must not import numpy or sort, longest_streak and sort_colours must not sort, and tidy_path must not import a path library. A stub does nothing, so it never breaks those rules. They begin to matter once you start typing.

A test fails with E NotImplementedError: TODO(you). Is there a bug in your code?

Answer

No. The function has not been written yet: its body is still the stub's raise. The traceback above that line shows which test called which function, and on which line.

It is day 3 of the module. Which drills belong in block 1, and in which order?

Answer

The redos first: the set 00 problems you first solved on day 1, which fall due at +2 days, with your ledger as the list. Then the day's new problem, sort_colours, which also prepares the partition step of M3.
