Chapter 01

Two clocks

At the end of this chapter you will be able to time a piece of Python with the right clock, tell waiting apart from computing, and explain why the same code takes a different time on every run. You will also know when a repeated call stops measuring what you meant, and how to pass a function around as a value, which is what milestone M1 needs.

The problem: one timing lies

Here is the simplest way to time something in Python: read a clock, do the work, read the clock again, and subtract.

import time

start = time.perf_counter_ns()
total = sum(range(2_000_000))
stop = time.perf_counter_ns()

print(f"total {total:,}, wall time {(stop - start) / 1_000_000:.2f} ms")

Run it five times in a row. The shell's for loop saves you typing the command five times:

$ for i in 1 2 3 4 5; do uv run python scratch/one_sum.py; done

One run on the M5; yours will differ:

total 1,999,999,000,000, wall time 11.44 ms
total 1,999,999,000,000, wall time 14.30 ms
total 1,999,999,000,000, wall time 11.78 ms
total 1,999,999,000,000, wall time 11.49 ms
total 1,999,999,000,000, wall time 11.70 ms

The total is the same every time, as it must be. The time is not: the second run took a quarter longer than the first. Had you run it once and written "summing two million numbers takes 14.3 ms", you would have told the truth about one run and misled about all the others. To answer "how long does this take?" you need the right clock, read the right way, and the habit of never trusting a single reading. This chapter gives you both; the next one shows how to summarise many readings honestly.

What a clock is to the computer

First principle

A computer clock is a counter. A crystal on the board vibrates at a fixed rate, and a piece of hardware counts the vibrations. On Apple silicon the counter that Python reads goes up 24 million times a second, so one tick is 1 / 24,000,000 of a second: about 41.7 nanoseconds. "Reading the clock" means asking for the current count. A duration is the difference between two counts, multiplied by the length of a tick. The kernel, the part of the operating system that owns the hardware and decides which process runs on which core, keeps a second, different kind of clock as well: an account, for each process, of how long it has actually been running on a core.

A nanosecond (ns) is a billionth of a second. A microsecond (µs) is a thousand nanoseconds, and a millisecond (ms) a thousand microseconds. Python's _ns functions return whole numbers of nanoseconds, as an int, which is why one_sum.py divides by 1,000,000 to print milliseconds. Whole numbers are exact; the older functions without _ns return seconds as a float, which loses the last digits once the count is large.

Three clocks in the time module

Python's time module offers several clocks. Three matter here.

  • time.perf_counter_ns(): the wall clock for measuring, so called because it is the time a clock on the wall would show passing. It never goes backwards, it ticks finely, and it keeps running whatever your program is doing, computing or waiting. Its starting point means nothing; only differences between two readings do.
  • time.process_time_ns(): the CPU clock. It counts only the time this process spent running on a core, added up over every core it used. While your program sleeps or waits for a file, it stands still.
  • time.time(): the calendar clock: seconds since 1 January 1970, the time of day your Mac shows in its menu bar. It is the right clock for "when did this happen?" and the wrong one for "how long did it take?".
Analogy

perf_counter_ns is a stopwatch: you press start, and it runs until you press stop, whether you were working or staring out of the window. process_time_ns is a timesheet: it records only the hours you actually worked. time.time is the clock on the town hall: everyone agrees on it, but now and then someone climbs up and sets it right, and if you timed your run by it you could find you finished before you started. Where it breaks: a person can only work one job at a time, so a timesheet never shows more hours than the stopwatch. A process can run on several cores at once, and then its "timesheet" adds up all of them. A section below shows it.

time.get_clock_info tells you what each clock promises on the machine you are on:

import time

for name in ["perf_counter", "process_time", "time"]:
    info = time.get_clock_info(name)
    print(f"{name:13} monotonic={info.monotonic!s:5}  adjustable={info.adjustable!s:5}  "
          f"resolution={info.resolution:.2e} s  ({info.implementation})")

On the M5 (another machine prints other implementations and resolutions):

perf_counter  monotonic=True   adjustable=False  resolution=4.17e-08 s  (mach_absolute_time())
process_time  monotonic=True   adjustable=False  resolution=1.00e-06 s  (clock_gettime(CLOCK_PROCESS_CPUTIME_ID))
time          monotonic=False  adjustable=True   resolution=1.00e-06 s  (clock_gettime(CLOCK_REALTIME))

Read the three columns:

  • monotonic: the clock never goes backwards. Two readings in a row can be equal, but the second is never smaller.
  • adjustable: something outside your program may change the clock while it runs. The calendar clock is adjustable: your Mac corrects it against a time server on the internet, and you can set it by hand.
  • resolution: the smallest step the clock can show. For perf_counter it is 4.17 × 10-8 s, the 41.7 ns tick of the hardware counter. The CPU clock moves in steps of a whole microsecond, 24 times coarser.

The last column names the call that does the work: mach_absolute_time() reads the hardware counter; CLOCK_PROCESS_CPUTIME_ID asks the kernel for the process's account.

Trap

Never time a duration with time.time(). It is adjustable and not monotonic: if the Mac corrects its clock between your two readings, the difference includes the correction, and it can even be negative. That correction happens rarely, which makes the bug worse: your benchmark works for weeks and then reports a call that took minus 300 milliseconds. Durations come from perf_counter_ns.

A kettle and a sum

Now use both measuring clocks at once, on two jobs that are as different as possible. Waiting for a kettle is all waiting: you stand there, and nothing you do makes it faster. Doing a sum in your head is all work: nothing is waiting, and the time is the time you spend thinking. In Python, time.sleep(0.2) is the kettle: it asks the operating system to take the process off its core for 200 ms. A loop that adds up numbers is the sum.

import time

# The kettle: wait 200 ms and do nothing.
wall_start = time.perf_counter_ns()
cpu_start = time.process_time_ns()
time.sleep(0.2)
cpu_stop = time.process_time_ns()
wall_stop = time.perf_counter_ns()

wall_ms = (wall_stop - wall_start) / 1_000_000
cpu_ms = (cpu_stop - cpu_start) / 1_000_000
print(f"kettle: wall {wall_ms:7.2f} ms   cpu {cpu_ms:6.2f} ms   cpu share {cpu_ms / wall_ms:.2f}")

# The sums: add up numbers, and never wait.
wall_start = time.perf_counter_ns()
cpu_start = time.process_time_ns()
total = 0
for i in range(3_000_000):
    total += i
cpu_stop = time.process_time_ns()
wall_stop = time.perf_counter_ns()

wall_ms = (wall_stop - wall_start) / 1_000_000
cpu_ms = (cpu_stop - cpu_start) / 1_000_000
print(f"sums:   wall {wall_ms:7.2f} ms   cpu {cpu_ms:6.2f} ms   cpu share {cpu_ms / wall_ms:.2f}")

One run on the M5; yours will differ:

kettle: wall  205.06 ms   cpu   0.04 ms   cpu share 0.00
sums:   wall  116.42 ms   cpu 116.36 ms   cpu share 1.00

Look at the order of the reads: the wall clock is started first and stopped last, so the CPU readings sit inside it, and nothing but the work happens between them.

The kettle took 205 ms on the stopwatch and 0.04 ms on the timesheet: 40 microseconds of work, for the call into sleep and back, and 200 ms of standing still. The sums took 116 ms on both clocks: every moment of wall time was spent computing. Divide CPU time by wall time and you get the CPU share, one number that says what kind of job it was: about 0 for waiting, about 1 for computing. Most real work is somewhere between, and the share tells you where.

Notice that the kettle took 205 ms, not 200. sleep promises to wait at least as long as you asked; then the operating system has to give your process a core again, and macOS groups timers together to save power, so it wakes you a little late.

Try it

Change the kettle to time.sleep(0.01), then to time.sleep(0.05). Before each run, write down the wall time you expect. Then run it a few times.

What the M5 showed

About 15 ms for a 10 ms sleep and about 60 ms for a 50 ms sleep, with the CPU time still near zero. The overshoot is not a fixed amount and not a fixed fraction: it depends on how the operating system groups its timers at that moment. That is one reason a benchmark of anything that sleeps or waits is noisy.

Where the analogy breaks: more than one pair of hands

The timesheet picture says CPU time can never exceed wall time. That holds for a process that computes on one core. It does not hold when a process uses several cores at once, because the CPU clock adds up the time on every core. numpy's matrix product is a good example: numpy hands it to a library that comes with macOS (Accelerate), and that library splits the work across cores.

import time

import numpy as np

rng = np.random.default_rng(0)
a = rng.random((2_000, 2_000))
b = rng.random((2_000, 2_000))

wall_start = time.perf_counter_ns()
cpu_start = time.process_time_ns()
c = a @ b  # a matrix product: numpy hands it to a library that uses several cores
cpu_stop = time.process_time_ns()
wall_stop = time.perf_counter_ns()

wall_ms = (wall_stop - wall_start) / 1_000_000
cpu_ms = (cpu_stop - cpu_start) / 1_000_000
print(f"wall {wall_ms:.1f} ms   cpu {cpu_ms:.1f} ms   cpu share {cpu_ms / wall_ms:.2f}")

One run on the M5; yours will differ:

wall 32.9 ms   cpu 64.0 ms   cpu share 1.94

A CPU share of almost 2: on average two cores were busy for the whole 33 ms. The matrix product is the operation a language model spends most of its time in, so you will meet it again. For your harness, a CPU share above 1 is not a bug: the work ran on more than one core. It is not a speed-up of the same size either. Held to one core (start the program with VECLIB_MAXIMUM_THREADS=1 in front of the command), the same product took 38 ms with a share of 1.00: the second core bought 5 ms of wall time and cost 25 ms of CPU time.

Why one run is not enough

Back to the five runs of one_sum.py. Why did the same code take between 11.4 and 14.3 ms? Nothing in the program changed. Everything around it did.

  • Other processes. Your Mac is running a hundred other programs: the browser, the editor, Spotlight indexing a file. When one of them wants a core at the wrong moment, your program waits, and the wall clock keeps running.
  • Frequency changes. A core does not run at one fixed speed. It speeds up when there is work and slows down to save power and stay cool. A burst of work starts on a core that has not yet sped up: on this Mac, a loop started straight after a half-second pause ran its first few milliseconds at well under half the speed it reached 30 ms later.
  • Two kinds of core. The M5 has 4 performance cores and 6 efficiency cores. The efficiency cores are slower and use much less power. macOS decides which kind your process runs on, and can move it in the middle of a run. The same loop can take several times as long there: pushed onto the efficiency cores on purpose (taskpolicy -b in front of the command), a loop that takes 90 ms here took 650 ms.
  • Caches. The processor keeps recently used memory in small, fast caches close to the core. The first time code touches some data, it comes from main memory, which is slow; the second time it is probably in a cache. Your program's own instructions are cached the same way.
  • The garbage collector. Python frees most objects as soon as nothing refers to them. Objects that refer to each other in a circle need a separate tidy-up, the cyclic garbage collector, which runs every so often (by default once about 2,000 more container objects, such as lists, dicts and instances, have been created than freed). When it runs in the middle of your timing, that call is slower. Python's own timeit module switches it off while it times, for this reason.

You cannot remove all of this, and your users' machines have the same noise. You can time many calls and look at how they spread (chapter 2), and keep the conditions steady and written down: power cable in, heavy programs closed (docs/setup.md, "Measuring on this Mac"). A thousand calls inside one process also share whatever that process happened to get: where its memory landed, which cores it was given. So repeat the whole measurement in a fresh process at least three times, and report the median of the runs and how far apart they were.

Comparing two versions of some code needs two more habits. Measure them in turns (A, B, A, B) and not all of A followed by all of B, so that anything that drifts, such as a background job or a warming machine, falls on both. And first measure one version against itself: the difference you see between two runs of the same code is your noise floor, and only a difference clearly larger than that is a result.

Warm-up

One source of difference is not noise at all, because it is the same every time: the first call. Many functions do extra work the first time they run, and then reuse it. Here is a function that builds a table of all primes below two million on its first call, keeps it in a dictionary, and only looks things up after that:

import time

cache = {}


def nth_prime(i):
    """The i-th prime, from 0. The first call builds a table of primes; later calls reuse it."""
    if "primes" not in cache:
        limit = 2_000_000
        is_prime = [True] * limit
        is_prime[0] = is_prime[1] = False
        for n in range(2, int(limit**0.5) + 1):
            if is_prime[n]:
                for multiple in range(n * n, limit, n):
                    is_prime[multiple] = False
        cache["primes"] = [n for n in range(limit) if is_prime[n]]
    return cache["primes"][i]


for attempt in range(1, 4):
    start = time.perf_counter_ns()
    p = nth_prime(10_000)
    stop = time.perf_counter_ns()
    print(f"call {attempt}: nth_prime(10_000) = {p}, {(stop - start) / 1_000:,.1f} µs")

One run on the M5; yours will differ:

call 1: nth_prime(10_000) = 104743, 64,268.3 µs
call 2: nth_prime(10_000) = 104743, 1.6 µs
call 3: nth_prime(10_000) = 104743, 0.2 µs

The first call took 64 ms, because it built the table (the sieve of Eratosthenes: cross out every multiple of every prime, and what is left is prime). The third took 0.2 µs: three hundred thousand times less. A benchmark that includes the first call reports something that is true once and never again.

The second call is still eight times slower than the third, although the table already existed. The dictionary is the visible warm-up; there are invisible ones. The processor's caches had just been filled with the sieve, not the lookup. And Python 3.13 rewrites a function's bytecode as it runs, specialising each instruction for the types it sees, so a function gets a little faster over its first few calls. You cannot list every warm-up effect of a given function, so the rule is simple: make some calls before you start recording, and throw their times away. Your harness takes a warmup count for exactly this. How many is enough? No number is right for every function, but the recorded times can tell you: if the first tenth of them is typically slower than the last tenth, the warm-up was too short, or the machine drifted while you measured.

Try it

Add the line nth_prime(0) just before the for loop, and predict the three times before you run it.

Show the answer

All three are now small, around a microsecond or less, because the table is built by the call before the loop and none of the timed calls has to build it. The first timed call may still be a little slower than the others: the invisible warm-ups (processor caches, specialised bytecode) are not finished after one call.

When repeating changes the work

Warm-up says: the first call is special, so throw it away. There is a trap on the other side. Some calls change the thing they work on, and then every later call does a different job. Sorting a list in place is the plainest case:

import random
import time

rng = random.Random(1)
marks = [rng.random() for _ in range(1_000_000)]

for attempt in range(1, 4):
    start = time.perf_counter_ns()
    marks.sort()  # in place: the list stays sorted for the next attempt
    stop = time.perf_counter_ns()
    print(f"attempt {attempt}: {(stop - start) / 1_000_000:6.2f} ms")

One run on the M5; yours will differ:

attempt 1:  94.32 ms
attempt 2:   5.66 ms
attempt 3:   5.46 ms

The first attempt sorted a million shuffled numbers. The other two were handed a list already in order, which Python's sort notices in one pass and leaves alone. Here the first reading is the only honest one: a warm-up call would have thrown it away and reported 5 ms for a 94 ms job. No harness can see this, because a harness calls what it is given. Whoever writes the benchmark has to ask of every call: does it leave the world as it found it? A list put in order, a queue emptied, a cache filled: each makes the next call cheaper or dearer than the first.

Try it

Change stale_input.py so that every attempt sorts shuffled numbers, in two ways: copy the list before the first clock read and sort the copy, or call sorted(marks), which builds a new list and leaves marks alone. Predict how the readings will differ, then run both.

What the M5 showed

With the copy made outside the timed stretch, every attempt took about 93 ms. With sorted(marks), about 97 ms: the reading now includes building the new list, which costs 1 to 4 ms on its own. Neither is wrong; a benchmark has to say which it measured. When the work has to be one function of no arguments, the copy can only be made inside it, so time the copy alone as well and report both numbers.

So which is the truth, the first call or the thousandth? It depends on the question. A server that answers requests all day lives in its steady state, the calls after everything has warmed up: warm up, then measure. A tool that runs once and exits is all cold start: measure it in a fresh process each time. Say which you measured.

The cost of reading a clock

Reading a clock is itself a function call, and it takes time. To see how much, read a clock a million times in a loop, and subtract what the empty loop costs:

import time

reads = 1_000_000

start = time.perf_counter_ns()
for _ in range(reads):
    pass
stop = time.perf_counter_ns()
empty_loop_ns = stop - start

start = time.perf_counter_ns()
for _ in range(reads):
    time.perf_counter_ns()
stop = time.perf_counter_ns()
perf_loop_ns = stop - start

start = time.perf_counter_ns()
for _ in range(reads):
    time.process_time_ns()
stop = time.perf_counter_ns()
process_loop_ns = stop - start

print(f"empty loop:         {empty_loop_ns / reads:6.1f} ns per turn")
print(f"perf_counter_ns():  {(perf_loop_ns - empty_loop_ns) / reads:6.1f} ns per read")
print(f"process_time_ns():  {(process_loop_ns - empty_loop_ns) / reads:6.1f} ns per read")

One run on the M5; yours will differ:

empty loop:           10.5 ns per turn
perf_counter_ns():    25.0 ns per read
process_time_ns():   267.1 ns per read

The stopwatch costs about 25 ns to read, because it reads the hardware counter without asking the kernel. The CPU clock costs ten times as much: the process's account lives in the kernel, and asking the kernel anything is a system call, a switch from your program into the operating system and back. Three consequences for timing a single call:

  • Every timing includes some of the clocks' own cost: nothing for a 10 ms call, a third of the answer for a 1 µs call timed with both clocks. BENCH.md suggests measuring this floor with your own harness.
  • Steps matter for short calls. On the M5, sum(range(300)), timed on its own between both clocks as in kettle_and_sums.py, read 1,250 to 1,458 ns on the stopwatch (multiples of the 41.7 ns tick). The CPU clock said 1,000 ns three times in four, and otherwise 2,000 or 0. One CPU reading of a short call says almost nothing; the total over many calls is what means something.
  • Put the cheaper, finer clock on the outside, as in kettle_and_sums.py: the wall time then includes the CPU clock's 267 ns, and the CPU time includes none of the stopwatch's.
Trap

Do not put anything between the clock reads but the work. A print, an append to a list or a format string inside the timed stretch is timed too, and for a short call it can cost more than the call itself. Read the clock, call, read the clock; everything else goes outside.

Two kinds of CPU time: user and system

The kernel keeps the CPU account in two parts. User time is the time a core spent running your program's own instructions, the Python interpreter's included. System time is the time a core spent inside the kernel on your program's behalf, in system calls: copying the bytes of a file, handing out memory, sending on a network. process_time_ns returns the two added together, which is all a CPU share needs. The shell shows them apart for a whole program: put time in front of a command.

$ time uv run python scratch/one_sum.py

One run on the M5, the last line zsh prints; yours will differ:

uv run python scratch/one_sum.py  0.02s user 0.01s system 91% cpu 0.032 total

That is user time, system time, the CPU share as a percentage, and the wall time (total) of the whole process, starting Python included. The split tells you where to look next. High user time: the cost is in your code or in Python, and a profiler finds the line (chapter 5). High system time: you are asking the kernel for a lot, in many small requests or many bytes moved. Wall time on neither account: the process was off the core, waiting, and no faster code will shorten that.

Short calls: time a batch

sum(range(300)) read about 1,300 ns when it was timed on its own with both clocks. How much of that was the sum? For a call this short the answer comes from another way of timing: make many calls between one pair of clock reads, and divide. The clock's cost and its step are then spread over the whole batch. Python ships a tool that does this, timeit:

$ uv run python -m timeit "sum(range(300))"

One run on the M5; yours will differ:

500000 loops, best of 5: 781 nsec per loop

Two decisions are packed into that line, and a third is out of sight.

  • 500000 loops. timeit tried batches of 1, 2, 5, 10 and so on, until one batch took at least 0.2 s, and then divided the batch's time by its size. A batch of 0.4 s is ten million ticks of the stopwatch, so one tick and one clock read no longer matter.
  • Best of 5. It timed five batches and reported the fastest. For pure computation, noise almost always adds time: another process can make the sum slower, and nothing makes it faster than the machine is. So the smallest reading is the one closest to the cost of the code itself.
  • It switched the cyclic garbage collector off while it timed.

So the sum costs about 780 ns, and some 500 ns of the 1,300 was the measuring: two reads of the CPU clock, at 267 ns each, sat inside the stopwatch's reading.

Trap

Give timeit something to compute. python -m timeit "2**10" reports 2 ns on the M5, because Python worked out 1024 once, when it compiled the line, and the loop then times nothing. With the 2 in a variable (-s "x = 2" "x**10") it reports 16 ns. And the -s setup runs once per batch, not once per loop, so a setup that builds a list and a statement that sorts it is the stale input again.

A batch buys precision and pays for it with the spread: one number for half a million calls, the slow ones averaged in among the fast. Which number to report depends on the question:

  • "What does this code cost, and which of two ways of writing it costs less?" The minimum, from batches.
  • "How long does a call typically take?" The median of single calls.
  • "How long will a user wait on a bad day?" The high percentiles, p95 and p99, of single calls (chapter 2).

Your harness times every call singly, because the spread is its purpose. That suits calls that take far longer than the clocks cost, from some tens of microseconds upward.

Functions are values

Your harness has to call a function it is given, many times, without knowing in advance which function that is. That needs one idea from Python that you may have used without naming it: a function is an ordinary value, like a number or a list. You can pass it to another function, keep it in a variable, and call it later.

Python you need

Functions as values. shout is the function; shout("tea") calls it. Leave off the brackets and you are passing the function itself, to be called later. lambda makes a small function without a name, in place: lambda w: w[::-1] takes w and returns it reversed. A lambda with no parameters, lambda: shout("ready"), packs up a call with its arguments into a function that takes none. A closure is a function defined inside another one that remembers the variables of the call that made it, even after that call has returned. nonlocal lets the inner function assign to such a variable.

def shout(word):
    return word.upper() + "!"


def apply_to_each(action, items):
    return [action(item) for item in items]


words = ["kettle", "clock", "tea"]

print(type(shout), shout.__name__)         # a function is a value, with a type and a name
print(apply_to_each(shout, words))         # pass it without brackets: no call happens here
print(apply_to_each(len, words))           # built-in functions are values too
print(apply_to_each(lambda w: w[::-1], words))  # a function with no name, written in place

later = lambda: shout("ready")             # no arguments: it remembers what to call, and with what
print(later.__name__)
print(later())

<class 'function'> shout
['KETTLE!', 'CLOCK!', 'TEA!']
[6, 5, 3]
['elttek', 'kcolc', 'aet']
<lambda>
READY!

apply_to_each does not know what action is, only that it can be called with one item. And later is a function of no arguments that calls shout("ready"): the argument travels inside it. This is how a call that needs arguments is handed to code that will only ever call fn().

A closure is the same trick with a def inside a def:

def make_greeter(greeting):
    def greet(name):
        return f"{greeting}, {name}"  # greeting comes from the enclosing call

    return greet


morning = make_greeter("Good morning")
evening = make_greeter("Good evening")
print(morning("Danish"))
print(evening("Danish"))


def make_counter():
    count = 0

    def tick():
        nonlocal count  # assign to the enclosing call's count, not to a new local
        count += 1
        return count

    return tick


tick = make_counter()
tick()
tick()
print("ticks:", tick())

Good morning, Danish
Good evening, Danish
ticks: 3

Each call of make_greeter creates a new greet that remembers its own greeting. Without nonlocal, the line count += 1 would make count a new local variable of tick, and Python would stop with UnboundLocalError, because the local has no value yet when += 1 reads it. The tests of M1 use closures like these to count how many times your harness called them.

One thing about closures surprises everybody once. Predict the two lines before you run this:

jobs = [lambda: n * 10 for n in range(3)]
print([job() for job in jobs])

jobs = [lambda n=n: n * 10 for n in range(3)]
print([job() for job in jobs])

[20, 20, 20]
[0, 10, 20]
Trap

A closure remembers the variable, not the value it had when the function was made. All three lambdas in the first list look up n when they are called, and by then the loop has finished and n is 2. The second list fixes it with a default argument, n=n, which is evaluated once, when each lambda is made, and so freezes the value. If you build a list of zero-argument lambdas in a loop to time later, this is the bug that makes every one of them do the same thing.

A worked example: breakfast

Put the pieces together on a job that both waits and works: wait 100 ms for the kettle, then do some arithmetic. Before running it, predict. The sums in kettle_and_sums.py did three million additions in about 116 ms; this loop does two million turns, each a remainder and an addition, so call it 70 to 80 ms of work. The sleep adds at least 100 ms of waiting. So the prediction is: wall about 180 ms, CPU about 75 ms, CPU share about 75 / 180, a little over 0.4.

import time

wall_start = time.perf_counter_ns()
cpu_start = time.process_time_ns()

time.sleep(0.1)  # wait for the kettle
toast = 0
for slice_number in range(2_000_000):  # then do some work
    toast += slice_number % 7

cpu_stop = time.process_time_ns()
wall_stop = time.perf_counter_ns()

wall_ms = (wall_stop - wall_start) / 1_000_000
cpu_ms = (cpu_stop - cpu_start) / 1_000_000
print(f"wall {wall_ms:.1f} ms, cpu {cpu_ms:.1f} ms, waiting {wall_ms - cpu_ms:.1f} ms, "
      f"cpu share {cpu_ms / wall_ms:.2f}")

One run on the M5; yours will differ:

wall 183.0 ms, cpu 73.0 ms, waiting 110.0 ms, cpu share 0.40

The prediction held, and wall time minus CPU time recovers the waiting: the 100 ms that was asked for and the 10 ms by which this sleep overshot. That subtraction is a tool on its own: when a real program is slow, it tells you how much of the slowness is waiting (for a disk, a network, a lock), which no faster arithmetic will fix. (Strictly, the difference is time off the core: mostly waiting for something, but also any time spent ready to run while another process held the core.)

In a real engine

A serving engine is timed with exactly these two subtractions. The client of vLLM's serving benchmark (vllm bench serve) reads time.perf_counter() when it sends a request and again each time a piece of the streamed answer arrives. Time to first token (TTFT) is the first arrival minus the send; each inter-token latency (ITL) is one arrival minus the one before. Inside the engine, each request carries stamps of the same kind (when it arrived, was scheduled, produced its first and its latest token), and the engine's metrics are differences of them. One warning for Module 6 onwards: work on a GPU runs asynchronously. Python asks the GPU to start, and the call returns at once, while the GPU is still computing. Either clock, read around that call, measures only the asking, unless you first wait for the GPU to finish (in PyTorch, torch.mps.synchronize() on the Mac and torch.cuda.synchronize() on an NVIDIA card).

Check yourself

Why is time.time() the wrong clock for measuring how long something took, even though it shows the right time of day?

Answer

It is adjustable and not monotonic: the Mac may correct it against a time server between your two readings, so the difference includes the correction and can even be negative. perf_counter_ns never goes backwards and nothing outside your program changes it.

A function waits 50 ms for a file to arrive over the network and then computes for 10 ms. Predict its wall time, CPU time and CPU share.

Answer

Wall time about 60 ms, CPU time about 10 ms, CPU share about 10 / 60 ≈ 0.17. The waiting shows only on the stopwatch.

A benchmark reports a CPU share of 3.2. Is the benchmark broken?

Answer

Not necessarily. The CPU clock adds up the time on every core the process used. A share of 3.2 means that, on average, a little over three cores were busy during the call, as when numpy hands a matrix product to a multi-core library.

get_clock_info("process_time").resolution is 1e-06 on the M5. You time a call that takes about 300 ns with the CPU clock. What readings do you expect?

Answer

Only 0, 1,000 and now and then 2,000 ns, with 0 and 1,000 about equally often. The CPU clock moves in whole microseconds, so the reading says how many steps the call happened to straddle, and never 300. Only the total over many calls is meaningful.

Name three reasons why the same code runs in a different time on two runs, and say for each whether warm-up calls would remove it.

Answer

Any three of: other processes taking a core (no), frequency changes (partly: some tens of milliseconds of work before recording let the core speed up), being placed on an efficiency core instead of a performance core (no), cold caches (yes, mostly), the garbage collector running mid-call (no), a cache the function itself builds on its first call (yes).

A benchmark script calls queue.sort() three times to warm up and then times twenty more calls, on a queue of a million shuffled numbers. Its median reading is 5 ms. What did it measure, and what do you change?

Answer

It measured sorting a list that is already sorted: the first warm-up call put the queue in order, and every later call found it so. To measure sorting shuffled numbers, each call needs a fresh shuffled copy, with the cost of making the copy measured and reported beside it.

python -m timeit says a call costs 800 ns, "best of 5". Your service makes that call once per request, and you are asked what its p99 is. Why can timeit's number not answer that, and why is it still the right number for choosing between two ways of writing the call?

Answer

Each of timeit's readings is one batch of many calls divided by its size, so the slow calls are averaged away, and "best of" then keeps the quietest batch: the tail is exactly what it removes. A p99 needs every call timed singly. For choosing between two ways of writing a small computation, that removal is the point: the minimum is the reading with the least noise in it.

You want to hand shout("tea") to code that will only ever call fn(), with no arguments. What do you pass?

Answer

lambda: shout("tea"): a function of no arguments that, when called, calls shout with "tea". Passing shout("tea") would call it right away and pass its result, a string, which cannot be called.
