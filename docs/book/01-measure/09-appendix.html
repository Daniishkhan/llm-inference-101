Reading a traceback

When a Python program raises an exception that nothing catches, the interpreter stops and prints a traceback: the chain of calls that were in progress at that moment, and the exception at the end. It is called a traceback because it lists the calls from the outside in, oldest first, so the line where things went wrong is at the bottom. Read it from the bottom up.

First principle

While a program runs, the interpreter keeps one frame for every call that has started and not yet returned: the function, its local variables, and the line it is on. The frames form a stack (chapter 7): a call pushes one, a return pops one. A traceback is a printout of that stack at the moment of the exception, one entry per frame, with the outermost frame (your script, called <module>) at the top.

A trip with three legs, one of which took no time at all:

def average_speed(distance_km, hours):
    return distance_km / hours


def trip_report(legs):
    speeds = [average_speed(km, hours) for km, hours in legs]
    return max(speeds)


legs = [(120, 1.5), (80, 1.0), (15, 0)]
print(trip_report(legs))

ZeroDivisionError: division by zero

(Paths in the outputs of this chapter are shortened to …/; yours show the full path to scratch/.) Read it in this order:

  1. The last line is the exception: its type, ZeroDivisionError, then its message, division by zero. Most of the time this line alone tells you what happened.
  2. The entry just above it says where: the file, line 2, inside average_speed, with the line's source text. Since Python 3.11 the carets under the line (~~~^~~~) point at the exact operation inside the line, here the /.
  3. Walk upwards to find out how the program got there: trip_report called it at line 6, and the script called trip_report at line 11. The first entry that is in your code, reading upwards, is usually where the fix goes. Here the bug is not the division, which is correct, but the data: a leg of 0 hours.

When a test fails, the entries at the top of a traceback belong to pytest and the ones at the bottom to your code; pytest hides its own frames, which is one reason its reports are shorter. When an exception happens while another one is being handled, Python prints both tracebacks, joined by "During handling of the above exception, another exception occurred". Read the last one first; the first one is the cause.

Analogy

A line of people passing a message along, each of whom asked the next one for help. The traceback lists them from the first who asked to the last, who is the one who failed. Where it breaks: the person who failed is not always the one to blame. The last entry says where the error was noticed; the mistake can be in any frame above it, often in an argument passed down from higher up.

Reading pytest's output

pytest runs every function whose name starts with test_ in every file whose name starts with test_, and reports. A toy test file with one bug in each of two functions:

import pytest


def to_fahrenheit(celsius):
    return celsius * 9 / 5 + 23  # a bug: the offset is 32


def parse_reading(text):
    """'21.5C' -> 21.5. Should raise ValueError for anything that does not end in C."""
    return float(text.rstrip("C"))


def test_freezing_point():
    assert to_fahrenheit(0) == 32


def test_a_week_of_readings():
    readings = [to_fahrenheit(c) for c in (0, 10, 20)]
    assert readings == [32, 50, 68]


def test_a_reading_without_its_unit_is_refused():
    with pytest.raises(ValueError):
        parse_reading("21.5")


def test_a_reading_with_its_unit():
    assert parse_reading("21.5C") == 21.5

  • The progress line, FFF.: one character per test, in file order. . passed, F failed (an assertion was false), E an error outside the test itself (in a fixture, or at import), s skipped.
  • One section per failure, headed by the test's name: the file and line of the test, the line that failed, and then the E lines, which are what went wrong.
  • Assertion rewriting. A plain assert only knows "true" or "false". pytest rewrites every assert in a test file before it runs, so that on failure it can show the values on both sides: assert 23.0 == 32 and, under it, where the 23.0 came from: where 23.0 = to_fahrenheit(0). For lists it shows the first index at which they differ. That is why tests here use bare assert and not assertEqual.
  • DID NOT RAISE. with pytest.raises(ValueError): fails when the block inside it finishes without raising. The code accepted input that the spec says it must refuse.
  • The short summary at the bottom: one line per failure, and the totals.

Four options change what you see. -x stops at the first failure, which is how you work one red test at a time. -k week runs only the tests whose name contains "week" (and -k "not slow" all the others). --lf ("last failed") reruns only the tests that failed last time, which pytest remembers in .pytest_cache/. -q drops the header and keeps the report short; -vv does the opposite and prints full diffs instead of "Use -v to get more diff". Trap

A test that passes on day one is not a test you have passed. In this module five tests are green before you type anything: they read your code and check that stats.py neither imports numpy nor sorts, that two drills do not sort, and that a third does not import a path library. They are green because the stubs do nothing, and their job is to stay green.

Reading hypothesis output

A property test does not check one example; it states something that must be true for every input of some kind, and hypothesis tries a hundred inputs of that kind, chosen to find trouble: empty lists, zeros, huge and tiny numbers, repeats. A bill split into shares that should add up to the bill:

from hypothesis import given
from hypothesis import strategies as st


def split_bill(total_pence, people):
    """Shares in whole pence, one per person, that add up to the total."""
    return [total_pence // people] * people  # a bug: the remainder goes missing


@given(total_pence=st.integers(0, 10_000), people=st.integers(1, 10))
def test_the_shares_add_up_to_the_bill(total_pence, people):
    assert sum(split_bill(total_pence, people)) == total_pence

The E lines are pytest's as usual, then hypothesis adds the failing example: the arguments for which the property was false. This version of hypothesis heads it "Failing test case"; older versions and most of what you read online say "Falsifying example". It is the same thing.

The example is small for a reason. The first input that failed was probably something like total_pence=7311, people=6. Hypothesis then shrinks it: it tries smaller and simpler inputs that still fail (smaller numbers, shorter lists, earlier letters) until it cannot make it any simpler. One penny shared by two people is the smallest bill that loses its remainder, and that is the example you are shown. Read it as a ready-made scratch/ program: call the function with exactly those arguments and look.

Hypothesis also remembers. Every failing example is saved in a .hypothesis/ folder next to where you ran pytest (git ignores it), and the next run tries the saved examples first. So a failure you have not fixed fails again at once, and a fix you think works is tested on the very input that broke it. If a failure ever seems to follow you after you have changed the test itself, deleting .hypothesis/ is safe.

Looking at data with numpy and statistics

CallGives
np.percentile(xs, 95), np.percentile(xs, [50, 95, 99])Percentiles by the linear method, the definition your percentile matches
np.histogram(xs, bins=20)(counts, edges): 20 counts and 21 edges of equal-width bins
np.mean, np.median, np.std, np.min, np.maxThe usual summaries
statistics.fmean(xs), statistics.median(xs), statistics.stdev(xs)The same without numpy
statistics.quantiles(xs, n=100, method="inclusive")The 99 cut points between 100 equal groups; with method="inclusive" they agree with numpy's linear method, with the default ("exclusive") they do not

These are for looking at data and for checking your answers by hand. Your stats.py may use none of them: its percentile is built on your quickselect.

import statistics

import numpy as np

commute_min = [22, 25, 24, 31, 23, 26, 58, 24, 27, 25, 23, 41]

print("mean   ", round(statistics.fmean(commute_min), 2))
print("median ", statistics.median(commute_min))
print("stdev  ", round(statistics.stdev(commute_min), 2))
print("numpy p50, p90, p99:", np.percentile(commute_min, [50, 90, 99]))
print("quartiles, numpy's way:   ", statistics.quantiles(commute_min, n=4, method="inclusive"))
print("quartiles, the default way:", statistics.quantiles(commute_min, n=4))
counts, edges = np.histogram(commute_min, bins=4)
print("counts", counts)
print("edges ", edges)

sys.settrace and its events

PieceWhat it is
sys.settrace(tracer)Installs a global tracer: from now on, every new call in this thread calls tracer(frame, "call", None)
sys.settrace(None)Removes whatever tracer is installed, yours or another tool's. To stop tracing, put back the one you found instead: old = sys.gettrace() before, sys.settrace(old) in a finally (chapter 5's Trap)
sys.gettrace()The tracer installed now, or None
the tracer's return valueOn a "call" event, the function to use as the local tracer for that frame's other events, or None for "not interested in this frame"
"call"A function is entered; arg is None
"line"A new line is about to run, in a frame that has a local tracer
"return"A function is about to return; arg is the value it returns
"exception"An exception happened in the frame; arg is (type, value, traceback)
frame.f_code.co_name, frame.f_code.co_filenameThe function's name and file
frame.f_linenoThe line number the frame is on now
frame.f_backThe caller's frame

A tracer is called by the interpreter for every event, so a program runs many times slower while one is installed. That is the price of exact counts, and the reason profilers of busy servers sample instead (chapter 5).

Glossary

Assertion rewriting
pytest's trick of rewriting each assert in a test file so that a failure shows the values on both sides (9).
Big-O
How the number of steps grows with the size of the input, keeping only the fastest-growing part: O(n), O(n log n), O(n²) (3, 7).
Bin
One of the equal-width ranges of a histogram, and the count of values that fall in it (2).
Binary search
Finding a value in a sorted list by looking at the middle and throwing away the half it cannot be in, again and again (3).
Box
The object Python wraps around every value, with its type and reference count, which is why a float takes 24 bytes and not 8 (6).
Cold start
The first call, or a whole run in a fresh process, with nothing warmed up; what a tool that runs once and exits lives in (1).
Contiguous
Stored side by side in one block of memory, as the numbers in a numpy array are and the floats of a list are not (6).
CPU share
CPU time divided by wall time: about 1 for busy work, about 0 for waiting (1).
CPU time
The time a process spent computing, measured with time.process_time_ns; it stops while the process waits. It is user time plus system time (1).
Edge
A boundary between two bins of a histogram; n bins have n + 1 edges (2).
Event
One thing a tracer is told about: a call, a line, a return or an exception (5).
Expected value
The average result of something random over many tries, such as 3.5 for one die (3).
Frame
The interpreter's record of one call in progress: the function, its locals, and the line it is on (5).
Half-open interval
An interval that includes its start but not its end, like a booking from 13 to 15 (7).
Hash
A number computed from a key, used by a dict or a set to jump to the key's slot without searching (7).
Histogram
A count of how many values fall in each of a row of bins, drawn as bars: the shape of a spread (2).
Interpolation
Reading a value between two known ones on the straight line that joins them (2).
Kernel
The part of the operating system that owns the hardware, decides which process runs on which core, and keeps each process's CPU account (1).
Markup
rich's square-bracket tags, such as [bold], that style text instead of being printed (4).
Noise floor
The difference you measure between two runs of the same code; a difference between two versions counts only if it is clearly larger (1).
Oracle
A slow or trusted way to get the right answer, used to check a fast one; numpy is this module's (8).
p50, p95, p99
The 50th, 95th and 99th percentiles: the typical call, and the slow calls one in twenty and one in a hundred users meet (2).
Partition
Splitting items around a pivot into smaller, equal and larger groups (3).
Percentile
The value below which a given percentage of the values lie (2).
Pivot
The value a partition splits around (3).
Profiler
A tool that says where a program spends its time (5).
Property test
A test that states something true for every input of a kind and lets hypothesis search for an input that breaks it (2).
Quickselect
Finding the k-th smallest value by partitioning and keeping only the side the answer is on: about n steps on average (3).
Resolution
The smallest step a clock can show (1).
Run
A stretch of neighbours in a sequence that agree: the same letter, the same direction (7).
Sampling
Profiling by looking at where a program is at regular moments instead of recording every event: cheap and approximate (5).
Selection
Finding the value at one position of the sorted order without sorting (3).
Shrinking
Hypothesis's search for the smallest, simplest input that still fails (2).
Sliding window
A fixed-width run of consecutive items that moves one step at a time, one item in and one out (7).
Stack
A pile where you only touch the top: last in, first out (7).
Steady state
The calls that come after everything has warmed up; what a server that runs all day lives in (1).
System call
A request from a program to the kernel, such as reading a file or asking for the CPU clock; it costs a switch into the kernel and back (1).
System time
CPU time spent inside the kernel on a program's behalf (1).
Tail
The slow end of a spread of timings, where p95 and p99 live (2).
Throughput
Calls completed per second of wall time; the docstring of summarise defines it (8).
Traceback
The printout of the calls in progress when an exception was raised, oldest first (9).
Tracer
A function the interpreter calls on every event once it is installed with sys.settrace (5).
User time
CPU time spent running a program's own instructions, the interpreter's included (1).
Wall time
Time on a stopwatch, waiting included, measured with time.perf_counter_ns (1).
Warm-up
Calls made before recording starts, so that one-time costs such as filling a cache are not counted (1).

What Module 2 brings

Module 2 is the tokenizer: the piece of an engine that turns text into the numbers a model reads, and back. A preview, so that you recognise the names; nothing here is needed this module.

  • Bytes and UTF-8. A string is a sequence of characters, but a file, a socket and a tokenizer see bytes. UTF-8 spends one byte on an English letter and up to four on other characters, so the length of a text depends on what you count.
  • Byte-pair encoding (BPE). Start from single bytes, count every pair of neighbours, merge the most frequent pair into a new token, and repeat. GPT-2's tokenizer is the list of merges this produced.
  • The patterns. Hash maps, to count the pairs (this module's dicts again); heaps, to find the best merge first; linked lists, to merge neighbours in place without shifting a whole list.
  • Done when round trips are exact on any Unicode text, and your token ids match GPT-2's tokenizer on the test set, with tiktoken as the oracle.
  • Measured with the harness you build this week: how many tokens per second, and what tokenization does to cost and latency.

Check yourself

A traceback has four entries and ends with KeyError: 'p95'. Which entry do you read first, and what do you look for in it?

Answer

The last one, just above the exception: the file, the line and its source text, with the carets under the part that failed. There a dict was read with the key 'p95', which it does not have. Then walk upwards to find where that dict was built, which is often where the fix goes.

pytest prints E assert [1, 2, 4] == [1, 2, 3]. What does it tell you, and what made it possible?

Answer

Your code returned [1, 2, 4] where the test expected [1, 2, 3]; the next line says they differ at index 2. Assertion rewriting made it possible: pytest rewrote the plain assert so that it keeps the values of both sides.

Which pytest command reruns only the tests that just failed, and stops at the first one that still fails?

Answer

uv run pytest --lf -x, with the path if you want to limit it.

Hypothesis reports a failing example values=[0.0, 0.0]. Why is it so small, and what do you do with it?

Answer

Hypothesis shrank the input that first failed to the simplest one that still fails. Call your function with exactly that input in a scratch/ program and look at what it does. The example is also saved in .hypothesis/, so the next run tries it first.

Your quickselect passes on shuffled lists and fails with RecursionError on a list that is already in order. What is wrong, in one sentence?

Answer

The pivot comes from a fixed place, so on ordered input each round throws away only one element and the recursion goes n deep, past Python's limit of about 1,000.

Your report shows line 12: squares = and nothing after the equals sign. What happened?

Answer

rich read the square brackets of the source text as markup and removed them with everything inside. Escape the text with rich.markup.escape, or pass it as a Text.

How many bytes does the word "naïve" take in UTF-8?

Answer

Six: one each for n, a, v and e, and two for ï. It is five characters.
